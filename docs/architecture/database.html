1. Relationship diagram

Arrows run from the table holding the foreign key to the table it references (many to one). Ink solid: a declared foreign key. Amber dashed: a link enforced by a trigger or by convention, with no foreign key. References to users from deeper tables are written inside the box (→ users) instead of drawn, to keep the picture readable.

2. How tenancy and roles work

  • Two roles. The owner role runs migrations, owns every object, and bypasses RLS (used by migrations, the dev seed and the test harness). sk_app is created NOLOGIN in 0001; the API connects and runs SET ROLE sk_app for every request, so policies apply. A LOGIN role with a real password is a deployment task, not in the repo (rule 12).
  • Household context. At the start of each request transaction the API runs set_config('app.household_id', <uuid>, true). app_current_household() reads it; unset means NULL, every policy compares to NULL, and nothing is visible or writable. Isolation fails closed.
  • Policies. Every household-scoped table has one policy, <table>_current, with USING and WITH CHECK both household_id = app_current_household(). users is visible only when the user shares the current household.
  • Not FORCE. FORCE ROW LEVEL SECURITY is deliberately off, so the SECURITY DEFINER ledger trigger (owned by the owner role) is bound by its foreign keys rather than by the caller's session setting (0006 header).
  • Doors with no household yet. Creating a household, redeeming a join code and listing my memberships happen before a household context exists, so they go through three SECURITY DEFINER functions (section 7) instead of table grants.
  • Least privilege. sk_app has no DELETE anywhere and no UPDATE on any quantity column or the ledger. Section 7a has the full matrix.

8. Observations for review

Things a database developer would likely question. Each is ENGINEERING INFERENCE from reading the DDL, not a decision; several are deliberate trade-offs, noted where the repo says so. Any change is a new migration with your approval.

  1. Two ways to reference a member. inventory_confirmations.confirmed_by and inventory_item_moves.moved_by point at memberships by (household_id, user_id); the shopping tables point by (household_id, id) (membership id). Both work; mixing them makes joins and future deletion rules inconsistent. Worth picking one before more tables are added.
  2. Units are text in three places with three rules. inventory_items.unit only checks nonblank (the domain registry validates it in code); shopping_rows.unit has a 10-value CHECK; the ledger copies the item's unit by FK. A lookup table, a domain type, or one shared CHECK would keep them aligned.
  3. Enumerations are text with CHECK. Location, tier, type, status and role are all text CHECK IN (…), repeated per table (the location set appears four times). Deliberate for easy migration; a CREATE DOMAIN per set would remove the repetition without enum-type rigidity.
  4. Quantity stored twice. *_micros bigint plus a numeric(24,6) mirror, with a CHECK that they agree. The mirror is for human reads; it could be a generated column (GENERATED ALWAYS AS (… / 1000000) STORED) instead of a written one.
  5. No ON DELETE path for household data. Memberships and join codes cascade from households; items, lots, ledger, shopping and the append-only tables do not, and the append-only triggers block DELETE for every role. Deleting or exporting a household (ARCHITECTURE §7.13, needed before launch) has no designed path yet.
  6. Soft links without foreign keys. inventory_transactions.correlation_id is text holding a uuid; shopping_rows.added_transaction_id is trigger-checked; shopping_row_writes.transaction_id is unchecked. The correlation design is polymorphic (receipt line, meal log, shopping item), which is why it is not a foreign key.
  7. Index leading columns. inventory_lots_item_idx is on (item_id) alone and inventory_transactions_correlation_idx on (correlation_kind, correlation_id) without household_id, while most other indexes lead with household_id. Fine at current size; worth aligning when RLS filters show in plans.
  8. Timestamp defaults are mixed. Older tables default to now() (transaction start), newer ones to clock_timestamp(), after M2-T3a showed transaction-start stamps can order wrongly under concurrency.
  9. Nullable location. inventory_items.storage_location is nullable while moves and shopping require one. Intentional for imports, but the app always sets it today.
  10. Insert-only by grant vs by trigger. The ledger, confirmations and moves block UPDATE and DELETE for every role (trigger); shopping_row_writes relies on sk_app's grants only, so the owner role could change it.
  11. RLS not forced. Owner and superuser bypass policies by design (0006 header). Production must make sure nothing in the app path runs as the owner role.
  12. Printed best-by dates as instants. inventory_lots.expires_at is timestamptz; a printed date stored as UTC midnight reads a day early west of UTC (open M3-T11 follow-up). A date column for printed dates is the usual fix.

9. Proposed tables (from the revisit, not designed)

Names only, from the foundation revisit; nothing is decided and no DDL exists. Listed so the review above can account for them: ingredients (global, read-only), recipes and recipe_ingredients (global, read-only), plan_entries (household, one per date and meal), household_settings (one row per household), meal_logs (append-only, correlation target for USE_IN_MEAL rows), a per-ingredient shopping state table, and an optional ingredient key on shopping_rows.
