## 2. Dependency added

`@types/node` as a **devDependency only** in `apps/mobile/package.json`, for
`src/lint-rules/copy-scan.test.ts` alone (it does real `node:fs`/`node:path` I/O to scan the tree, the
same reason `packages/adapters` already carries this exact devDependency for its own
`recommendations-corpus-consistency.test.ts`). It is opted in with a file-scoped
`/// <reference types="node" />` rather than adding `"node"` to `apps/mobile/tsconfig.json`'s
project-wide `types` array. No runtime/production dependency was added.

**Correction (review F3):** the first draft of this report, and of the file's own doc comment, claimed
the triple-slash reference kept Node's ambient globals scoped to that one file. That claim was wrong.
TypeScript ambient global declarations are program-wide once any file in the compilation references
them, so `process.env`, `Buffer`, `NodeJS.Timeout`, etc. type-checked clean from every other file in
this app too, including `src/onboarding/validation.ts`, which has nothing to do with Node. The actual
containment now in place is an eslint rule, not the triple-slash reference: `eslint.config.js` adds
`no-restricted-globals` for `process`, `Buffer`, `__dirname`, `__filename` and `global`, scoped to
`apps/mobile/app/**` and `apps/mobile/src/**` with an exception for `src/lint-rules/**`. It blocks
*using* those five names as globals outside that one directory (a locally declared identifier of the
same name, e.g. `domain-boundary.test.ts`'s own `declare const process`, shadows the global and is
unaffected). `apps/mobile/src/lint-rules/node-global-containment.test.ts` proves the rule.

Alternative considered and rejected for the devDependency itself: hand-rolling local
`declare module "node:fs" { ... }` blocks to avoid the devDependency entirely. This compiled under
`tsc -b` far less reliably than the triple-slash reference (`TS2591` persisted regardless of the shape
of the hand-written ambient module), so the small, precedented devDependency plus the eslint
containment fix was the more robust combination.

## 3. A pre-existing latent bug this ticket had to fix to meet its own acceptance bar

M2-T1's review (triaged at acceptance, and again at M3-T1's acceptance) flagged, as a **known M3-T3
blocker**: importing `FixtureApiClient` from any screen fails `expo export`, because
`@smart-kitchen/adapters`'s barrel re-exports `product-lookup`, which evaluates
`fileURLToPath(import.meta.url)` (`node:url`/`node:path`) at module load, something Metro cannot bundle
for React Native. It was harmless in M3-T1 because no screen imported `client.ts` yet.

M3-T2 is the first ticket that wires a screen to the client (S1, S2, Home all call it), which makes
that latent failure real and directly blocks this ticket's own required acceptance check
(`pnpm --filter mobile export` green). I fixed it **inside this ticket's existing file scope**
(`apps/mobile/src/api/client.ts` extension): the fixture inventory and household data are now plain
`@smart-kitchen/contracts`-shaped literals defined in `client.ts` itself, not read through
`@smart-kitchen/adapters`. `packages/adapters`'s own barrel, its `@smart-kitchen/adapters` dependency
entry in `apps/mobile/package.json`, and its tsconfig project reference are all untouched, removing
those now-unused entries is still M3-T3's job per the existing backlog note. `expo export` produces
both Android and iOS bundles cleanly from an empty build state (verified below, both before and after
this round's review fixes). The independent review endorsed this fix. Still worth a reviewer's second
look given its footprint goes beyond onboarding itself.

### Round two (re-review of `cfa0118`)

- **F18 (major).** `resolveLayoutRedirect` was correct, but `app/_layout.tsx` called it with the
  *previous* pathname's onboarding-state read, because the read is async and the layout does not
  remount between navigations. Concretely: S2's Continue calls `router.replace("/")`; on the frame
  where `pathname` becomes `"/"`, the in-flight fetch had not resolved yet, so the layout still held
  the pre-save read (tagged, in spirit, for `/onboarding/allergies`) and computed
  `resolveLayoutRedirect("s2", "/")`, which redirected straight back to S2, forcing a second Continue
  press. Fixed by tagging every read with the pathname it was fetched for
  (`OnboardingStateRead = { pathname, state }` in `src/onboarding/route.ts`) and adding
  `resolveLayoutRedirectForRead(read, pathname)`, which only computes a redirect when
  `read.pathname === pathname`; otherwise it returns `null` and `_layout.tsx` renders `Slot` (the
  destination screen) for that one frame instead of redirecting away on stale data. `route.test.ts`
  adds a pure test for exactly this fresh-vs-stale decision, including the precise F18 scenario (a
  stale read tagged for `/onboarding/allergies`, current pathname `/`, must not redirect).
- **F19 (minor).** `no-restricted-globals` (F3) catches the bare identifiers `process`/`Buffer`/etc.
  but not a member access through `globalThis` (`globalThis.process`), which reaches the same ambient
  global by a different path. Rather than adding `"globalThis"` itself to `no-restricted-globals`
  (which would also have flagged `apps/mobile/src/api/client.test.ts`'s legitimate
  `globalThis.fetch = …` mocking, `fetch` is a web standard, not a Node global), added
  `no-restricted-properties` entries for `globalThis.process`/`.Buffer`/`.__dirname`/`.__filename`/
  `.global` specifically, in the same `eslint.config.js` block, same file exception
  (`src/lint-rules/**`). `node-global-containment.test.ts` gets a matching describe block proving both
  that each of the five is rejected through `globalThis` and that `globalThis.fetch` still lints
  clean. `copy-scan.test.ts`'s doc comment now also notes that `NodeJS.*` *types* (e.g.
  `NodeJS.Timeout` used as a type annotation) remain visible everywhere by design, only runtime global
  values are restricted, a type has no runtime access to anything.
- **F20 (minor).** S1's two inline error notices (household-name validation, join-code rejection) set
  `accessibilityLiveRegion="assertive"` but never called `AccessibilityInfo.announceForAccessibility`,
  so iOS VoiceOver (which does not support `accessibilityLiveRegion`) never heard them, only Android
  would have. Both `handleCreateHousehold`'s and `handleJoinHousehold`'s error branches in
