# M3-T1 worker report: Expo scaffold, design tokens, tab shell, fixture ApiClient

**Branch:** `m3-t1-expo-scaffold` · **Worker:** Sonnet, isolated worktree · **Date:** 2026-09-22

## What was built

- `apps/mobile`: Expo managed workflow, TypeScript, Expo Router, inside the pnpm workspace.
- `apps/mobile/src/design/tokens.ts`: the single source of colour, type scale, radius and
  spacing. Colours are the D-021 palette, copied verbatim from prototype v4's `:root` block.
  `tokens.test.ts` pins every hex and recomputes WCAG contrast for the seven D-021 fixes.
- The tab shell: five slots (Home, Inventory, centre scan FAB, Menu, Shopping), order and
  labels matching prototype v4's `.nav`/`.fab` CSS. Active state text `--brand-deep`, icon
  stroke `--brand`. Every tab screen shows only its name and where the real screen lands.
  Menu reads "Held until D-020 is ratified." (no M3-Tn ticket exists for it yet, per D-023),
  every other tab and the centre Add screen read "Coming in M3-Tn."
- `ApiClient` port + `FixtureApiClient` (`apps/mobile/src/api/client.ts`): no network call
  anywhere, ever (proven by a test that stubs `globalThis.fetch` and asserts it's never
  called). Supplies the fixture identity token `fixture.dean.chen` and
  `getInventoryItems()` returning the Chen household's fixture rows.
- Root toolchain wiring: `tsconfig.json` references `apps/mobile`; eslint gets a domain-
  boundary rule for `apps/mobile` plus JSX support for `apps/**/*.tsx`; CI gets one new step
  (`pnpm --filter mobile export`); `.gitignore` gets Expo's own cache/generated-file entries;
  `apps/README.md` and `CONTRIBUTING.md` point at `apps/mobile/README.md`.

## Fonts

Fraunces (display) and Inter (body), vendored under `apps/mobile/assets/fonts/` as variable
fonts fetched from `github.com/google/fonts` (OFL-1.1), with each family's `OFL.txt`.
Exact URLs and commit references are in `apps/mobile/assets/fonts/SOURCES.md`.

**Limitation, flagged for the architect:** `google/fonts` does not carry static per-weight
files for either family in its current layout, only one variable `.ttf` each. Both are
registered under one font-family name; the type scale applies `fontWeight` as a normal RN
style, asking the platform's text renderer to pick a weight from the file's `wght` axis.
Expected to work on iOS (CoreText); Android's behavior depends on OS/engine version and
was **not verified on a device** (M3-T1 ships placeholder screens only, no design-sensitive
typography yet). Recommend verifying on a real Android device, or fetching static per-weight
files from another OFL source (`rsms/inter`, `undercasetype/Fraunces` GitHub releases),
before a design-sensitive screen (M3-T2+) depends on the Fraunces/Inter weight distinction.

## Deviations from the ticket text (all reasoned through, not guessed)

1. **React/React Native version.** The ticket says "use the current stable Expo SDK." The
   npm registry's newest `react-native` (0.87.1) is *not* what Expo SDK 57 bundles or
   supports: `@expo/metro-config@57.0.12` still imports `react-native/rn-get-polyfills.js`,
   a file that no longer exists in `react-native@0.87.1`'s package (the export smoke check
   failed with exactly this until fixed). Pinned instead to the versions in
   `expo@57.0.24`'s own `bundledNativeModules.json` (`react@19.2.3`, `react-native@0.86.3`),
   confirmed working end to end.
2. **No inventory item fixtures existed to "export."** The ticket's file scope says
   `packages/adapters/src/**` may only "export the existing inventory fixtures for the
   client, no new fixtures." A thorough search (`tests/fixtures/**`,
   `packages/adapters/src/**`, `packages/domain/src/inventory/test-support.ts`) found none.
   `testing-strategy.md §3` lists `tests/fixtures/inventories/` as a future subdirectory
   whose first fixtures had not landed. Rather than either (a) hand-inventing raw ledger
   numbers (risking an invariant-breaking fixture, rule 7 concern) or (b) blocking the whole
   ticket over a factual gap in its premise, built the fixture `InventoryItem` aggregates
   through the real domain ledger functions (`createInventoryItem` + `appendTransaction`,
   the same ones `apps/api` uses), then projected them down to a new, plain
   `InventoryItemSummary` DTO in `packages/contracts` (permitted by the ticket's own file-
   scope note: "client-facing DTOs only if M2-T1 has not defined them") before they ever
   reach `apps/mobile`. `@smart-kitchen/domain` moved from adapters' `devDependencies` to
   `dependencies` for this (it was already used by adapters' tests). **Proposed follow-up
   for the architect:** decide whether this becomes the real `tests/fixtures/inventories/`
   corpus (its own ticket, mirroring how M1-T5 built `tests/fixtures/products/`), or gets
   superseded once M2-T1's real endpoint and DTOs land.
3. **Household ids/tokens.** Per the architect's coordination note mid-task, the fixture
   identity tokens are exactly `fixture.dean.chen`, `fixture.maya.chen`,
   `fixture.owner.other`, documented in `tests/fixtures/identity/README.md` so M2-T1 (running
   in parallel) adopts the same strings. The fixture inventory's household ids
   (`hh-fixture-chen`, `hh-fixture-other`) are named to match.
4. **Type scale and spacing are ENGINEERING INFERENCE, not DOCUMENTED values** (CLAUDE.md
   rule 5). Neither design-direction.md §0 nor tokens.md publishes a formal type scale or
   spacing scale. Both are derived from the prototype's own bespoke per-element values
   (cited by CSS selector/line in `tokens.ts`'s comments). Flagged so the architect can
   promote or correct these when a real screen needs more granularity than this shell does.
5. **Relative imports inside `apps/mobile` have no `.js` extension**, unlike every other
   package in this repo (which use NodeNext's "`.js` refers to the `.ts` file" convention).
   Metro (the bundler Expo uses, not `tsc`) does not understand that convention and fails to
   resolve it at bundle time; `apps/mobile/tsconfig.json` uses `"moduleResolution": "Bundler"`
   accordingly and does not extend the root `tsconfig.base.json` (NodeNext-based) for the
   same reason, documented with a comment in the file itself.
6. **F2 (review):** `packages/adapters/package.json` and `packages/adapters/tsconfig.json`
   were edited outside the ticket's literal file scope (M3-T1 lists `packages/adapters/src/**`,
   not the package's own manifest/tsconfig). Both edits were necessary consequences of
   Deviation 2 above (moving `@smart-kitchen/domain` to a real dependency, and adding a
   project reference to `packages/contracts`), not separate scope creep, but the review
   correctly flagged that the ticket text did not name these two files. No code change from
   this worker; the architect ratifies the file-scope extension at acceptance.
7. **F3 (review):** the fixture inventory rows built via the real domain ledger functions
   (Deviation 2) are accepted by the review as a reasonable judgment call given no fixtures
   existed to export, not a ticket-compliant default to repeat without discussion on a future
   ticket that assumes a fixture corpus already exists.

## Review fixes

**F1 (major, addressed).** The independent review found that the apps/mobile domain-boundary
rule only used `no-restricted-imports`, which matches on the import *specifier* string, so a
relative import reaching straight past it, e.g. `import { createInventoryItem } from
"../../../../packages/domain/src/inventory/ledger"`, lints and typechecks clean. Fixed by
adding an `import-x/no-restricted-paths` zone to the same `apps/mobile` eslint.config.js
block, `target: ["./apps/mobile/src", "./apps/mobile/app"]`, `from: ["./packages/domain/src"]`,
mirroring the zone `packages/domain`'s own block already uses for its adapters/contracts
boundary. `apps/mobile/src/lint-rules/domain-boundary.test.ts` gained three new cases proving
it: a relative reach from `apps/mobile/src` is rejected, the same reach from `apps/mobile/app`
is rejected, and a relative import that stays inside `apps/mobile/src` (not touching domain)
is still allowed. The in-memory `Linter` approach turned out sufficient (no on-disk fixture
needed): a `filename` under the real `apps/mobile/src`/`app` trees is enough for the rule's
path resolution to fire correctly against the real `packages/domain/src` on disk, even though
that exact filename does not itself exist. Two smaller fixes were needed to get the new test
passing under apps/mobile's own strict, `"types": []` tsconfig: `process.cwd()` needed a
locally-declared minimal type (rather than pulling in `@types/node` project-wide, which would
have reintroduced Node globals into RN app code, the exact thing `"types": []` exists to
prevent), and the plugin registration reuses `eslint-plugin-import-x`'s own
`flatConfigs.recommended` object (the same one `eslint.config.js` itself already uses) instead
of hand-building a `plugins` record, since the plugin's own shipped types do not structurally
unify with `eslint`'s own `Linter.Plugin`/`Linter.Config` names (which, separately, are not
even resolvable by name from outside the `eslint` package: a real quirk in its `.d.ts`, worth
noting for the next person who hits it).

## Escalations

- **`@testing-library/react-native` was not adopted**, per the ticket's own instruction to
  escalate rather than add it silently. Used a pure test instead: `src/navigation/tabs.ts`
  is plain data (no React import), tested directly in `tabs.test.ts` for order, labels,
  icons, routes and placeholder copy. This is the "pure test of the route config" the
  ticket names as the fallback. No component-rendering test exists anywhere in this ticket.
- **The domain-boundary lint rule is tested via ESLint's `Linter` API against in-memory
  source strings**, not an on-disk fixture file, because a real fixture file that's
  *supposed* to fail lint would otherwise need excluding from the actual `pnpm lint` sweep
  (and from `tsc`, since it imports a package apps/mobile doesn't declare as a dependency),
  more fragile than asserting against a string. `apps/mobile/src/lint-rules/domain-
  boundary.test.ts` runs the exact rule config from `eslint.config.js` and checks it rejects
  `@smart-kitchen/domain` (bare and deep imports) while allowing `@smart-kitchen/contracts`
  and `@smart-kitchen/adapters`.
