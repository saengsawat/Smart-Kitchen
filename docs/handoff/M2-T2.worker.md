## 2. The write path, explained

### Locking

`applyInventoryWrite` takes `SELECT id FROM inventory_items … FOR UPDATE` **before**
it reads or plans anything. Every decision below is computed against a balance
(which lots a decrease drains, what delta reaches a target quantity, whether the
request overshoots), so two concurrent writes to one item must not plan against the
same "before" state. `appendTransactionToDb` takes the same lock again per row,
which costs nothing once held, and migration 0004's trigger is the backstop that
turns a *missed* lock into a retryable `40001` instead of a wrong balance. Zero rows
from the lock means the item is not visible to this session, which is a 404.

The whole thing runs inside one `withRetriedHouseholdTransaction` (M1-T9), reached
through `TenantSessionRunner.write`. Handlers still never see the pool.

### Allocation

- **Increase** (positive `ADJUSTMENT`): one row on the most recently acquired lot
  that still holds something, falling back to the most recently acquired lot of any
  balance, and opening a lot (server-generated uuid) when the item has none.
  "Most recently acquired" is `acquiredAt` descending with undated lots last, ties
  broken by the later lot in the item's own order.
- **Decrease** (a removal, or a negative `ADJUSTMENT`): `planLotConsumption(item,
  { policy: "FEFO", qtyMicros })`, then `consumptionInputsFromPlan` for the removal
  types. A negative `ADJUSTMENT` cannot go through `consumptionInputsFromPlan`,
  which refuses a signed type on purpose so that a correction is never split behind
  a caller's back. Its rows are built in `write-service.ts` from the same
  allocations, with the same key derivation and the same explicit field list (never
  a spread of a caller's object, the M1-T1 F1 rule).
- **Shortfall.** The planner never allocates more than a lot holds, so its rows
  cannot clamp; what it reports instead is `shortfallMicros`. That part is recorded
  as one more row against the last lot the plan touched, at full magnitude. See
  "Clamp" below.
- No request field names a lot, ever.

### Keys

Every row this endpoint writes carries a **derived** key
`<clientKey>/lot/<n>` (`PLAN_KEY_INFIX`), even when there is only one row. The
client's key is never used as a ledger key directly. Uniformity buys three things:
a write's rows are exactly the rows under its prefix, a replay is decided per row by
the ledger, and undo can recover a multi-row write from any one of its rows.

Client keys are constrained to `^[A-Za-z0-9._-]{1,128}$`. That excludes `::` (the
ledger's own namespace) and `/` (so no client key can land inside another key's
derived namespace, because a key ending in `/lot` would otherwise make "the rows of
this write" ambiguous). A key outside the charset is `INVALID_IDEMPOTENCY_KEY`.

### Replay and conflict

When rows already exist under the client's key, the write is **planned again against
the item as it stood immediately before those rows** (`rehydrateInventoryItem` over
the ledger prefix), and the resulting inputs are handed to the ledger exactly as a
first attempt would be. The ledger's own `isSamePayload` then answers `duplicate` or
`IDEMPOTENCY_KEY_CONFLICT`.

This is the part worth reading twice. A naive implementation computes
`targetAmount - currentQty`, which on a replay is a *different* delta (the balance
already moved), so an honest replay would be reported as a conflict. Recomputing
against the pre-write state makes replay work for target-quantity corrections,
FEFO-allocated removals and default-full-amount removals alike, with one code path
and with the comparison still being the ledger's, not ours.

`replayed: true` on the response means nothing was appended. The body is otherwise
identical to the original, so a client that ignores the flag is still correct.

### Clamp

Only the ledger writes a clamp. When the plan reports a shortfall, the API appends
the user's full statement (allocation rows, plus one row for the uncovered part
against the last lot touched), and `appendTransaction` sees that row drive the lot
below zero and appends its own `OVER_CONSUMPTION` `ADJUSTMENT`. The response carries
the clamp row alongside the statement rows. Recording only what was on hand would
have made the user's statement disagree with the ledger and erased the
correction-rate signal (ARCHITECTURE §8) that says our belief was wrong.

domain-model.md OQ-1 explicitly left "record the overshoot or refuse and prompt" to
the caller. This ticket's acceptance criteria settle it as **record the overshoot**
for the manual write path. M8 decides it again for meal-log decrements; nothing here
pre-empts that.

### Undo

1. The named row is found by `transactionId` within the item (404 if it is not
   there). A clamp row is refused with 400 `INVALID_FIELD`: it is the ledger's own
   correction, not a person's statement.
2. The group is the named row's whole write: `<clientKey>/lot/*`, or a bare key for
   a row written by the seed or the repository directly, plus any clamp attached to
   those rows.
3. Each lot is compensated by the **negation of the group's net effect on that lot,
   clamps included**. A statement that overshot moved the balance by less than it
   says, so reversing its face value would invent stock. A group whose net is zero
   (a statement entirely clamped away) is refused with `ZERO_DELTA`: there is
   nothing to reverse.
4. Rows are `ADJUSTMENT`s with `reason` `undo:<transactionId>`, the undo's own client
   key, and derived per-lot keys, so a retried tap is an idempotent replay.
   Undoing twice under two different keys appends twice, by design and documented.

A client cannot forge the reason: a `reason` starting with `undo:` on a normal write
is refused with `INVALID_FIELD`.

### Identity, errors, logs

Actor is `session.userId`, always; there is no request field for it and the body
schema declares no such property. 404 for an item outside the caller's household, on
POST, undo and GET, byte-identical to the 404 for an item that does not exist.
Refusals answer 400 (409 for a reused key) carrying the `LedgerErrorCode` and one
fixed sentence of ours, and **never** the domain's `message`, which quotes stored values
and is written for a log. Two log lines exist (`inventory.write.applied`,
`inventory.write.refused`); both carry the correlation id via pino's `reqId` and
neither carries a body, a reason, a name or a key.

## 5. Deviations from the ticket, declared

1. **`reason` on `InventoryTransactionDto` is optional (`reason?: string | null`),
   not required.** The ticket asks for `reason: string | null` and also says the
   mobile client is out of scope. `apps/mobile/src/inventory/ledger.ts` and
   `why.test.ts` construct these rows, so a required field would have meant editing
   the client. Every row the API produces carries the field explicitly; `undefined`
   means "this producer does not record reasons". **M3-T4 should tighten it to
   required** once the client is wired.
2. **`apps/api/src/app.test.ts` was edited** (outside file scope): three lines, to
   build the new `{read, write}` runner shape. `app.ts` itself needed no change,
   which is why the runner became an object rather than gaining a second exported
   factory. `apps/api/src/http/tenancy.db.test.ts` and `tenant-session.test.ts` are
   in scope and were updated the same way.
3. **`correlationLabel` is never populated** on a history row. The schema stores a
   correlation *kind and id*, there are no meal-log or receipt rows to point at yet,
   and putting a display string in an id column would be a lie about the column. The
   field stays absent until M5/M6 give it a real source. The seed therefore does not
   reproduce the prototype's "Chicken & spinach stir-fry" caption.
4. **The seed's history differs from the client fixture in three stated ways**
   (documented in `fixture-inventory.ts`): the chicken's two purchases are two real
   lots, so the drained Wednesday lot exists as a zero-balance lot; a multi-lot item
   gets one opening row per lot rather than one row for the total; and no correlation
   label. Every **quantity, unit, tier and source** matches the fixture exactly.
5. **`.env.example` unchanged.** The seed introduces no new variable; it reuses
   `DATABASE_URL` and `NODE_ENV`.
6. ~~**Unknown body properties are stripped, not rejected.**~~ **Closed by review
   F1.** The architect extended file scope to one line of `app.ts`;
   `removeAdditional: false` is now set and an undeclared property is a 400. See
   §10.
7. **A JSON number in a quantity field is coerced to a string by the validator**
   before the handler sees it (AJV's `coerceTypes`, left on by architect ruling at
   review). The parser only accepts plain decimal text within the ledger range, so a
   lossy double shows up as extra digits and is refused with `PRECISION_EXCEEDED`
   rather than recorded; there is a test for it. The residual is a number near 1e8
   with six decimals, where a double's last digit could round, and the contract says
   to send text. Re-checked after F1: `removeAdditional: false` does not affect
   coercion, and the coercion test still passes.

No ARCHITECTURE CONFLICT was found. Nothing in ADRs, DECISIONS.md, an INV-\*
invariant or CLAUDE.md had to bend.

## 6. Proposed migration (not applied, rule 16)

The ticket allowed a `correlation_kind` value for undo and told me to use `reason`
meanwhile, which is what I did (`undo:<transactionId>`). My recommendation is **not**
to add `undo` to `correlation_kind`: that enum names the *artefact* that produced a
row (a receipt line, a meal log, a shopping item), and an undo points at another
ledger row, which is a different kind of relationship. The honest shape would be a
new column:

```sql
ALTER TABLE inventory_transactions
  ADD COLUMN compensates_transaction_id uuid,
  ADD CONSTRAINT inventory_transactions_compensates_fkey
    FOREIGN KEY (household_id, compensates_transaction_id)
    REFERENCES inventory_transactions (household_id, id);
```

It would make "which rows undid this one" an index lookup instead of a string
prefix, and would let a screen render an undo badge without parsing a reason. It is
**not needed for M2 or M3**: nothing reads the relationship today, and `reason`
already renders. I recommend deciding it with M8 (reconciliation), when something
actually queries it. Architect's call; no migration is in this branch.

### data-model.md §6 (Idempotency): add after the existing M1-T11 paragraph

> **HTTP writes derive a key per row (M2-T2, 2026-09-22).** A client sends one
> `idempotencyKey` per request; the API never uses it as a ledger key directly.
> Every row a write appends is keyed `<clientKey>/lot/<n>`, the M1-T8 planner's
> namespace, so one request that splits across three lots writes three
> independently idempotent rows and the set of rows belonging to a request is
> exactly the set under its prefix. Client keys are restricted to
> `[A-Za-z0-9._-]{1,128}`, which keeps them out of both reserved namespaces (`::`

> injective. A replay is not remembered: the request is planned again against the
> item as it stood immediately before the stored rows (rehydrated from the ledger

> payload comparison is what distinguishes an idempotent replay (200, nothing
> appended) from a reused key (409, `IDEMPOTENCY_KEY_CONFLICT`). This is what makes
> replaying a *target quantity* correction work, since the target is relative to a
> balance the first attempt already moved. Undo rows carry their own client key and
> the same derivation; undoing twice under two keys appends twice.

> Writes (M2-T2) use the same pipeline with one addition: the handler is given a

## 9. What the reviewer should attack first

In order, highest value first:

1. **The replay recomputation** (`applyInventoryWrite`, `stateBefore`). Try to make
   it return `duplicate` for a request that is not the same request, or `409` for one
   that is. Specific angles: a write whose lots changed between attempts; a removal
   with no explicit amount replayed after the balance moved; an increase replayed
   after another lot was opened by a different path (I documented this as a possible
   false 409, never a double apply, so check that claim); a client key that is a prefix
   of another client key.
2. **The shortfall row and the clamp.** The planner guarantees clamp-free rows; I
   deliberately add a row that *does* clamp. Try to get two clamps, a clamp on the
   wrong lot, a negative lot balance, or a clamp whose cause row is not the one
   immediately before it (migration 0003's `reserved_marker` CHECK encodes that).
3. **Undo arithmetic.** `netByLot` decides what an undo compensates. Try: undo a
   group that contains both a statement and its clamp; undo after an unrelated write
   landed in between; undo a row written by the seed (bare key, no `/lot/` infix);
   undo an undo; two undos of the same row under different keys (should append
   twice); a group spanning a lot that has since been drained.
4. **Atomicity of a multi-row write.** Every refusal throws so the transaction rolls
   back. Find a path where a rejection returns normally and lets a partial write
   commit, or where the M1-T11 `COMMIT`-tag check would fire.
5. **Tenancy.** The three-token matrix, a forged body field, a forged header, an
   itemId from another household on undo, and `transactionId` from another item of
   the *same* household (the undo looks the row up within the item's own history, so
   this should 404, confirm it does).
6. **The seed.** Try to make it non-idempotent (interrupt it mid-run and re-run),
   make it write outside the fixture households, or make it run with a `NODE_ENV`
   spelling the allowlist misses.
7. **The boundary parser** (`quantity-text.ts`). It is the one piece of arithmetic
   outside the domain. The property tests claim exact inverse and exact agreement
   with `amountToMicros`; try to find a value where that is false.

## 10. Review fixes (adversarial Opus review, PASS WITH FIXES)

All seven required fixes are applied on the same branch. Rulings are recorded
where they changed a decision.

**F1 (major) Unknown body properties were stripped, not rejected.** Fastify's
bundled AJV runs `removeAdditional: true`, which turns `additionalProperties:
false` into a deletion rather than a refusal, so `{"type":"DISCARD","amuont":"0.25"}`
validated with the quantity gone and removed the **whole item** with a 200. Fixed
under the architect's scope extension: `ajv: { customOptions: { removeAdditional:
false } }` on the Fastify instance in `app.ts`, one line, reasoning in a comment.
The schema comment in `routes.ts` now states what actually happens. Three new
tests (a misspelled quantity field on the write body is a 400 with the item
untouched; an unknown property on the undo body is a 400 with nothing appended;
the body carries only the generic sentence), and the four "body names a household
/ an actor / a lot / a system flag" tests now assert refusal instead of no
effect, which is the stronger claim.

**F2 (major) A negative `targetAmount` minted a clamp.** `targetAmount: "-5"` on
an item holding 8 became a decrease of 13: every lot drained, the uncovered 5
recorded as an overshoot, and the ledger appending an `OVER_CONSUMPTION` row for
a malformed request. That row is not cosmetic, because the correction-rate KPI
counts clamps as evidence our record was wrong, so a client bug could inflate the
product's primary metric. Fixed in a new `targetDelta`: a negative target is
refused with `QUANTITY_OUT_OF_RANGE` before the subtraction, on the grounds that
a target states what is on hand and nothing is on hand a negative number of
times. `deltaAmount` stays signed. Two API tests (the refusal leaves the balance
and the item's clamp count unchanged; a negative `deltaAmount` still works) and
one pure test.

**F3 (minor) The undo test did not discriminate.** Undoing the eggs' first row
compared +8 against +8, so face value and net effect gave the same answer. The
test now names the **overshoot** row: face value -4, its clamp +4, group net -8,
so a face-value undo would append +4 and the net-effect undo appends +8. A second
test pins the documented behaviour that undoing the same group again under a new
key appends again.

**F4 (minor) An undo that would overdraw a lot is now refused.** Architect
ruling, implemented as a pre-flight in `undoInventoryTransaction`: a compensation
larger than the lot's current balance throws `UndoNotPossibleError`, answered
**409** with `UNDO_NOT_POSSIBLE` and "That change can't be undone. The stock it
added has already been used." The code is an `ApiErrorCode`, not a
`LedgerErrorCode`, because the ledger would have taken the row and clamped it;
the refusal is the API's, and it exists because that clamp would be a lie (the
record was not short, the undo was late) and would count against the
correction-rate metric. Four tests: the seed's drained chicken purchase refuses
with nothing appended and no clamp minted; the body carries no `ledgerCode`; and
a matched pair on one item shows the same undo succeeding while the stock is
there and refusing once it is gone. The architect adds the string to copy-deck §8
at acceptance.

**F5 (minor) The seed's role requirement was stated wrongly.** A plain member of
`sk_app` cannot run it: the identity half writes `households`, on which `sk_app`
holds only SELECT. CONTRIBUTING now says to connect as the role that ran the
migrations (the owner, or a superuser) and explains the two privilege levels the
seed uses; `fixture-inventory.ts`'s header and the proposed ARCHITECTURE §7 item
4 wording in §7 above carry the same correction.

**F6 (minor) Pure tests for the two pure decisions.** New
`db/inventory/write-service.test.ts`, 29 tests, no database. `increaseLot`: open
lot preferred, later `acquiredAt` wins, a dated lot beats an undated one in
either declaration order, a tie falls to lot order, fallback to the closed-lot
pool, no lots at all, and an unparseable date ignored rather than ranked on NaN.
`planWrite`: both or neither quantity form, `amount` on an `ADJUSTMENT`, target
or delta on a removal, negative and zero amounts, negative target, precision,
range, non-decimal text, an empty item, an item with no lot, plus the output
shape (derived keys in order, the FEFO split, the overshoot row, actor and
provenance). `planWrite` and `PlannedWrite` are now exported with a comment
saying they are exported for that suite. The unparseable-date case has to use a
hand-built item because the domain refuses such a lot at creation, which the test
says.

**F7 (minor) `SET ROLE` could land on a different connection.** The append-only
privilege test issued `SET ROLE`, the `UPDATE` and `RESET ROLE` through
`pool.query` separately, so the `UPDATE` could run as the owner, succeed and
