## 2. The metric, verbatim (ticket definition, not redefined)

One row per `(household_id, item_id)` over `inventory_transactions`:

- `statement_count` — rows where `system_flag_kind IS NULL` (i.e. NOT a system clamp row).
- `user_adjustment_count` — `type = 'ADJUSTMENT' AND actor_kind = 'user'`.
- `clamp_count` — `system_flag_kind = 'OVER_CONSUMPTION'`.
- `correction_event_count` — `user_adjustment_count + clamp_count`. Safe as a plain sum, never double-counted: a clamp row's `actor_kind` is always `'system'` (the reserved-marker CHECK in migration 0003 pins that), so it can never also satisfy `user_adjustment_count`'s predicate.
- `correction_rate` — `correction_event_count::numeric / statement_count`, `NULL` when `statement_count = 0`.
- `first_recorded_at` / `last_recorded_at` — `min`/`max(recorded_at)` over **all** of the item's rows (statements and clamps alike), per the ticket text.

I implemented this as written and did not second-guess it. One thing worth the architect's attention, not something I changed: ARCHITECTURE.md §8 currently describes the KPI as "corrections ÷ transactions per household-**week**" — a time-bucketed rate. This ticket's metric is an all-time, per-item aggregate with an optional `[since, until)` window on the read side, not a rolling weekly bucket. Both are the same numerator/denominator idea; reconciling the wording is the proposed §8 paragraph in §5 below.

## 3. View SQL, and why it's structured this way

```sql
CREATE VIEW inventory_correction_telemetry
WITH (security_invoker = true) AS
SELECT
  household_id,
  item_id,
  count(*) FILTER (WHERE system_flag_kind IS NULL)                     AS statement_count,
  count(*) FILTER (WHERE type = 'ADJUSTMENT' AND actor_kind = 'user')  AS user_adjustment_count,
  count(*) FILTER (WHERE system_flag_kind = 'OVER_CONSUMPTION')        AS clamp_count,
  (... + ...)                                                          AS correction_event_count,
  CASE WHEN statement_count = 0 THEN NULL ELSE (...)::numeric / statement_count END AS correction_rate,
  min(recorded_at) AS first_recorded_at,
  max(recorded_at) AS last_recorded_at
FROM inventory_transactions
GROUP BY household_id, item_id;
```

`FILTER (WHERE …)` rather than `CASE WHEN … THEN 1 END` inside `count()` — both are equivalent in Postgres, but `FILTER` reads as "count of X" rather than "sum of a synthetic indicator", and it's the same idiom the ticket's own prose uses ("rows that are…").

**`security_invoker = true`** — non-negotiable per ADR-003 standing rule 3, and load-bearing here specifically: without it, `sk_app` would read every household's correction data in one unfiltered `SELECT`, defeating the entire RLS scheme from migration 0006 for exactly the query most likely to be exposed on an internal dashboard. Verified two ways: (1) `telemetry/view.test.ts` asserts `pg_class.reloptions` contains `security_invoker=true`, the same mechanism `tenancy.test.ts` uses for the 0005 reconciliation views; (2) a positive-and-negative tenancy pair — the owner role sees both seeded households' rows, Alpha sees only Alpha's, Beta only Beta's, and a transaction with no `app.household_id` context sees zero rows (never "everyone's"), exercised directly against the view (not just through the read function).

**Grants** — `GRANT SELECT ON inventory_correction_telemetry TO sk_app;` only, matching 0006's style. Verified against `information_schema.role_table_grants`: `sk_app`'s only privilege on the view is `SELECT`.

**A finding worth recording:** I initially wrote grant tests expecting `sk_app`'s `INSERT`/`UPDATE`/`DELETE` attempts to fail with `42501` (insufficient privilege), by analogy with the tenancy suite's write tests. They instead fail with `55000` ("cannot insert/update/delete … view is not simple"). I spiked this manually against a throwaway database: the *owner* role (full superuser, no `SET ROLE`, no RLS involved at all) gets the identical `55000` on the identical statement. Postgres refuses writes against any view built on aggregates + `GROUP BY` — it isn't auto-updatable — and it makes that determination before privilege checking ever runs, for every role including the owner. So the three write-attempt tests now assert `55000` and document why in a comment; the actual proof that `sk_app` holds no write grant is the fourth test in that block, a direct `information_schema.role_table_grants` query. The three write-attempt tests still have value — they prove the exact statement a misbehaving caller would try is refused, end to end — but they are not, on their own, a grants test for this particular view shape. I'd flag this as a useful thing for the reviewer to double-check independently, since I could not find a place the ticket anticipated this and had to make a judgment call.

**Down migration** is a plain `DROP VIEW` — the `GRANT` was issued in this same migration's up, and dropping the view removes it with the object; no separate `REVOKE` needed (unlike 0006, which revokes privileges on tables that continue to exist).

## 4. Read function

`readCorrectionTelemetry(client, householdId, { since?, until? })` in `apps/api/src/db/telemetry/correction-rate.ts` returns `{ household, items }`.

- **Two queries, not a `GROUPING SETS` single query.** I first tried one query with `GROUP BY GROUPING SETS ((household_id, item_id), (household_id))`, but that produces **zero rows** when the period/household has no matching transactions at all — there's nothing to group. The ticket's return type has `household` as an always-present `CorrectionTelemetryTotals`, not optional, so a household with no activity in the requested period still needs `statementCount: 0n`, `correctionRate: null`, etc., not an absent field. An aggregate query **without** `GROUP BY` always returns exactly one row (its counts are simply zero), so the household total is its own ungrouped query; the per-item breakdown is a second, `GROUP BY item_id` query that correctly returns an empty array in the same case. Both carry the identical `FILTER`/`CASE` column list (`AGGREGATE_COLUMNS`, a shared template string) so the two can't drift apart.
- **Period bounds are SQL, not JS.** `($2::timestamptz IS NULL OR recorded_at >= $2::timestamptz) AND ($3::timestamptz IS NULL OR recorded_at < $3::timestamptz)` — `since` inclusive, `until` exclusive, exactly as the ticket specifies, applied over the base table (the view itself carries no period argument, by design — see the migration header).
- **No float arithmetic on counts anywhere.** Counts and `correction_event_count` are Postgres `bigint`/derived-bigint, returned as decimal text by `pg` and converted with `BigInt(...)`, never `Number(...)`. `correction_rate` is returned as the exact `numeric` text Postgres computed (or `null`) and is not parsed to a JS number at all.
- **RLS applies as normal.** The function takes an already-open `client` and does no session setup itself — same convention as `loadInventoryItem` in `apps/api/src/db/inventory/repository.ts` — so it must be called from inside `withHouseholdTransaction`. I also kept the explicit `WHERE household_id = $1` filter (redundant with RLS when the caller passed the same id as the session context, defense-in-depth when it doesn't): with no `app.household_id` set, RLS alone already reduces every row to invisible, so the household aggregate still returns its one zero-valued row and `items` comes back empty — verified as a "no context" case in the tenancy tests, both via the view directly and via this function.

## 5. Proposed ARCHITECTURE §8 paragraph (architect to apply at acceptance)

Replacing/extending the existing "Inventory correction rate" bullet in ARCHITECTURE.md §8:

> **Inventory correction rate** (M1-T7, `apps/api/db/migrations/0007_correction_telemetry.sql`) — per household-item: `statement_count` counts every ledger row that is not a system-generated over-consumption clamp; `user_adjustment_count` counts user-authored `ADJUSTMENT` rows; `clamp_count` counts `OVER_CONSUMPTION`-flagged rows (ADR-008's clamp policy); `correction_event_count = user_adjustment_count + clamp_count`; `correction_rate = correction_event_count / statement_count` (undefined when there are no statements yet). Read as the all-time aggregate via the `inventory_correction_telemetry` view (`security_invoker`, `SELECT`-only for `sk_app`), or bounded to a `[since, until)` window over `recorded_at` via `readCorrectionTelemetry` (`apps/api/src/db/telemetry/correction-rate.ts`), which computes the same definitions in SQL over the base ledger table. *Primary metric*: it measures whether the system's beliefs track reality (brief §18C) — a falling rate with steady usage means the product is working. Weekly/rolling-window presentation (dashboards, alerting) is M9's job; this ticket only establishes the query the KPI is built from.

## 6. Tests

All gated on `dbTestsEnabled` with the harness's SKIP-NOTICE pattern (loud stderr locally, hard CI failure if a suite ever skips there — `ci-guard.test.ts` covers the guard itself and needed no changes).

`apps/api/src/db/telemetry/correction-rate.test.ts` (read function):
- **Composition** — the ticket's exact worked example, appended through the real repository path (`appendTransactionToDb`, never raw SQL): 1 `INITIAL_STOCK`, 2 `CONSUME`, 1 user `ADJUSTMENT`, 1 over-consuming `CONSUME` producing a clamp. Asserts `statement_count=5, user_adjustment_count=1, clamp_count=1, correction_event_count=2, correction_rate=0.4` both by querying the view directly and via `readCorrectionTelemetry` with no period bound, and checks `first/last_recorded_at`.
- **System `ADJUSTMENT` that isn't a clamp** — a `system`-actor `ADJUSTMENT` with an ordinary (non-`::over-consumption-clamp`) idempotency key counts as a statement only: not a user adjustment (wrong actor kind), not a clamp (`system_flag_kind` stays `NULL` on an ordinary `ADJUSTMENT`).
- **Tenancy via the function** — household A sees only A's item, B only B's, and a transaction with no household context sees zero items and a zero-valued (not absent) household total.
- **`since`/`until` boundaries** — three rows at `t0`, `t1`, `t2`; `[t1, t2)` counts only `t1`; `[t0, t0)` counts nothing (upper bound excludes the exact instant it names even when a row sits there); open-ended bounds on either side; unbounded counts everything.

`apps/api/src/db/telemetry/view.test.ts` (the view as a database object):
- `security_invoker=true` via `pg_class.reloptions`.
- Tenancy directly against the view: owner sees both seeded households, Alpha only Alpha's row, Beta only Beta's, no context sees none.
- Grants: `sk_app`'s only privilege is `SELECT` (`information_schema.role_table_grants`); separately, `INSERT`/`UPDATE`/`DELETE` attempts are refused (with the `55000`/non-updatable-view caveat from §3 above, documented in the test comments).
- Migration reversibility scoped to this one view: `migrateDown(url, 1)` removes the view while leaving `inventory_transactions` untouched, `migrateUp` restores it.
