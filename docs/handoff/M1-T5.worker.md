## 1. What was built

### 1.1 Ports (`packages/adapters/src/product-lookup/`)

- `ports.ts` — `ProductLookupPort.resolve(code) → ResolveResult` (`hit | not-found | error`) and
  `NutritionSourcePort.byProductCode`/`byIngredientSearch(...) → NutritionLookupResult`
  (`hit | not-found | error`), exactly the shapes named in ai-architecture.md §3.
- `types.ts` — record types shaped to align with domain-model.md's `ProductCatalogItem` /
  `NutritionProfile` / `AllergenAssertion`, but **owned by this package**, not imported from
  `packages/domain` (which has no product-catalog module yet) or `packages/contracts` (out of
  scope per the ticket). No vendor SDK type crosses the port surface — every field is redefined
  in this module's own vocabulary.
- `errors.ts` — self-contained `AdapterError`/`AdapterErrorCode`/`Outcome<T>`/`ok`/`err`, mirroring
  the `Outcome<T>` total-function idiom already established in
  `packages/domain/src/{inventory,units}` (never throw for an expected rejection).
- `schema.ts` — hand-rolled validator for the fixture JSON shape (no `zod`/`ajv` — CLAUDE.md rule
  11 requires justifying new dependencies, and this schema is small/stable enough not to need
  one). Includes `gs1CheckDigit`/`validateCodeFormat` (real GS1 mod-10 check-digit algorithm,
  shared by fixture generation and runtime validation).
- `fixture-paths.ts` / `fixture-loader.ts` — resolves `tests/fixtures/products` +
  `tests/fixtures/barcodes/manifest.json` from this module's own file location (not
  `process.cwd()`), so path resolution is robust in CI regardless of invocation directory. This
  is the **only** I/O in the module, and it only ever touches these two fixture paths.
- `fixture-product-lookup-port.ts` / `fixture-nutrition-source-port.ts` — the fixture-backed
  implementations used in tests/dev (ai-architecture.md §3: "every port has a fixture
  implementation").

### 1.2 Design decisions worth flagging

- **Per-field provenance, not one blanket provenance.** Every field group
  (`name`/`brand`/`category`/`packageSize`/`servingSize`/`ingredientsText`/`imageRef`) is wrapped
  as `Provenanced<T> = { value: T; provenance: FieldProvenance }`; `nutrition` and `allergens`
  are arrays whose entries each carry their own provenance. `FieldProvenance` is
  `{tier, source, observedAt, confidence?}`, exactly the shape named in BACKLOG.md M1-T5 —
  deliberately narrower than the domain ledger's `Provenance` (no `modelRef`/`confirmedBy`, which
  describe *confirmation into ledger state*, out of a product-catalog record's scope).
- **Multi-source conflicts are modeled as multiple `NutritionProfile` entries on one product**,
  never merged/picked by the adapter. "Our-catalog merge logic" is explicitly out of scope
  (BACKLOG.md: "M4"), so when upstream sources disagree, both profiles are returned with their
  own `source`/`provenance` and the caller (a future M4 merge layer) decides — the fixture corpus
  includes 6 such products to exercise this.
- **`ResolveResult` stays 3-way (`hit`/`not-found`/`error`)** per the ticket's literal port
  signature; "conflict" is data-modeled (multiple nutrition profiles on a `hit`), not a 4th
  status — avoids inventing a merge-decision the port isn't supposed to make.
- **No dependency on `packages/domain`.** M1-T4 (allergens, which would own a real allergen
  taxonomy) hasn't landed; this ticket's `AllergenTag.allergenCode` is a free string (FDA
  major-allergen codes used in fixtures for realism) rather than importing a taxonomy that
  doesn't exist yet. Keeps `packages/adapters` self-contained.
- **Real GS1 check-digit validation**, not just length checks — `validateCodeFormat`/
  `gs1CheckDigit` implement the actual mod-10 algorithm (shared by EAN-8/UPC-A/EAN-13/GTIN-13),
  proven against two independently-known test vectors (`012345678905`, `4006381333931`) in
  `schema.test.ts`, and used both to validate fixtures and to reject malformed runtime codes
  (`INVALID_CODE`, never a false "not-found").

## 2. Fixture corpus (`tests/fixtures/products/**`, `tests/fixtures/barcodes/manifest.json`)

101 synthetic `ProductCatalogItem` JSONs (target "~100" per testing-strategy.md §3) + a 109-entry
barcode manifest (105 `hit` + 4 deliberate `not-found` misses). All codes are **synthetic**
(invented company-prefix + running serial, GS1-check-digit-valid) — no real product data copied
in.

| Case (testing-strategy.md §3) | Count | Notes |
|---|---|---|
| Complete branded items | 74 | `kind: "BRANDED"`, **excluding** the multi-code/multi-source-conflict/missing-nutrition rows below (a residual bucket, not a separate literal-all-fields count — see note) |
| Missing-nutrition items | 8 | `nutrition: []` — never a guessed value (SR-3) |
| Allergen-bearing items | 51 | mix of `CONTAINS`/`MAY_CONTAIN`, FDA's 9 major allergens |
| Multi-code products | 4 | same product, 2 codes (UPC-A + its GTIN-13 form — a repackage/redesign scenario) |
| Generic/PLU produce | 15 | `kind: "GENERIC"`, `codeType: "PLU"`, no barcode |
| Multi-source-conflict | 6 | 2 disagreeing `NutritionProfile` entries (`open-food-facts` vs `usda-fdc` sourced) per product |

The rows above are **not mutually exclusive counting buckets except by construction** — most
notably, **6 of the 8 missing-nutrition items are also generic/PLU produce** (real produce
often carries no nutrition data at all), so "missing-nutrition" + "generic/PLU" do not sum to
distinct products. For reference, other readings of "complete branded" from the raw data: 86
products are `BRANDED` total; 84 of those have `nutrition.length > 0`; only 7 have every one of
the 8 field groups (`brand`/`category`/`packageSize`/`servingSize`/`nutrition`/
`ingredientsText`/`allergens`/`imageRef`) simultaneously present (most complete-branded fixtures
deliberately omit 1-2 optional groups for realism, matching real label variation) — the 74
figure above is `BRANDED` minus whatever is already counted in the multi-code (4)/conflict
(6)/branded-missing-nutrition (2, since 6 of the 8 missing-nutrition items are generic) rows, so
each product is counted in exactly one row of this table.

Category spread: dairy 13, produce 15, meat 11, pantry 24, frozen 10, snacks 10, beverages 5,
baking 5, condiments 8 (=101; some categories overlap with the case rows above since e.g. a
multi-code product is *also* counted in its category).

`tests/fixtures/barcodes/manifest.json`: `{code, codeType, expect: "hit"|"not-found", productId?,
caseLabel?, notes?}` rows — the caseLabel field lets contract tests find "the multi-code case",
"the conflict case", etc. without hardcoding specific codes, so the corpus can grow without
breaking tests.

## 4. R-1 research spike — method + headline numbers

Full writeup: [`docs/research/food-data-coverage.md`](../research/food-data-coverage.md). Raw
data: [`docs/research/food-data-coverage.raw.json`](../research/food-data-coverage.raw.json).
Script: [`scripts/food-data-coverage-research.mjs`](../../scripts/food-data-coverage-research.mjs)
(documented in `scripts/README.md`; not part of `pnpm test`/CI — live network calls, run
manually).

**Method:** a 110-item basket (target "~100") assembled from general knowledge of common US
grocery categories per brief §18A — **not** sourced from OFF/FDC (which would bias the sample).
Two arms: 23 items use real, standardized IFPS PLU codes sent to OFF's barcode-lookup endpoint
(produce; PLU isn't a GS1 barcode, so this tests what actually happens when one is queried as
one); 87 branded items use brand+name text search, because — disclosed explicitly in the
doc — this worker (an LLM with no shopping trip, scanner, or catalog access while building the
basket) cannot attest a real barcode from memory with confidence, and fabricating one would
produce a meaningless, universal miss.

**Headline numbers (OFF, fully measured):**

- Raw hit-rate: 102/110 overall (92.7%); name-search arm 87/87 (100%); PLU-as-barcode arm 15/23
  (65.2%).
- **But raw hit-rate is not the finding.** A manual quality review of every match found: the
  PLU-as-barcode arm's "hits" are genuinely correct only 6/15 (40%) of the time — the rest are
  unrelated products or empty junk records (e.g. PLU `4070` "Celery" → matched a French banana
  tart). The name-search arm's matches are correct/close 74/87 (~85%) of the time, with 13/87
  (~15%) clear mismatches (e.g. "Kirkland Signature whole milk" → matched "Artichoke Hearts";
  "Baby carrots"/"Baby spinach" both matched unrelated infant-formula products because of the
  word "baby").
- Field completeness (OFF hits): allergens present on only 41% of branded hits, 0% of PLU hits —
  FDC has **no allergen field at all** (structural, not a gap in this run).
- **FDC: attempted 27 items (documented subset, per dispatch), completed 0.** Every attempt
  returned HTTP 429 (`OVER_RATE_LIMIT`) from the public `DEMO_KEY`; 6 follow-up retries at
  90-second intervals (~9 more minutes) all still 429. One earlier exploratory call (made before
  the timed run, to confirm the endpoint shape) did succeed, confirming the endpoint/query are
  correct — the block is rate-limiting, not a broken integration. **No FDC numbers are reported
  or estimated** — this is a disclosed gap in the evidence, not filled in with a guess.

**Recommendation for ADR-006** (full reasoning in the doc §7): cascade shape A→B→manual still
looks directionally right, sharpened by this evidence — (1) PLU/produce must be pulled **out**
of any live barcode cascade entirely and served from a small curated PLU table instead (a wrong-
but-"found" record is worse than a clean miss); (2) FDC's slot in the cascade is unvalidated,
not disproven — needs its own follow-up measurement before ADR-006 finalizes on it; (3) OFF's
branded-name identification is strong on well-known brands specifically (selection-bias caveat
stated explicitly) but even at its best has a real ~15% wrong-match rate, reinforcing why every
cascade output needs the confirmation-gate the architecture already specifies; (4) allergen data
has a structural FDC gap that the cascade design must account for explicitly; (5) ODbL review
(R-4) remains a precondition for any merged catalog, independent of hit-rate.

## 7. Proposed doc updates (for architect to apply at acceptance)

### ADR-006 — proposed OPEN → PROPOSED wording

> **Status:** PROPOSED (evidence from M1-T5's R-1 spike; FDC arm still incomplete — see below).
>
> **R-1 findings (measured 2026-09-09, `docs/research/food-data-coverage.md`):** Open Food
> Facts gives strong branded-product identification via name/text search (~85% genuine match
> rate after manual review, on a basket biased toward well-known national brands — not a
> general-population estimate; real unbiased hit-rate needs live scan telemetry, M4). USDA
> FoodData Central's role is **unvalidated** — the public `DEMO_KEY` rate-limited every attempt
> in the documented 27-item subset (0 completed); needs a follow-up measurement (slower pacing
> or a real key) before this ADR can rely on a real FDC number.
>
> **Settled sub-decision (promote from "open question" to decided):** PLU/produce items must
> **never** be sent through a live barcode-lookup cascade to OFF or FDC. Empirically, treating a
> PLU digit string as a barcode against OFF returns a wrong/unrelated product roughly 60% of the
> time it "hits" at all (worse than a clean miss, since it looks like success) — produce needs
> its own small, manually curated PLU → `CanonicalIngredient` table, decoupled from the live
> cascade.
>
> **New requirement for the M4 cascade implementation:** allergen tags cannot be treated as
> "fall back to nutrition source B" the way nutrition values can — FDC has no allergen field at
> all. A product resolved via an FDC-only path must render allergen status as unknown + warning
> (SR-2), never omit the warning because "no allergen data came back."
>
> **Still open:** (a) FDC hit-rate/field-completeness — needs the follow-up measurement above;
> (b) ODbL share-alike implications for a merged catalog — flag to counsel (R-4), unresolved
> regardless of the hit-rate findings; (c) whether a commercial source (option C) is needed —
> not yet justified by this evidence, revisit after M4's live telemetry.

   consequence).** Required: this ticket is the first to add real Node I/O

   here — this only extends its use to a second package, adds no new package to the lockfile,
   and is dev-only/type-only (zero runtime footprint). Explicitly permitted by the ticket's file
   scope ("its package.json devDependencies ONLY if truly needed + lockfile as consequence").

**Everything else is within the assigned file scope** (`packages/adapters/src/**`,
`tests/fixtures/products|barcodes/**`, `scripts/**` + its README line,
`docs/research/food-data-coverage.md` + raw data file, this handoff doc). No file under
`packages/domain/**`, `packages/contracts/**`, `apps/**`, or any other `docs/**`/root config was
