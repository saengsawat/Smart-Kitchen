# M2-T6 worker report: move an item between locations (D-024 row 1)

**Worker:** Sonnet, isolated worktree, branch `m2-t6-move-item`.
**Base:** main `7b73c0d` (includes M2-T5's migration 0010 and M3-T7).
**Outcome:** parts (a), (b), (c) and (d) built and tested. Migration 0011 ran only on throwaway databases (rule 16). The phone check is not done (no device in this session).

## Exactly what a move writes

Written before coding, and kept to.

- **One row in `inventory_item_moves`:**
  - `household_id` and `item_id`: the request's (the household from the session, the item from the path).
  - `from_location`: the item's location as read under the item lock (NULL when the item has none).
  - `to_location`: the request's.
  - `moved_by`: the session's user.
  - `client_key`: the request's `idempotencyKey`.
  - `id` and `occurred_at`: from their defaults (`gen_random_uuid()`, `clock_timestamp()`).
- **One column of one row in `inventory_items`:** `storage_location`, set to `to_location` in the same database transaction. The app role already held `UPDATE (storage_location)` since 0006.
- **Nothing else.**
  - No `inventory_transactions` row is inserted or changed.
  - No `inventory_lots` row, no quantity column, no snapshot column.
  - The item lock (`SELECT ... FOR UPDATE`, the same lock every ledger write takes first) writes nothing.
- **Pinned by tests:**
  - `moves.test.ts` compares every row of `inventory_transactions` and `inventory_lots`, and every `inventory_items` column except `storage_location`, through `to_jsonb` before and after a move (row counts and full rows). Replays and every refusal leave all of it identical too.
  - `inventory-move.db.test.ts` does the same across its whole HTTP run. The only new ledger rows there are the suite's own deliberate ADJUSTMENT on the Eggs, and the test says so.
  - On the running API, after the curls: 15 ledger rows (the seed's 15), 2 move rows.

## What changed and why

### Migration `apps/api/db/migrations/0011_inventory_item_moves.sql`

- **Table `inventory_item_moves`:**
  - composite FK `(household_id, item_id)` to `inventory_items (household_id, id)` (the 0003 trick), so a move can never name another household's item;
  - `moved_by` as a composite FK to `household_memberships (household_id, user_id)`, same as 0010's `confirmed_by`, so only a member of the item's own household can be recorded;
  - `from_location` nullable (an item may be stored with no location, 0003 allows NULL), `to_location NOT NULL`, both with the four-value CHECK;
  - `CHECK (from_location IS DISTINCT FROM to_location)`, so a move that goes nowhere is never recorded;
  - `client_key` with the M2-T2 key-shape CHECK, `UNIQUE (household_id, item_id, client_key)` (household-scoped like every key here);
  - `occurred_at DEFAULT clock_timestamp()` (the M2-T3a lesson);
  - index `(household_id, item_id, occurred_at)` for the detail read.
- **Append-only, both layers:** `sk_app` has SELECT and INSERT only; `inventory_item_moves_no_mutation` and `_no_truncate` triggers raise `0A000` for every role, the owner included.
- **RLS** with the 0006 shape. Unlike 0010 it adds no unique constraint on `inventory_transactions`, because it does not point at a ledger row.
- **Down:** revokes, drops the policy and the table, drops the trigger function. Moves recorded are lost with the table; the items keep the location they hold now (tested, with the ledger untouched in both directions).

### API

- **`apps/api/src/db/inventory/moves.ts` (new).** The statements: lock the item and read its location, find a move by `(item, key)`, insert the move, set the location, read an item's moves. Every one is household-filtered in SQL as well as by the policy. It also holds the location list the route's body schema uses (`STORAGE_LOCATIONS_DB`), pinned to both migrations' CHECKs by `moves.pure.test.ts`.
- **`apps/api/src/inventory/move-service.ts` (new).** In order:
  1. validates the key (`CLIENT_KEY`);
  2. locks the item and reads its location (404 if not visible);
  3. looks up the key on this item: same destination and same user is a replay (200, nothing written); a different destination or user is `IDEMPOTENCY_KEY_CONFLICT`;
  4. refuses a destination equal to the current location (`SAME_LOCATION`);
  5. inserts the move row, updates the column;
  6. reads the item back.

  The replay check runs before the same-location check on purpose: after the first move the item is at the destination, and the retry must answer 200, not 409. No arithmetic, no model (rule 7).
- **`apps/api/src/inventory/move-route.ts` (new).** Body schema `{ toLocation: enum, idempotencyKey }` with `additionalProperties: false`, household route for any member. It logs the route and a replay flag, never a name, key or location.
- **`apps/api/src/http/routes.ts`.** The route declaration only: one `registerMoveRoute(...)` call.
- **`apps/api/src/db/inventory/history-merge.ts` (new, pure).** The merge rule, tested without a database:
  - ledger rows keep their `sequence` order, always (never re-sorted against each other);
  - a move goes before the first ledger row recorded after it;
  - a tie goes to the ledger row first;
  - moves among themselves go by time, then id;
  - comparison is at stored microsecond precision, as fixed-width ISO text from `to_char`, not at the millisecond a JS `Date` would round to.
- **`detail.ts`.** `readInventoryItemDetail` merges the moves into `detail.history`. The ledger-only `history` it also returns (which the write path uses to find a write's own rows) is unchanged. `LedgerHistoryEntry` gained an internal `recordedAtUs` that never goes on the wire.
- **`create-service.ts`: a regression my feature would have caused, fixed.** A retried item create compares the stored item to the request, including `storage_location`. After a move that comparison would fail, and a retry of the original create (same key) would be refused as a key conflict instead of replaying. `findByKey` now reads the creation-time location: the first move's source when the item has moves, else the current column. Tested: create, move twice, replay the create (replayed, no new item), and a create with the same key but another location still conflicts.

### Contracts (`packages/contracts`)

- `InventoryMoveEntryDto { type: "MOVED", moveId, fromLocation | null, toLocation, recordedAt, actor }`.
- `InventoryHistoryEntryDto = InventoryTransactionDto | InventoryMoveEntryDto`; `InventoryItemDetailDto.history` is now that union. `MOVED` is the discriminant on `type` and is deliberately not a `TRANSACTION_TYPES_DTO` value.
- `MoveItemRequestDto { toLocation, idempotencyKey }`, `MoveItemResponseDto { item }`, `INVENTORY_ITEM_MOVE_ROUTE`, `inventoryItemMovePath`.
- `SAME_LOCATION` added to `API_ERROR_CODES` (`errors.ts`, same precedent as `NOT_A_PROPOSAL` and `ROW_HAS_NO_ITEM`). `index.ts` exports the new names.
- The response carries no replay flag, so a retry answers a byte-identical body.

### Client (`apps/mobile`)

- **`ApiClient.moveItem(itemId, toLocation): Promise<void>`.**
- **`HttpApiClient.moveItem`:** one key per call, reused on the one network retry; a coded refusal becomes a `LedgerRefusedError` carrying only the code; a malformed 200 is an error. On success the item's entry in the summary cache is replaced with the server's post-move summary, so the stale fallback can never regroup it under the old location (same reasoning as M2-T5's confirm).
- **`FixtureApiClient.moveItem`:** same behaviour in memory. `MutableItemFixture` gained a mutable `storageLocation` and an append-only `moves` list; `appendMove` in `ledger.ts` never touches `history`, `lots` or a quantity. `toDetailDto` merges with the same rule as the API (`history.ts`). Moving to the current location rejects with `SAME_LOCATION`.
- **`src/inventory/history.ts` (new):** `isMoveEntry`, `ledgerRowsOf` (everything that does quantity work or narrates a quantity goes through it), `otherLocations`, row wording, and the fixture merge.
- **S5 (`app/inventory/[itemId].tsx`):**
  - a "Move to" section under "Use or remove" with a chip for each of the other three locations (the current one is never offered);
  - tapping calls `moveItem`, re-reads the detail, updates the header ("on hand · Pantry"), toasts, and the history shows the new row first (history is newest first);
  - chips are disabled while a move is in flight (one request per tap);
  - a failed move toasts the §8 generic write fallback and changes nothing on screen;
  - if the move lands but the re-read fails, it toasts the §8 generic read fallback rather than claiming a failed save;
  - the "Why {qty}?" line is built from `ledgerRowsOf(history)`, so a move never enters the quantity story.
- **S4:** no code change. The root navigator is `<Slot />`, which swaps screens rather than stacking them, so going back from S5 remounts S4 and it reads the list again (the same path a removal already relies on). Not verified on a device.

## Semantics as built

| Case | Answer | Writes |
|---|---|---|
| Member moves an item to another location | 200, `{ item }` with the new location and a `MOVED` entry | one move row, one column |
| Same key, same destination, same user | 200, byte-identical body | nothing |
| Same key, different destination (or different user) | 409 `CONFLICT`, `ledgerCode: IDEMPOTENCY_KEY_CONFLICT` | nothing |
| New key, destination equals current location | 409 `SAME_LOCATION` | nothing |
| Item of another household, no such item, or a non-uuid id | 404 `NOT_FOUND`, identical bodies | nothing |
| Key outside `^[A-Za-z0-9._-]{1,128}$` | 400 `BAD_REQUEST`, `ledgerCode: INVALID_IDEMPOTENCY_KEY` | nothing |
| Destination outside the enum, missing field, `clientKey`, `householdId`, `movedBy` or `fromLocation` in the body | 400 | nothing |
| No or unknown token | 401 | nothing |

## Deviations (each small, flagged for the reviewer)

1. **The body field is `idempotencyKey`, not `clientKey`** (the ticket text says clientKey loosely). The column stays `client_key`. A shape-refusal test pins that `{ "clientKey": ... }` is a 400.
2. **`create-service.ts` changed** (its `findByKey` query), which the ticket does not list but `apps/api/src/db/inventory/**` covers. Reason above: without it a create retried after a move would be refused. Reviewer: please read that query and the new test.
3. **`packages/contracts/src/errors.ts` and `index.ts` changed.** `SAME_LOCATION` must be an `ApiErrorCode`; the exports must exist. M2-T5 and M7-T1 set the precedent.
4. **`InventoryItemDetailDto.history` is a union now, so existing tests that read ledger fields off it were adapted, not weakened.** Each reads the same value through `ledgerRowsOf` (mobile) or `ledgerRows` (API test helper). Files: `client.test.ts`, `item-detail-typed-quantity.test.ts`, `ledger.test.ts`, `shopping-screen.test.ts`, `confirmations.test.ts`, `shopping-http.db.test.ts` (its own local `ledgerRows` function forced an import alias), `inventory-confirm.db.test.ts`, `inventory-writes.db.test.ts`. No assertion changed meaning; none deleted.
5. **`MutableItemFixture.storageLocation` is no longer `readonly`**, and the type gained a required `moves` field, so the three object literals that build one (`fixture-household.ts` twice, `ledger.test.ts`) gained `moves: []`.
6. **No Undo on the move toast.** Undo in this app is a ledger concept (a compensating ADJUSTMENT). Moving back is one more chip tap. Flagged in case the architect wants one.
7. **A move row carries no tier chip.** A chip says how a fallible fact about a quantity is known (copy-deck §4). A move is a member's own recorded action, and the DTO has no provenance for it. See the open question below.

## Open question (rule 3, not resolved by assumption)

- **Does a move row wear a provenance chip?** copy-deck §4 says "every fallible fact wears one of these three; there is no 'no chip' state". I read that as applying to claims about a quantity or an expiry, and a move as a member's own recorded action (which §4 would call Known Fact: "your own entry"), so I rendered no chip and added no tier to the DTO. If the architect rules a move is a fact that needs the chip, the DTO needs a tier (always `KNOWN_FACT`, since a move can only be a person's own entry) and `MovedRow` one more element. Classification: OPEN QUESTION for the architect.

Verdict was PASS WITH FIXES (F1, F2 required; N3, N4 small). All four done.

- **F1, clock_timestamp pinned.** New test in the `moves.test.ts` concurrency block, using two connections as the reviewer described: E begins and runs a SELECT; F begins, moves the item and holds the lock; E moves the same item and blocks; F commits; E commits. Ordering by `occurred_at` must be [F's move, E's move], with the from and to chain FRIDGE to PANTRY to FREEZER. The items image stays content-only, because a move legitimately rewrites the item tuple. A no-op UPDATE on a lot would now fail both suites.
- **N3.** The 0011 header comment now says "the trigger function" (there is one).
- **N4, ref guard.** `handleMove` guards on a `useRef` (set before the request, cleared in `finally`); the `moving` state stays for the disabled styling. The S5 test now fires all three taps inside one `act()`, so no re-render happens between them. Checked by mutation: guarding on the state makes the test fail; the ref passes.
