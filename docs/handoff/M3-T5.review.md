# M3-T5 review: Shopping list (S11)

Reviewer: Opus (independent session, read-only). Base: origin/main c6d8ff6. Branch: m3-t5-shopping @ 230ffdc.

## Round 1 verdict: FAIL

Most of the ticket is solid: the four CI gates and the export smoke are green from a clean state, scope is clean, there are no new dependencies, and the client never computes a gap. The drift test really does run `neededQuantity` over every fixture row. Copy is clean and the HTTP rejection path works. But the three failure modes the ticket told review to attack all break with concrete sequences, and each was reproduced with a throwaway test against the real screen and FixtureApiClient (deleted afterwards, nothing committed):

1. A queued check-off is lost silently whenever S11 unmounts.
2. A stale queued entry overwrites a newer online state.
3. The loop Add can append two PURCHASE rows for one check-off.

Each of these breaks a ticket invariant, not polish. The fixes are bounded: all of them sit in `app/shopping.tsx`, `src/shopping/queue.ts` and the fixture's `addCheckedOffToInventory`.

## Findings

**F1 [blocker] apps/mobile/app/shopping.tsx:59-64. The queue and the optimistic rows live in component state, and S11 unmounts on every route change.**
- The root layout renders `<Slot />` (apps/mobile/app/_layout.tsx:90). Its own comment says per-screen state "unmounts with the screen".
- `queueRef` and `list` are therefore destroyed whenever the user taps another tab, and also when they tap Add on a no-`itemId` row, because that pushes `/add/manual`.
- Sequence: Simulate offline, check off Chicken breast ("Queued" shows), tap the Inventory tab, come back. `getShoppingList` refetches, chicken is open again, there is no tag and no message, and the check-off never syncs.
- This breaks the invariant "a queued check-off is never lost silently". The in-session scope in Objective (f) means surviving the session, not surviving the screen.
- Fix: hoist the queue to a module-level singleton or a provider above `<Slot />`, next to ToastProvider. Apply queued state over the fetched list on mount, so a queued row renders as checked with its tag. Add a component test: offline, check off, unmount, remount, tag still visible, back online, replayed once.

**F2 [major] apps/mobile/app/shopping.tsx:129-148 with src/shopping/queue.ts. An online tap on a row that still has a failed queued entry bypasses the queue, and the stale entry later overwrites the newer state.**
- Reproduced: offline, check chicken (K1, checked=true), go online, replay rejects (entry stays queued), user unchecks chicken online. The direct call succeeds, so the server row is open while the "Queued" tag is still shown. Toggle offline and back online: K1 replays and the server row becomes done, while the UI still shows it unchecked.
- That is reordered, stale delivery plus a server/UI divergence.
- Separately, a failed entry only retries on the next offline-to-online transition. If connectivity stays up, it sits there indefinitely.
- Fix: when a row has a pending entry, route the new tap through the queue (replace the entry, then replay immediately if online) instead of the direct call. Give failed entries a retry trigger: the next online tap, or a Try again on the tag.

**F3 [major] apps/mobile/app/shopping.tsx:163-191 with src/api/client.ts `addCheckedOffToInventory`. The loop Add has no in-flight guard, and the fixture has no per-row guard.**
- Reproduced: two presses of Add before the promise settles give two keys and two PURCHASE rows. Chicken goes from 1.25 to 2.75 lb.
- Also reproduced: Add, uncheck, re-check, Add again appends a second 0.75 lb PURCHASE for the same shopping row.
- The fixture also accepts Add on a row that is not `done`. The test at client.test.ts "different idempotency key ... does append again" runs on an open row and enshrines this behaviour.
- With the fixture this needs a same-frame double tap. Under M7 latency it becomes easy.
- This breaks "the loop Add is one PURCHASE row" (rule 10 spirit) and "never applied twice".
- Fix: mint one key when the loop bar opens for a row, and reuse it for every Add press on that bar until success (that also covers "reused on retry" at the user level); disable Add while a call is in flight; make the fixture refuse Add unless the row is `done`, and record a per-row `addedTransactionId` so a second Add for the same check-off returns the original result; carry that rule into the M7 endpoint note.

**F4 [minor] src/shopping/queue.ts:83 and shopping.tsx:88-101. There is no replay-in-progress guard, so connectivity flapping during a replay runs two concurrent replays that deliver the same entry twice.**
- Reproduced at unit level: two concurrent `replay` calls give `apply` calls `["k1","k1"]`.
- Same key, and check-off is set-state, so the server can dedupe. But the queue module's docs claim "apply is never called twice for the same tap".
- Fix: hold one in-flight replay promise and chain or skip. Add a test.

**F5 [major, required test missing] No test proves the rendered amount comes from `buyMicros` rather than need minus have.**
- Tests required lists "a test that the rendered amount text equals the DTO's micros formatted (never need minus have)".
- The fixture always satisfies buy = need minus have, because the drift test enforces it. So a mutant that renders `need - have` in `ShoppingRow` passes every test. No component test even asserts "0.75 lb".
- Fix: add a component test with a DTO whose `buyMicros` deliberately differs from need minus have (for example need 2 lb, have 1.25 lb, buy 1 lb), and assert the row renders "1 lb".

**F6 [minor] apps/mobile/src/api/client.test.ts "appends exactly one PURCHASE". It asserts type and delta but not tier or unit.**
- The ticket requires "the right micros and unit and tier". Assert `provenance.tier === "KNOWN_FACT"`.
- Assert the row's unit equals the item's unit, and make the fixture refuse a mismatch (see F7).

**F7 [minor] fixture-shopping-list.json row-olive-oil. The worker's "safe because Add is never offered for a pre-done row" (report §4.3) is false.**
- Uncheck olive oil and re-check it: the loop bar opens with `itemId` set, and Add then appends `buyMicros: 0`, which ZeroDeltaError refuses. The user gets the "Enter an amount to record a change." toast.
- While unchecked, the row reads "0" to buy and counts in the header. The done row also displays "0" where the prototype shows "1".
- If `buyMicros` were ever non-zero, "each" micros would land on a "bottle" item with no unit check.
- Fix: either drop `itemId` from the olive oil row or give it a registry unit that matches the item, and add the unit guard from F6.

**F8 [minor] apps/mobile/app/shopping.tsx:282 Remove button, `hitSlop={6}` on a 24px-high button.**
- 24 + 12 = 36px, under the 44px target. The tokens §5 figure of 6px was computed for `.okbtn` at 32px. The prototype overrides Remove to 24px, and at that height the §5 formula gives ceil((44-24)/2) = 10.
- Fix: `hitSlop={10}`. The other controls are fine: `.chk` is 9, loop Add is 5 on 34px (reaches 44), and the dev toggle, Try again and Browse recipes use full-size buttons.

**F9 [minor] apps/mobile/app/shopping.tsx:316-320 `formatMicrosAsPlainAmount` truncates.**
- A `buyMicros` of 500000 becomes "0". S9's `prefillCount` then falls back to 1, so a 0.5 lb gap is silently prefilled as 1 lb, and 1.5 lb becomes 1 lb.
- No current fixture row hits this, but it is a client-side quantity change (rules 6 and 7).
- Fix: pass the exact decimal. In S9, if the amount is not a whole number, leave the stepper at its default and show nothing prefilled, or refuse the prefill explicitly. Never round.

**F10 [minor] apps/mobile/app/shopping.tsx:163-176. Deviation from Objective (f) that the report does not list as a judgment call.**
- A no-`itemId` Add still navigates to S9 while offline. The ticket says "the Add of the loop bar is refused while offline".
- S9's save is also a server write under M2-T3/M7.
- It is defensible (it is navigation), but it is an unlisted deviation, and combined with F1 it drops the queue. Architect to rule.

**F11 [minor] apps/mobile/app/shopping.tsx:234. The dev offline toggle is gated only on the client being FixtureApiClient, not on `__DEV__`.**
- HttpApiClient never exposes it, so a configured build cannot reach it.
- Any fixture-backed build without `EXPO_PUBLIC_API_URL` ships a visible "Simulate offline" button, including the demo or hallway-test build D-023 anticipates. The string is in all three exported bundles.
- Fix: `__DEV__ && hasDevOfflineToggle(apiClient)`.

**F12 [minor] docs/handoff/M3-T5.worker.md contains 27 em dashes, against CLAUDE.md rule 31 and P11 for docs.** There are no em dashes in any UI string; every non-comment added line was grepped.

**F13 [minor, copy] The load-failure state shows "Couldn't load your shopping list." plus the §8 generic fallback "Something went wrong saving that...".**
- "Saving that" is wrong for a read.
- The title string is new and is missing from the worker's §7 proposed strings, although the DoD requires the "HTTP fallback" string to be proposed there.
- Architect to decide the deck wording.
