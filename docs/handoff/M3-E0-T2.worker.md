## 4. Judgement calls (flagged for the reviewer/architect, not silently resolved)

1. **The standing caveat and the assistant line are two exceptions to the forbidden-words gate, not one.** BACKLOG's M3-E0-T1 acceptance criteria mentions only "except the assistant's 'can't mark any food as safe'" as the carved-out exception, and the dispatch's own §10 instruction says "the exceptions (the one assistant line)" (singular). But the dispatch *also* hands me the exact caveat wording verbatim in its own text ("Known matches only. Not a guarantee this food is safe.") and design-direction §7's already-adopted wording does the same. Both are negations (disclaiming safety, never asserting it), so I documented **both** as exceptions in §10 rather than silently dropping the caveat's own "safe" or inventing a paraphrase that avoids the word. Flagging this explicitly rather than resolving it as if the dispatch's "one exception" language were authoritative over its own verbatim string.
2. **Reason-chip mapping (§5) is an inference, not a sourced fact.** The brief lists six reasons (Used, Consumed, Discarded, Expired, Donated, Manually adjusted); the domain's `TransactionType` has eight values and is documented in `types.ts` as "a superset of brief §7 reasons." I mapped brief's "Used"/"Consumed" onto the domain's `USE_IN_MEAL`/`CONSUME` split ("Cooked" chip vs "Used" chip) because that is the only sensible reading once a recipe-driven consumption path exists, but neither source states this mapping outright. Marked **ENGINEERING INFERENCE** in the deck itself (§5) per rule 5's classification requirement, and called out again here.
3. **Design-direction §7's scan-sheet ALLOWED_WITH_UNKNOWNS wording used a colon-as-label shape** (`"severe: sesame"`) inside its parenthetical. I preserved the wording's substance but dropped the colon (`"severe {allergen} allergy"` instead) because P11 explicitly forbids colon-as-label constructions in live copy, and the ticket also asks me to reuse the design-direction wording. Documented the exact substitution and its reason directly in the §3.3 table row rather than silently diverging from "reuse it verbatim."
4. **The shortfall prompt (§5) is explicitly marked PROPOSED,** per the dispatch's own instruction, since `docs/po/decision-brief-2026-09.md` A9 is a proposed answer to OQ-1, not yet a `DECISIONS.md` entry. I did not promote it to DECIDED and did not pick between the primary and alternative wording; both are recorded, with the primary flagged as the one I'd ship absent a PO steer.
5. **`MAJOR_ALLERGEN_LABELS`** (`taxonomy.ts`) is documented in its own source as "a fallback UI label, not final copy." I adopted it as the deck's `{allergen}` placeholder source anyway (it is the only allergen-name data that exists), but flagged in §2 that a dedicated display-name/pluralization pass ("peanut" vs "peanuts") is still open, not invented here.
6. **User-facing vs internal-only split for `LedgerErrorCode`** (§8) is my own engineering judgement about which errors a normal client action can plausibly trigger (7 user-facing, 7 with only the generic fallback, plus `NOT_FINITE` folded into the fallback family with no distinct row). This is not sourced from any existing doc; it is a reasonable first pass that the reviewer should sanity-check against the eventual M3 client's actual input validation, since a client that validates more aggressively client-side could shrink the user-facing list further.

## 5. Proposed backlog items (not applied; for the architect to accept or reject)

1. **Allergen display-name/pluralization pass** — `MAJOR_ALLERGEN_LABELS` gives singular, unpluralized labels ("tree nut", "crustacean shellfish"); a client-facing string table needs plural forms for natural sentences ("contains peanuts" vs "contains peanut"). Small, M3-adjacent.
2. **Ratify the reason-chip mapping** (judgement call 2 above) as a DECIDED item once the M3 client's consumption flow is designed, since `USE_IN_MEAL` vs `CONSUME` chip framing affects the recipe "Cook this" flow directly.
3. **Resolve OQ-1/A9 shortfall wording** before M8 consumption UX build — the deck carries the proposed primary wording plus one alternative; a PO decision would let this become DECIDED copy instead of PROPOSED.
4. **Toast/undo-window duration** is a client behavior parameter I deliberately did not invent a number for (no source states one); worth a small product decision when the correction flow is actually built, not blocking this deck.

## 6. Honest gaps

- This deck does not cover assistant dialogue beyond the one line needed for the forbidden-words exception (out of scope per the ticket).
- i18n and marketing copy are explicitly out of scope and not addressed.
- The deck assumes a client-side humanization/pluralization layer over `MAJOR_ALLERGEN_LABELS` and `restrictionLabel` that does not exist yet (flagged as backlog item 1); until it exists, a literal implementation would read slightly stiff ("contains peanut" rather than "contains peanuts").
- I did not attempt to design the exact visual/interaction spec for "prominent" (`critical` severity) beyond noting placement/icon requirements; that is a design-system concern for M3-E0-T1's prototype and M3-E0-T3's token work, not this copy deck.
