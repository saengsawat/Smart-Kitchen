# M3-T3 worker report: Inventory list (S4), item detail with ledger history (S5), HTTP read client, correction/removal behind the client port

Branch `m3-t3-inventory`. Implementation model used: Sonnet, per the ticket. Reviewer: Opus-class per
the ticket (ledger semantics on screen).

## 1. What was built

**Contracts** (`packages/contracts/src/inventory.ts`, exported from `index.ts`): `InventoryTransactionDto`
(`transactionId`, `type` from the eight `TransactionType`s, `deltaMicros`/`amount` as exact decimal
text, `recordedAt`, `actor: {kind, displayInitials?}`, `provenance: FieldProvenanceDto`,
`systemFlag?: "OVER_CONSUMPTION"`, `correlationLabel?`) and `InventoryItemDetailDto` (`summary` plus
`history` in sequence order). The M3-T1 placeholder types (`InventoryItemSummary` and friends) are
removed; `InventoryItemSummaryDto`/`InventoryItemDetailDto` are the only inventory client types now.

**Contracts consistency test** (`packages/adapters/src/contracts-consistency/inventory-contracts-consistency.test.ts`):
proves `TRANSACTION_TYPES_DTO` equals the domain's `TRANSACTION_TYPES`, in the same package as the
household one for the same reason (only `packages/adapters` may depend on both contracts and domain).

**Formatting** (`apps/mobile/src/inventory/quantity.ts`): `parseMicros`/`microsToAmountText` are the
only two functions that touch a `bigint` quantity; `trimAmountText` drops a DTO's exact six-place
fraction for display via string manipulation, never a `number`; `formatQuantityDisplay` covers the
prototype's plain-amount, uniform-multi-lot-pack ("3 × 16 oz"), lot-label pack-total ("8 of 12"), and
Estimated-tier "~" prefix cases. A test proves a float never enters the path: `0.1 + 0.2 !== 0.3` in
IEEE-754 but the equivalent micro-unit statement is exact.

**Expiry** (`src/inventory/expiry.ts`): freshness-ring thresholds and urgency text (tokens.md §4.6
ramp: green/amber/rose, never `danger`), calendar arithmetic only, no quantity involved.

**Fixture ledger** (`src/inventory/ledger.ts`, `src/inventory/fixture-household.ts`): an in-memory,
append-only ledger per item (`MutableItemFixture.history`, oldest first, the ledger's authoritative
sequence order). `appendDecrease` clamps at zero exactly the way ADR-008/domain-model.md §4 invariant 2
describes: the decrease is recorded at its full stated magnitude, then a system-authored `ADJUSTMENT`
(`systemFlag: "OVER_CONSUMPTION"`, actor `{kind: "system"}`, no `displayInitials`) restores the balance
to zero. `appendCorrection`/`appendRemoval`/`appendUndo` back `correctQuantity`/`removeQuantity`/`undo`;
nothing edits or deletes a row (rule 10). `buildChenInventory()` reproduces the prototype's S4 rows and
the chicken-breast history exactly: +2.0 (purchase), −2.25 (`USE_IN_MEAL`, clamps), +0.25 system row,
+1.25 (purchase), net 1.25 lb, asserted directly in `ledger.test.ts`.

**"Why" line** (`src/inventory/why.ts`): `buildWhyLine` renders copy-deck.md §5's per-row template
("{action} · {signed qty} · {date} · {who or source}") for each history row in sequence order, and the
§5 clamp sentence instead of the template for the system row. Tested against the chicken-breast fixture.

**Client port** (`apps/mobile/src/api/client.ts`): `ApiClient` gains `getInventoryItem`,
`isInventoryStale`, `correctQuantity`, `removeQuantity`, `undo`, `confirmAiProposal`.
`FixtureApiClient` backs all of it through the ledger module above; `HttpApiClient` implements
`getInventoryItems` for real against `GET /v1/inventory/items` with the fixture bearer token, falling
back to the last good result and reporting `isInventoryStale()` on a network failure (copy-deck.md §7
S4's stale-offline banner). See §3 for what `HttpApiClient` does *not* implement for real yet.
`createApiClient(baseUrl)` is the pure selector `apiClient` is built from, reading
`EXPO_PUBLIC_API_URL` exactly once via `src/config/env.ts` (the sole file exempted from
`no-restricted-globals`/`no-restricted-properties` for `process`).

**Screens**: `app/inventory.tsx` (S4: header with count/verified%/legend link, location segmented
control, Sort · expiry and Needs confirmation chips, the AI-tier confirmation tray, grouped rows with
freshness ring/exact quantity/expiry text/provenance chip, first-run/filtered-empty/location-empty
states, stale-offline banner); `app/inventory/[itemId].tsx` (S5: big quantity, the "Why {qty}?" line
with a legend link, the Correct this stepper and Save correction, Use or remove reason chips, Lots,
History newest-first with the clamp row rendered distinctly); `app/legend.tsx` (the three copy-deck.md
§4 lines in tier order plus the closing line). All three tolerate the layout's pre-redirect frame
(render an empty `View` rather than assume a household/item exists) per the M3-T2 follow-up.

**Shared UI modules** (`src/inventory/`): `list-view.ts` (pure grouping/filtering/sorting, tested
separately from the screen), `provenance.ts` (copy-deck §4 chip/legend text), `transactions.ts`
(reason-chip → `TransactionType` mapping, action labels), `motion.ts` (`useReducedMotion`,
`pressScaleStyle` (drops the transform under `AccessibilityInfo.isReduceMotionEnabled`, tokens.md §6),
`Toast.tsx` (the undo toast, screen-local, not global, see §4).

**Cleanup**: `@smart-kitchen/adapters` removed from `apps/mobile/package.json` and the tsconfig project
reference (nothing imported it since M3-T2); `pnpm install` updates the lockfile; `pnpm --filter mobile
export` verified clean (no `node:fs`/`node:url` bundling error), closing the M2-T1 review's blocker.

**README** (`apps/mobile/README.md`): documents `EXPO_PUBLIC_API_URL`, what switches to
`HttpApiClient` versus what stays fixture-backed, and that seeded rows arrive with M2-T2.

## 3. Deviations (flagged for the reviewer, not silently made)

1. **`packages/adapters/src/inventory/fixture-inventory-items.ts` deleted, outside the ticket's literal
   file scope.** Removing the deprecated placeholder types from `packages/contracts` (an explicit
   ticket instruction) orphaned this M3-T1 stopgap file. It imported the type being removed and
   nothing else in the repo used it for real (only a string literal in a lint-rule test, not an actual
   import). Its own doc comment already flagged its fate as an open question for the architect
   ("decide whether the ledger-built fixtures become the real fixtures corpus"); deleting it (plus its
   test and the one export line in `packages/adapters/src/index.ts`) was the smallest fix that kept
   `pnpm typecheck`/`pnpm test` green after the explicit contracts change, and matches the direction the
   M3-T1 review itself proposed. Flagged here for architect ratification, the same way M3-T1's own
   `packages/adapters` edits were ratified at that ticket's acceptance.

2. **`HttpApiClient` only implements the inventory *list* read for real.** No endpoint exists yet for
   single-item history, household/onboarding state, or any write (M2-T2/M2-T3 are later tickets), so
   `HttpApiClient` composes an internal `FixtureApiClient.returningUser()` and delegates everything
   else to it. `getInventoryItem` wraps the real list row with an *empty* history rather than
   fabricating one. This is a scoping decision within the ticket's own stated boundary ("the client
   consumes M2-T1's `InventoryItemSummaryDto`", write methods "fixture only"), documented in the class's
   doc comment and the README, but it is a real limitation: a live `HttpApiClient` today shows S5 with
   no history for any item until a history-read endpoint exists.

3. **Legend screen's intro sentence reworded.** The prototype's literal text ("It is never a safety
   check by itself.") trips copy-deck §10's forbidden-word grep on the "safe" substring inside
   "safety", proven by the copy-scan test failing on first write. Reworded to "not a claim about the
   food itself," same meaning, not the prototype's exact wording. Proposed for copy-deck §7/§11 below.

4. **"8 of 12" and "3 × 16 oz" pack formatting is an engineering inference, not a wire feature.** No
   DTO in this ticket's scope (or M2-T1's) carries a pack-size total. `formatQuantityDisplay` detects a
   uniform multi-lot pack directly from `InventoryLotDto[]` (safe, general), and separately reads an
   `InventoryLotDto.label` string for an "of N" pattern for the single-lot count case (a fixture-
   authoring convention on an existing free-text field, not a new one). This is my own fixture's
   `"carton of 12"` label, not something a real receipt/OCR pipeline is known to produce yet; flagged as
   a proposed follow-up if a real pack-size field is wanted on the wire.

5. **Removal's secondary reason ("Spoiled", "Wrong item", …) is stored in `correlationLabel`.**
   `InventoryTransactionDto`, per the ticket's own field list, has no dedicated `reason` field (unlike
   the domain's `TransactionInput.reason`). `correlationLabel` is the one free-text field available;
   reusing it for a removal reason is a compromise, not a clean fit (its doc comment describes it as
   "e.g. a recipe name"). Flagged as a proposed follow-up for a dedicated wire field.

6. **History row titles for `USE_IN_MEAL` read "Cooked in {recipe}", not the prototype's static "Used
   in {recipe}".** copy-deck.md §5 ratifies "Cooked" as `USE_IN_MEAL`'s chip label; I used the same
   word for the history-row action label for internal consistency (one vocabulary, not two), rather
   than reproducing the prototype's one hardcoded instance verbatim. A defensible call, not an
   oversight. Flagged because the ticket asks for prototype-verbatim copy elsewhere and this is the one
   place I chose the deck's ratified word over the mockup's literal text.

7. **No undo affordance after a removal.** The acceptance criteria describe undo only for the
   correction flow ("shows 'Corrected. Undo', and undo appends the compensating row"); the removal
   criterion says only "returns to S4". The prototype's `applyReason()` does show an Undo toast, but
   `Toast.tsx` is screen-local state, so navigating back to S4 immediately would unmount it before it
   could be seen. Implemented to the literal acceptance criteria (no removal-undo toast) rather than
   inventing a cross-screen toast mechanism; flagged in case the reviewer reads the removal undo as
   implied.

8. **Lots are a static per-item snapshot, not recomputed after a correction/removal.** The ticket's
   write methods are explicitly item-level ("derives the quantity by summing deltas … per item"), and
   per-lot consumption (FEFO/FIFO allocation) is OQ-1, still open and out of scope ("FEFO shown as a
   multi-lot split" is listed out of scope). A consequence: S5's "Lots" section can look stale relative
   to a fresh correction/removal in the same session. Acceptable for a fixture; flagged for M2-T2 (the
   real endpoint will derive lots from the actual ledger on every read).

9. **Freshness-ring amber/green boundary (7 days) is an engineering inference.** The prototype's own
   fixture data has no `data-days` value between 3 (amber) and 10 (green); documented in
   `expiry.ts`'s doc comment.

10. **No component-rendering test for "S4 renders safely when the layout redirect is pending."**
    M3-T1 did not adopt `@testing-library/react-native` (still true here, no new dependency without
    escalation). The existing `apps/mobile/src/onboarding/route.test.ts` (M3-T2) already covers
    `/inventory` explicitly as one of the deep-link-protected `APP_ROUTES`, including the
    stale-read-never-redirects case the ticket's tolerance requirement is about
    (`resolveLayoutRedirectForRead(null, "/inventory")` returns `null`). I relied on that existing
    coverage rather than duplicating it, and wrote both screens' own `if (items === null) return <View
    style={styles.screen} />;` guard as the mechanism that satisfies the requirement at the component
    level; there is no automated proof the component itself doesn't throw, only that the pattern is
    present in source and the underlying route logic is tested. Flagged as the weakest test coverage in
    this ticket, first thing to attack.

## 8. Review fixes (independent Opus review, PASS WITH FIXES)

All required findings addressed, one commit per group, smallest reasonable steps:

- **F1** (quantity.test.ts didn't discriminate the float path): added `microsToAmountText`/
  `trimAmountText` cases beyond `Number.MAX_SAFE_INTEGER`; `[itemId].tsx`'s `formatDraftAmount` now
  calls `microsToAmountText` instead of restating its whole/frac split.
- **F2** (location-empty state unreachable): `buildInventoryListView` now reports `emptyCause`
  (`"location" | "filtered" | null`); S4 branches on it instead of a single flag that always favoured
  the filtered-empty copy. Tests for both causes and the combined case.
- **F3** (undo could target the wrong row; unhandled rejections): `correctQuantity` resolves
  `{ transactionId }`, the row it actually appended; the toast/undo target comes from that value, never
  from re-reading history. Rejections render copy-deck §8's `ZERO_DELTA` sentence or the generic
  fallback via the new `messageForLedgerError`. Tests for both branches and a concurrent-write
  regression.
- **F4** (removal copy read "Discarded in Spoiled"): ruling implemented, a removal renders its action
  label with a separate "reason: {lowercased}" caption; `correlationLabel` is reserved for a recipe name
  and is never set on a removal row (the reason now travels in `provenance.source`). Fixed in
  `ledger.ts`, `why.ts`, `[itemId].tsx`; updated the tests that asserted the old behaviour.
- **F5** (cold-start offline left a blank screen forever): `src/inventory/load-inventory.ts` pulls the
  load call into a pure function that never rejects; S4 renders the copy-deck §8 generic fallback with a
  Try again action on failure. Tests with a rejecting fake client.
- **F6** (no dedicated reason-chip mapping test): `transactions.test.ts` asserts the four
  `REMOVAL_REASON_CHIPS` pairs against copy-deck §5.
- **F7** (removal at zero balance threw unhandled): the four reason chips disable at a zero balance;
  `handleApplyReason` still catches defensively for a race. Test: `removeQuantity` on an already-zero
  item rejects.
- **F8** (row accessibilityLabel never announced the tier): rows now append the tier via the new
  `tierRowAnnouncement` ("Known Fact" / "Estimated" / "AI, needs confirmation").
- **F9** (AI chip ruling): rows keep the prototype's compact chips as the reviewed visual, full label as
  the accessibility label; the AI chip is now its own 44pt `Pressable` calling `confirmAiProposal`
  directly, a sibling of the row's navigate-to-detail area rather than nested inside it.
- **F10** (clamp row had no tier chip): added; `ROW_CHIP_TEXT` is exhaustive over `ProvenanceTierDto` and
  the DTO's `provenance.tier` is required, so this state is unreachable by construction now.
- **F11** (internal token "fixture-seed" could render): `baseItem`'s `source` param is now required;
  every fixture item passes a plausible one. Same class of bug fixed in `ledger.ts`'s
  `appendCorrection`/clamp sources, which the finding didn't cite by line but the same rule applies to.
  Test: no fixture history row's source matches an internal-token pattern.
- **F15** (unguarded HTTP response shape): `isInventoryItemsResponse` checks `items` is actually an
  array before trusting a parsed body; a malformed body is treated as a failure the same way a network
  error is. Tests for four malformed shapes and the stale-fallback case.
- **F16** (post-removal navigation could get stuck): guarded with `router.canGoBack()` /
  `router.replace("/inventory")`, matching `handleBack`.
- **F17** (legend intro ruling): restored the prototype's exact sentence, including "It is never a
  safety check by itself."; `copy-scan.test.ts`'s allow-list is now `ALLOWED_SAFE_SENTENCES` (an array),
  compared with whitespace normalised so a multi-line JSX text node's line-wrapping can't fail an
  otherwise-exact match.
- **F18** (architect: dead toasts must not ship): the search icon is removed from S4's header entirely
  (comment naming M4); the tray's Edit button now opens the item's S5 screen instead of toasting.
- **Also requested**: `src/config/env.test.ts` covers `getApiBaseUrl`'s set/unset/whitespace-only cases,
  using `vi.stubEnv`/`vi.unstubAllEnvs` rather than touching `process.env` directly, so no
  `eslint.config.js` exemption was needed for the test file itself.
