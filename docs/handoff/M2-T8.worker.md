# M2-T8 worker report: count units take whole numbers (D-029)

Branch `ticket/M2-T8`, from origin/main 08af99d. Implementation model: Opus.

## What I built

An amount in a COUNT-kind unit is a whole number on every new write. The server refuses a fraction with 400 `COUNT_NOT_WHOLE`; S5 and S8 step counts by 1 and refuse a typed fraction with a hint. Mass and volume are unchanged. Existing fractional history reads, replays and undoes as before. No migration, no change to any ledger row, no UPDATE or DELETE.

## How each rule is enforced, and where

Count detection on the server is the domain registry itself: `isCountUnit(unit)` in `apps/api/src/db/inventory/write-service.ts` calls `unitKind` (root export of `@smart-kitchen/domain`), so every alias (count, counts, ct, each, ea, unit, units, pc, pcs, piece, pieces, any case) is covered and an unregistered unit such as `bottle` is not a count unit. The whole check is `micros % MICROS_PER_UNIT === 0n`, on exact `bigint` micros parsed by `decimalTextToMicros`. No float anywhere.

| Rule | Where | Behaviour |
| --- | --- | --- |
| 1 Create | `create-service.ts`, `createInventoryItemWithStock`, after the replay lookup | `assertWholeCount(unit, micros, "amount")`. Both MANUAL and BARCODE. |
| 2 ADJUSTMENT target | `write-service.ts`, `targetDelta` | target must be whole. 12.5 to 12 or 13 is fine; to 12.25 is refused. Existing refusals (negative, precision) come first. |
| 2 ADJUSTMENT delta | `write-service.ts`, `planWrite` | balance + delta must be whole. 12.5 by -0.5 is fine; 12.5 by -1 is refused. `ZERO_DELTA` still comes first. |
| 3 Removals | `write-service.ts`, `planWrite` | allowed when the amount is exactly the balance, or the amount is whole and leaves a whole balance. Omitted amount (remove all) is always fine. |
| 4 Undo | `undoInventoryTransaction` | untouched, never checks the rule. |
| 5 Shopping PURCHASE | `shopping-routes.ts` / `db/shopping/service.ts` | No change. The add-to-inventory body is `{ idempotencyKey }` only; the amount is the server's own gap (`computeRowGap`), never a client amount. |
| 6 Reads, replay, snapshot, reconciliation | not touched | Fractional history still reads (DB test pins detail and list). |

Wire answer: `CountNotWholeError` (an API refusal, not a `LedgerError`, because the ledger holds any exact decimal) is mapped in `routes.ts` `answerFailure` to 400 via `countNotWholeResponse` in `ledger-errors.ts`. No `ledgerCode`. The log line carries the field name only, never a quantity. `COUNT_NOT_WHOLE` is added to `API_ERROR_CODES` with a doc comment; the write and create DTO doc comments say what is refused.

Idempotent retries: the rule judges new statements only. `planWrite` takes `{ wholeCountRule }`, which `applyInventoryWrite` turns off when rows already exist under the client key; the ledger's own replay comparison then answers duplicate (200) or `IDEMPOTENCY_KEY_CONFLICT` (409), so no new row can land. The create check runs after the replay lookup for the same reason. DB tests prove that a fractional write and a fractional create accepted before D-029 still replay 200 and append nothing, and that a changed payload under the same key is still 409.

### Reading of rule 3 (please confirm)

Rule 3's text says "the amount must be whole, or exactly equal to the item's current balance", and the next sentence says "Removing 1 from 12.5 is refused; the member corrects first". Read literally, 1 is whole and would pass. I implemented the example, which matches rule 2's "the resulting balance must be whole": a removal is the exact balance, or a whole amount that leaves a whole balance. On a whole balance that is exactly "the amount is whole". One consequence: an overshooting removal from a fractional balance (13 from 12.5) is refused; remove all instead. An overshooting whole removal from a whole balance still clamps as before. If the literal reading was intended, it is one line in `planWrite` and two test rows.

## Client

`apps/mobile/src/inventory/quantity.ts` gains `COUNT_UNIT_ALIASES` (restated from the registry because mobile never imports the domain; pinned by a test against the literal list), `isCountUnit`, `isWholeMicros`, `classifyTypedAmount` (valid / fraction / unusable), `stepSizeMicros`, `stepAmountMicros`, `isCountNotWholeRefusal`, and the two strings.

- S5 (`app/inventory/[itemId].tsx`, amount field, stepper and error mapping only; the Lots block is untouched for M3-T9): count units step by 1 (labels "Increase/Decrease quantity by 1"), and from a fraction to the next whole number in that direction. A typed fraction shows "Use a whole number, like 2." and Save stays off; the draft keeps the fraction so the stepper can step from it. Unusable text keeps "Enter a number, like 2 or 0.5.". A fractional balance from history shows as is with no hint and Save off until it changes. Mass and volume step 0.25 as before.
- Removal controls: S5's reason chips always send no amount, which means the whole balance, which rule 3 always allows. There is no partial-removal path on S5, so nothing to build; a fractional balance can always be cleared.
- S8 (`app/add/scan.tsx`): the typed package size is judged in the record's unit as the create request spells it (`ct` becomes `each`). A fraction in a count unit shows the whole-number hint and Add stays disabled. The package-count stepper already steps whole packages.
- Refusal mapping: `COUNT_NOT_WHOLE` renders "Use a whole number for this item." on S5 correction, S5 removal and S8 Add, never the server's sentence. `client.ts` needed no change: it already passes the top-level code through to `LedgerRefusedError` when there is no `ledgerCode`.

Scope note: the natural home for the §8 mapping is `ledgerErrorMessage` in `apps/mobile/src/inventory/errors.ts`, which is outside this ticket's file scope. I mapped it at the two screens through `isCountNotWholeRefusal` instead (matched by error name and code, to avoid an import cycle quantity -> errors -> ledger -> quantity). Proposed follow-up: add `case "COUNT_NOT_WHOLE"` to `ledgerErrorMessage` and drop the screen-level wrapper.
