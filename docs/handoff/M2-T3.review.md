# M2-T3 review: household endpoints and item creation

Reviewer: Opus (independent session, read-only). Base: origin/main c6d8ff6. Branch: m2-t3-households @ 8f59d0b.

## Round 1 verdict: PASS WITH FIXES

The tenancy boundary holds, checked against a real cluster, not just by reading the code. All three SECURITY DEFINER functions create or reveal exactly one user's memberships. `app_create_household` refuses outside the new household's own context and cannot be pointed at an existing id. The new table's RLS fails closed. The Okafor owner cannot see or rotate Chen. A household-less caller gets 403 on every household route. Codes are HMAC-hashed and never reach a log: 72 log lines from the compiled server contained no plaintext code and no hash. The rate limit counts before the lookup and keys on the port's user id. Item creation is one transaction, and concurrent double submits serialise. Every CI step is green from an empty build state, and both DB counts match the worker's. The one real defect is in item creation: `bestByDate` accepts non-ISO strings through lenient `Date.parse`, and parses them in the host's local timezone, which gets around the domain's own strict instant rule and stores nonsense dates (F1). Two replay fields are compared correctly but no test pins them (F2), and the rotation route accepts an arbitrary body without complaint (F3). None of the three touches tenancy.

## Findings

F1 [major] apps/api/src/db/inventory/create-service.ts:226. `bestByDate` is validated only with `Number.isNaN(Date.parse(bestBy))` and then canonicalised, so the domain's `ISO_INSTANT_RE` (packages/domain/src/inventory/ledger.ts:70, lot-selection.ts) never sees the raw input. Reproduced against the compiled API with Dean's token: `bestByDate: "1"` gives 201 and lot expiry `2001-01-01T05:00:00.000Z`. `"March 7"` gives 201 and `2001-03-07T05:00:00.000Z`. The 05:00 is this host's UTC-5 offset, so what gets stored depends on the server's timezone. The refusal message itself says "must be an ISO-8601 date or instant". Fix: accept exactly `YYYY-MM-DD` (a regex, parsed as UTC) or `ISO_INSTANT_RE` before canonicalising, and add `"1"` and `"March 7"` to the refusal table in households.db.test.ts, and a unit case in create-service.test.ts.

F2 [minor] apps/api/src/db/inventory/create-service.ts:296, :302, :293. In `sameCreation`, deleting `stored.unit === planned.unit`, `stored.product_ref === planned.productRef` or `stored.sequence === 1` fails no test. The 409 table (households.db.test.ts:753) covers amount, name, location, best-by, both tiers and source, but not unit or productRef. The behaviour itself is correct: with the compiled API, same key with `unit: kg` gave 409 and same key with `productRef: dairy-099` gave 409. Fix: add two rows ("a different unit" `{unit:"kg"}`, "a different product" `{productRef:"dairy-099"}`) and one case for a canonicalisation replay that must stay 200 (`"2026-10-12"` vs `"2026-10-12T00:00:00.000Z"`, confirmed 200).

F3 [minor] apps/api/src/http/household-routes.ts:303-304. `POST /v1/households/me/join-code` has no body schema. Any body, including `{"householdId":"<Okafor>"}`, is accepted and ignored: Dean got 200 and Chen, not Okafor, was rotated, so this is safe. But it breaks M2-T2's "unknown body fields are 400" rule, which the worker applied to every other new route. Fix: `schema: { body: { type: "object", additionalProperties: false, properties: {} } }` (or refuse any body), plus one test.

Notes, not fixes for this ticket:
- N1: `POST /v1/households` has no idempotency key. A retried tap makes two households, and the session moves to the newer one. Combined with the worker's deviation 13 (a member can create a household and their session moves to it) and no switching, a Chen member who creates a household cannot get back to Chen: re-joining with a code is idempotent and does not bump `joinedAt`. Only reachable through the API today, since the M3-T2 onboarding offers create only to new users. Recommend a backlog entry, or an architect/PO call: refuse create for a caller who already has a membership until switching exists, and/or add a client key.
- N2: `resolveJoinCodePepper` decides the dev fallback from `NODE_ENV` alone, not from which identity adapter was chosen. Today it cannot matter, because the fixture adapter refuses the same environments first. With NODE_ENV=production the compiled API exits on the identity refusal before the pepper is ever checked, so the pepper refusal is only unit-tested. Once a real adapter exists, a run with NODE_ENV unset would silently use the public pepper. For the vendor ticket: tie the fallback to the fixture adapter, and refuse a configured pepper equal to `DEVELOPMENT_JOIN_CODE_PEPPER`.
- N3: The DB functions trust the `p_owner_user_id` / `p_user_id` they are given, and `app_user_memberships` lists any user id. The DB has no notion of the session user, so this relies on the app layer (the worker flagged the third). Worth a line in the threat model.
- N4: Membership is checked once, in the port's own transaction, before the request's transaction. RLS keys on household id only. Fine while memberships cannot be removed. A future "remove member" ticket must re-check membership inside the tenant transaction, or a request already in flight still runs in the old household.
- N5: The `FOR SHARE` race in `app_redeem_join_code` against a rotation is correct under READ COMMITTED (the redeem waits for the rotation to commit, then fails the `revoked_at IS NULL` recheck), but no test pins it.

## Judgment calls
- Pepper (HMAC-SHA-256, public dev fallback, refuse outside dev/test): accept. The right call for a 1.7e8 code space. Tighten per N2 when the vendor lands.
- `HouseholdSummaryDto` instead of `HouseholdDto`/`MemberDto`: accept. Sending `restrictions: []` / `noneConfirmed: false` would read as "no known allergies" (SR-1/SR-2 risk). Leaving the fields out through a smaller type is the safe reading of the M2-T4 note.
- No expiry: accept. It is an OPEN question for the PO, correctly not invented. The ticket's "expired" wording should be settled in DECISIONS.
- In-memory per-process limiter: accept for one instance. Endorse the backlog entry for a shared store and a per-IP/global budget before a second instance or real signups.
- Field-comparison replay: accept. Needed because creates have no client `occurredAt`. Actor included (another member's identical body gives 409) is consistent with household-scoped keys, and M2-T2's rule compares the stored row, actor included. Add the F2 tests.
- Provenance strictness: accept for the quantity. The M3-T4b screens (`app/add/scan.tsx:212`, `app/add/manual.tsx:86`) already send `confidence: null, recordedAt: null`, so the real endpoint will not break them. Server-chosen source and refusing AI_INTERPRETATION on the ledger row are right under rule 8. One inconsistency: `bestByProvenance.source/confidence/recordedAt` are accepted and dropped without comment (the scan fixture sends `source` and `recordedAt`; `confidence: "0.9"` got 201), because the lot schema stores only `expiry_tier`. Not a fix for this ticket. For the architect: best-by provenance keeps only the tier, and an AI_INTERPRETATION best-by lands on the lot unconfirmed (labelled as such). Decide whether that needs a confirmation state per ai-architecture.md.
