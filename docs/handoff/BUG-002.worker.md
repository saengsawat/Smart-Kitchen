# BUG-002 worker report: allowlisted browser origins (CORS) on the API

Branch `bug-002-api-cors`, cut from `main` at `74371f1`. Builds D-027 as the architect proposed it
on 2026-09-30 (PO still to ratify). No architecture conflict found. No new package. Two small
deviations from the brief (the allowed request headers, and the attribution line); both are in
section 5.

## 1. What was built

- `apps/api/src/http/cors.ts` (new). Pure pieces: `resolveCorsPolicy(env)`, `parseCorsOrigins`,
  `matchAllowedOrigin`, `corsResponseHeaders`, `corsPreflightHeaders`, the constants
  (`SK_CORS_ORIGINS`, the two implied dev origins, methods, headers, max age, `/v1/*`) and
  `CorsConfigurationError`. Two registration halves:
  - `registerCorsHeaders(app, policy)`: an `onRequest` hook that, for an allowed `Origin`, sets
    `Access-Control-Allow-Origin: <origin>` and `Vary: Origin` on the reply. It is registered
    **before** `registerAuthorization`, so a 401, 403, 404 or 500 to an allowed origin still
    carries the header and the page can read the status instead of seeing an opaque network
    failure.
  - `registerCorsPreflight(app, policy)`: `OPTIONS /v1/*`, declared
    `publicRoute("CORS preflight: ...")`, registered **after** `registerAuthorization` so the
    default-deny `onRoute` guard checks it. The handler reads only `request.headers.origin`, adds
    the preflight headers when it matches and answers 204 with an empty body. The authorization
    hook returns before reading any token for a public route, so identity is never consulted
    (pinned: a preflight carrying Dean's token resolves no token and opens no session).
  - With an empty allowlist neither half registers anything: no hook, no route, `OPTIONS` stays a
    404. That is byte-for-byte the behaviour before this change.
- `apps/api/src/app.ts`: `AppDependencies.cors?: CorsPolicy` (default `NO_CORS`), the two
  registrations in the documented order (header comment updated), and in
  `createAppFromEnvironment` the policy is resolved from the environment after the identity,
  database, pepper and OFF checks; a malformed entry throws `CorsConfigurationError`, which
  `server.ts` already turns into one stderr line and exit 1. When the dev list is implied, one
  structured info line is logged at startup: `cors: SK_CORS_ORIGINS is unset in development, so
  the local web origins are allowed`, with `corsOrigins`.
- `apps/api/src/server.ts`: unchanged. It already passes the whole environment to the composition
  root, so no plumbing was needed.
- `.env.example`: `SK_CORS_ORIGINS=` with a comment (name only, no value).
- `apps/mobile/README.md`: one paragraph in Step 5 (see section 6).

## 2. The exact allow rules and the dev-implied list

1. `SK_CORS_ORIGINS` set and not blank: the comma-separated entries, trimmed, blanks skipped,
   duplicates dropped, are the whole allowlist, in any `NODE_ENV`. Nothing is implied on top.
   Each entry must be exactly what a browser sends as `Origin`: `http` or `https`, a host, an
   optional non-default port, nothing else (checked as `new URL(entry).origin === entry`). A
   trailing slash, a path, a query, credentials, upper case, an explicit default port, another
   scheme, `*` or `null` refuses to start, with a message naming the form that would match. A
   value of only commas yields an empty list (no CORS).
2. `SK_CORS_ORIGINS` unset or blank, and `NODE_ENV` unset, blank or `development` (trimmed and
   lowercased with the identity registry's `normalizeNodeEnv`): exactly
   `http://localhost:8081` and `http://localhost:8090`. 8081 is Expo's web dev server (README
   section 1: press `w` or open `http://localhost:8081`). 8090 is not configured anywhere in the
   repo; it is the origin the web build was served from when BUG-002 was found
   (`docs/bugs/BUG-002-api-no-cors.md`), and the brief asked for it.
3. Anything else (`test`, `production`, `Production`, `prod`, `staging`, `dev`, ...): no origins,
   no CORS headers, no preflight route.

Matching is exact string equality against the list. For an allowed origin every response gets
`Access-Control-Allow-Origin: <origin>` and `Vary: Origin`; a preflight additionally gets
`Access-Control-Allow-Methods: GET, POST, OPTIONS`, `Access-Control-Allow-Headers: authorization,
content-type`, `Access-Control-Max-Age: 600`. The preflight route covers `/v1/*` only; `/healthz`
is not offered to browsers.

## 3. Security notes

- **No `*`.** The origin is echoed, never a wildcard, and `*` is refused as an entry. A wildcard
  tells every page on the web it may read the API's answers. Today a stranger's page has no bearer
  token to send (the token lives in the app), but that is a property of the client, not a rule of
  the server, and naming the origin costs nothing.
- **No credentials flag.** The app authenticates with an `Authorization: Bearer` header, not a
  cookie, so `Access-Control-Allow-Credentials` would permit nothing and is never sent.
- **Exact match only.** No case folding, trimming, prefix, suffix or subdomain logic. Browsers send
  the serialised lowercase origin, so exact equality is correct and cannot be fooled by
  `http://localhost:80810`, `https://app.example.test.evil.test` or two `Origin` lines joined by a
  comma (all pinned).
- **What a non-allowlisted origin sees.** No CORS header of any kind on any response, and its
  preflight is a bare 204, so the browser refuses the real request itself. Non-browser clients
  (the phone, curl) are unaffected either way: CORS is a browser rule, not access control, and
  every `/v1/` route is still behind the bearer token and the default-deny guard.
- **Production default is unchanged.** With the variable unset outside development there are zero
  CORS headers and no `OPTIONS` route (pinned through `buildApp` with no policy, through
  `createAppFromEnvironment` with `NODE_ENV=test`, and through the compiled server with
  `NODE_ENV=test`).
- **Default-deny stays honest.** The preflight route carries its own `publicRoute` reason; a
  mutation that drops it makes the app refuse to boot with `MissingAuthorizationDeclarationError`
  (17 tests fail).
- The startup log line carries only the two public localhost origins. No secrets anywhere.

## 5. Deviations and escalations

- **Allowed headers are `authorization, content-type`, not `authorization, content-type,
  idempotency-key`.** The brief said to match what the mobile client actually sends.
  `apps/mobile/src/api/client.ts` sends `Authorization` on every call and
  `Content-Type: application/json` on every POST; idempotency keys go in the JSON body. Allowing a
  header nobody sends would be dead surface. If a header-borne key is ever added, the constant is
  one line.
- **A malformed `SK_CORS_ORIGINS` entry refuses to start** rather than being skipped. The brief did
  not say; this follows the repo's pattern (bad pepper, bad `SK_OFF_BASE_URL`) and stops a
  trailing slash from silently serving nobody.
- **`Vary: Origin` only on matching responses.** The brief says a non-matching origin gets no CORS
  headers, so I did not add `Vary` there. Shared caches do not store responses to requests with
  `Authorization` by default, so the cache-poisoning case is not live today; flag if the reviewer
  wants `Vary: Origin` on every response once an allowlist exists.
- **Commit attribution** uses `Co-Authored-By: Claude Opus 5.5`, the model that did the work, not
  the `Claude Fable 5.1` line in the brief.
- `.env.example` line 1 has a pre-existing em dash (in the "Names only" header comment). Left alone as out of
  this change; worth fixing at merge.
- `cors.db.test.ts` is a second test file for the one new module; I read "its test" as covering
  it, because the four-token matrix on `/v1/households/me` needs Postgres.

## 7. Proposed D-027 consequences line

> Consequences: the web build works in real mode in local development with no extra setup; a
> deployed web client needs its exact origin in `SK_CORS_ORIGINS`, and nothing else is ever
> served; production stays CORS-free until someone writes that list; a bad entry stops the API at
> boot; the preflight is a declared public route that reads no identity, so the default-deny guard
> and the authz matrix are unchanged.
