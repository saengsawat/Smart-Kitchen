## 2. The safety contract as implemented

`screenSubject(input): Outcome<ScreeningResult>` is pure and total: no clock, no randomness, no I/O, no model call. Same input ⇒ byte-identical result (property-tested).

**Verdict is three-state and there is no fourth:**

| Verdict | Meaning |
|---|---|
| `BLOCKED` | A known allergen match |
| `ALLOWED_WITH_UNKNOWNS` | Nothing matched, but the data does not support concluding absence |
| `ALLOWED` | Nothing matched **and** an explicit `KNOWN_FACT` completeness declaration licenses concluding absence |

There is no `isSafe`, no `safe`, no `allergenFree` anywhere in the API — enforced by a test that walks the whole returned object graph and fails on any key matching `/safe|allergenfree|isok/i`. `ALLOWED` is documented everywhere as **"no known match"**.

**Per (member, restriction) the engine derives one outcome, worst-wins across loci** (a *locus* = the product, or each recipe ingredient):

| Outcome | Established by | Verdict |
|---|---|---|
| `MATCH` | a `CONTAINS` assertion for the restricted allergen, or a curated/user term found in a name or ingredient statement | `BLOCKED` |
| `POSSIBLE_MATCH` | a `MAY_CONTAIN` assertion | severity-dependent (§5) |
| `UNKNOWN` | nothing matched, nothing licenses absence | `ALLOWED_WITH_UNKNOWNS` |
| `NO_KNOWN_MATCH` | nothing matched, and absence is licensed | `ALLOWED` |

Household verdict = worst member verdict; member verdict = worst restriction verdict (domain-model.md §4 invariant 7).

### Why `ALLOWED` is reachable at all — the `AllergenDeclaration`

Absence-of-data is never absence-of-allergen (SR-2), so the engine will not infer absence from silence. But a verdict space where `ALLOWED` is unreachable would be useless, so absence needs a *positive, sourced* claim. That is `AllergenDeclaration`:

```ts
{ majorAllergens: "COMPLETE_FOR_MAJOR_ALLERGENS" | "PARTIAL",
  ingredientStatement: "COMPLETE" | "PARTIAL" | "ABSENT",
  tier: string,      // only the exact value "KNOWN_FACT" counts
  source: string, observedAt?: string }
```

Two independent claims because they license different conclusions: a US label enumerating the nine majors says nothing about a user-defined "mango" allergy, so `majorAllergens` licenses only `MAJOR` restrictions and `ingredientStatement` only `USER_DEFINED` ones. **Neither counts below `KNOWN_FACT` tier** — that is rule 9 / SR-1 expressed as a data rule: an `AI_INTERPRETATION` or `ESTIMATED` claim of completeness can never clear an allergen, while an AI-tier `CONTAINS` assertion still blocks (both are tested).

**Consequence worth flagging to the architect:** a bare LLM-generated recipe (ingredient names, no resolved catalog data) can only ever come back `BLOCKED` or `ALLOWED_WITH_UNKNOWNS`. That is the honest answer, and it makes M6's UI obligation concrete: unknowns are the normal case until ingredients resolve to declared products, not an edge case.

Note `AllergenDeclaration` is **new vocabulary this ticket introduces** — `domain-model.md` §2 has `AllergenAssertion` but nothing that expresses completeness. Proposed doc update in §10.

## 3. Exact matching rules (`text.ts`)

Applied identically to haystack text and to every term:

1. **Normalize** — NFKD, strip combining marks (so `crème` ⇒ `creme`, and a decomposed `è` cannot dodge a term); `toLowerCase()`; every character outside `[a-z0-9]` becomes a space (this splits `peanut-butter`, `soy(lecithin)`, `milk/cream`); collapse spaces; trim.
2. **Tokenize** — split on single spaces.
3. **Compare by token-sequence equality, never substring containment.** An n-token term matches at position i only if all n tokens compare equal. This is what makes `peanut` fail to match `pea` and `pea` fail to match `peanut`.
4. **One inflection rule:** a haystack token also matches a term token when it is that token + literal `s` or `es`. That is the *whole* rule — no `y`→`ies`, no consonant doubling, no irregular plurals, no runtime synonym generation. Irregulars (`anchovies`, `molluscs`) are listed explicitly in the data. The rule can only ever *widen* matching, i.e. only ever block more.
5. **Longest term wins** at each position and the scan resumes after the match, so results are independent of the order terms were listed in (tested).
6. **Exclusion phrases** are masked out of the haystack *before* an allergen's terms are scanned, and only for that allergen. `butter` is a milk term, so `milk`'s exclusions mask `peanut butter`, `almond butter`, `cocoa butter`, `cream of tartar`, `coconut milk`…; the peanut scan still sees `peanut butter` in full. Masking is longest-phrase-first, and a masked position can never be reused. Exclusions apply **only to free-text scanning** and can never suppress an explicit `CONTAINS` assertion — which is what stops them becoming a way to clear an allergen.

**Curated lists are incomplete by construction and always will be.** That is safe only because of how the engine uses them: a term match is evidence of *presence*; the absence of a match is never evidence of absence and never on its own yields `ALLOWED`. Growing the lists can therefore only make the engine block more — new entries are a low-risk, fixture-first change.

**User-defined terms** are normalized at construction and matched by the identical rules with no exclusions and no synonyms. A term shorter than 3 characters after normalization is rejected (`TERM_TOO_SHORT`) because short tokens match too much text to be safe evidence. User terms are additionally matched against the *raw code string* of allergen assertions, so a `mustard` tag blocks a user-defined mustard allergy even though the taxonomy has no mustard code.

## 5. PROPOSED policies for architect ratification

Four judgement calls that are policy, not implementation detail. All are one-line data changes.

### P1 — Cross-contact (`MAY_CONTAIN`) handling · **the one the ticket asked me to propose**

Implemented as `CROSS_CONTACT_POLICY` (frozen data in `screen.ts`, deliberately **not** a caller-supplied option — an option that turns a block into a non-block is exactly the override channel the safety contract forbids):

```ts
{ severe: "BLOCK", standard: "WARN_UNKNOWN" }
```

- **`severe` ⇒ `BLOCKED`.** Mandated by the dispatch and clearly right: for an anaphylactic allergy, "the manufacturer does not know whether this contains it" is not a risk worth recommending.
- **`standard` ⇒ `ALLOWED_WITH_UNKNOWNS` + a `high` `CROSS_CONTACT` warning.** My proposal, and the one I want the architect to actively ratify or overturn.

**Argument for `WARN_UNKNOWN` (what I implemented):** a `MAY_CONTAIN` label is *by definition* a statement of uncertainty — the manufacturer is saying "we do not know". That maps exactly onto the middle verdict, which exists precisely so we never have to choose between a false block and a false safety claim. It is never rendered as safe, it always carries a prominent warning naming the allergen, and it preserves the choice that people with non-severe allergies routinely make for themselves. Blocking instead would remove a large fraction of packaged goods from recommendations for anyone with a mild allergy, with no way to express tolerance — and "when in doubt, block" is satisfiable here without a block, because the doubt is *surfaced* rather than hidden.

**Argument for `BLOCK` (the alternative):** "when in doubt, block" read literally; users may not read warnings; a mild-allergy classification can be wrong or can change.

**Cost of overturning:** flip one map entry and update the `expect` blocks in `screening-006`/`screening-007` (both fixtures say so in their `notes`) plus the two-row matrix in `screen.test.ts`. No structural change.

### P2 — `shellfish` covers molluscs in the *term* data
FDA's major allergen is **crustacean** shellfish only, and the code is named `shellfish` to match the fixture spelling. Its curated term list additionally covers molluscs (clam, mussel, oyster, scallop, squid, octopus). Rationale: colloquial "shellfish allergy" usually includes them and over-inclusion blocks where under-inclusion would expose. This is broader than the FDA scope, so it should be a conscious decision. Alternative: drop the mollusc terms and tell users to add a user-defined restriction (worse — it depends on the user knowing to).

### P3 — `coconut` is screened as a tree nut
FDA classifies coconut as a tree nut for labeling purposes, so it is in the `tree_nut` term list. However most tree-nut-allergic people tolerate coconut, and this will block a lot of legitimate recipes. Options: keep (current, conservative), or give coconut its own code so users can restrict it independently. I recommend keeping it for MVP and revisiting when there is a preferences UI.

### P4 — severe allergy + unknown data stays `ALLOWED_WITH_UNKNOWNS`
I did **not** escalate severe + unknown to `BLOCKED`, because INV-ALRG-2 explicitly prescribes "unknown + warning", not "blocked". The engine instead emits a `critical` `SEVERE_ALLERGY_UNKNOWN_DATA` warning, and M6 can filter on that if the product decides recommendations should hide such items. Flagging it because it is arguably the most consequential remaining judgement call and it belongs to the recommendation layer, not here.

## 6. UI copy requirements (for M3 / M6 client tickets) — DoD item

These are requirements on client code, derived from SR-2, FR-ALG-2 and brief §3. Also recorded in the module docblock at `packages/domain/src/allergens/index.ts` so they travel with the API.

1. **Never render any verdict as "safe", "allergen-free", "OK to eat", or a green check that reads as clearance.** `ALLOWED` renders as **"no known allergen match"**.
2. **Every result carries a `NO_SAFETY_GUARANTEE` warning** (always, including on `ALLOWED`). Its standing caveat must be shown wherever a verdict is shown. It is `severity: "info"` because it is always present — that is a rendering hint, **not** permission to omit it.
3. **`ALLOWED_WITH_UNKNOWNS` must never be visually collapsed into `ALLOWED`.** They are different states and the middle one is the honest majority case early on. Show *what* is unknown: each `ScreeningUnknown` names `restrictionLabel`, `severity`, `reason` and `locus` for exactly this purpose.
4. **`critical` warnings must be prominent** (brief §3: "a prominent warning" for serious allergies): `SEVERE_ALLERGY_UNKNOWN_DATA`, `CROSS_CONTACT_SEVERE`. `high`: `CROSS_CONTACT`, `UNRECOGNIZED_ALLERGEN_DATA`.
5. **Key copy off `warning.code` and `unknown.reason`, never off `message`.** The `message` strings are machine-facing, deliberately terse, and not localized.
6. **A `BLOCKED` recommendation is never displayed as a choice** (INV-ALRG-1). Filtering is the caller's job — `partitionByVerdict` returns exactly that split. Showing it greyed-out with a reason is a product decision; showing it as selectable is a bug.
7. **`BLOCKED` always has evidence** — show it. `ScreeningEvidence` names the member, the restriction, which locus, and the matched term/text, so "why" is always answerable ("contains peanut — matched 'peanuts' in the ingredients of *Breakfast bar*").
8. **Per-member results exist** (`result.members`) — a household verdict alone is not enough UI. Say *whose* restriction blocked it.
9. **Unknown ≠ absent.** Copy for `reason: "NO_ALLERGEN_DATA"` should say "we don't have allergen information for this item", never "no allergens listed".

## 8. Fixture corpus, and the route I had to take

`tests/fixtures/recommendations/**` holds 15 JSON cases across all four required categories (`valid`, `allergen-violating`, `adversarial`, `missing-data`) plus a README documenting the schema. They are the durable artifact and are shaped for M6 eval reuse: expectations are data (`verdict`, per-member verdicts, per-restriction outcomes, and exact sets of evidence kinds / unknown reasons / warning codes).

**The domain tests cannot read them, and this is the fallback route the dispatch specified.** I first wrote a loader using `node:fs`. The dependency-boundary lint *does* permit it (it scopes `import-x/no-nodejs-modules` to `packages/domain/src/**` while ignoring `*.test.ts`), but **typecheck fails**: `packages/domain` has no `@types/node` and no `"types": ["node"]` in its tsconfig, unlike `packages/adapters` which declares both. `tsc` reports `TS2591: Cannot find name 'node:fs'` and `Property 'url' does not exist on type 'ImportMeta'`. Fixing that means editing `packages/domain/package.json` and `packages/domain/tsconfig.json` — outside my file scope, a dependency change under rule 11, and a deliberate weakening of the zero-I/O boundary that defines the deterministic core. So I took the documented alternative: **the JSON is the durable artifact, and `corpus.test.ts` mirrors the cases as in-file constants.**

The mirror was *generated from the JSON files*, so the two are identical as committed, and `corpus.test.ts` carries `CASE_FILES` plus a docblock stating the rule ("change one, change the other"). The residual drift risk is real and I have proposed a permanent fix in §12 (a mechanical consistency check in `packages/adapters`, which may read files).

# Fixes applied (post-review)

Independent Opus review returned **PASS WITH FIXES**: no block-bypass found, three fail-open paths to `ALLOWED`, two robustness/coverage gaps, plus endorsed additions. All ten items applied on `m1-t4-allergens` in commit `cfd797b`, same file scope, no dependency changes.

The common shape of F1/F2/F3 is worth stating: none of them let a *known allergen* through. All three were paths to a wrongly **permissive** verdict — which is exactly where the risk lives in this design, because `ALLOWED` is the state carrying a licence requirement. The reviewer attacked the licence rather than the block, and was right to.

## Required findings

**F1 — prototype keys resolved through the alias table.** `ALLERGEN_CODE_ALIASES[folded]` on a plain object read `Object.prototype`, so `normalizeAllergenCode("constructor")` returned the `Object` function. A `constructor`-coded assertion therefore looked *recognized*: the locus was treated as interpretable, which cleared `UNRECOGNIZED_ALLERGEN_DATA`, suppressed the critical `SEVERE_ALLERGY_UNKNOWN_DATA` warning, and let a completeness declaration upgrade the verdict to `ALLOWED`. Fixed with an `Object.hasOwn` guard before the lookup. Tests: 12 prototype-key spellings fold to `undefined` (`taxonomy.test.ts`), plus three screening-level repros including the suppressed-critical-warning case.

**F2 — a name was being treated as an ingredient statement.** `licensesAbsence` took a `hasText` flag satisfied by the *name*; since a recipe ingredient's `ref` is mandatory, that flag was unconditionally true for every recipe locus, so a user-defined allergy reached `ALLOWED` with zero ingredient statement scanned — contradicting the rationale written in `types.ts` itself. The parameter is now `hasIngredientsText`, computed from `locus.ingredientsText` alone, and `unknownReasonFor` was realigned so `NO_INGREDIENT_TEXT` fires for both shapes. Tests cover product-name-only, recipe-ref-only, whitespace-only text, **and** two non-over-rejection cases (a real ingredient statement still reaches `ALLOWED`; major-allergen restrictions are unaffected, since a label declaration genuinely does cover them).
