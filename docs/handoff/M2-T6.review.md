## Findings
- F1 [medium, test gap, required] `0011_inventory_item_moves.sql:60`: `clock_timestamp()` is unpinned; with `DEFAULT now()` (mutant M24) the suite stays green because the only test runs its moves one after another. Under `now()` a move whose transaction began earlier and then waited on the item lock is stamped before the move it waited for: the history lists the chain out of order and `create-service.ts`'s "first move's `from_location`" picks the wrong row and refuses a legitimate create retry. Probe: two connections (E begins and selects; F begins, moves and holds the lock; E moves and blocks; F commits; E commits); ordering by `occurred_at` must give [F, E]; passes on eb16af7, fails under M24. Fix: add that test to `moves.test.ts`.
- F2 [low, test gap, required] `moves.test.ts:144` and `inventory-move.db.test.ts` (`image()`): "byte-identical" compares `to_jsonb` only; a no-op `UPDATE inventory_lots SET label = label` on the move path (M41; the app role holds UPDATE(label)) passes. Fix: add `ctid` and `xmin` to the transaction and lot images (the M2-T5 precedent); the items image stays content-only.
- N1 [low, backlog] the history merge mixes two clocks: the ledger's `recorded_at` (the API host's `new Date()` before the transaction opens, millisecond precision) and the move's `occurred_at` (the database's `clock_timestamp()`); with the API clock 2 s ahead an ADJUSTMENT made before a move lists after it; same-host CI cannot see it; no quantity affected; the order is deterministic. Fix (follow-up): record the ledger position on the move row under the item lock (`after_sequence`) and merge by it, or one clock.
- N2 [low, backlog] the tie-break among moves is a random uuid (`create-service.ts:315`, `ORDER BY m.occurred_at, m.id`, and the merge); two chained moves with an identical `occurred_at` (inserted as the owner) made a correct create retry fail 5 times in 12; not reachable through the API under the item lock while the database clock only moves forward; a backward clock step makes it reachable. Same fix as N1.
- N3 [cosmetic] `0011:42-44`: "drops both trigger functions"; there is one.
- N4 [low, judgment] `[itemId].tsx:240`: the double-tap guard is React state, not a ref; two taps inside one frame both pass and the second gets SAME_LOCATION and an error toast after the success toast; the stand-in test passes because `fireEvent` re-renders between presses. Switched to a ref by ruling.
