### Supported units

| Kind | Base | Units (canonical symbol) |
|---|---|---|
| MASS | g | `g`, `kg`, `oz`, `lb` |
| VOLUME | ml | `ml`, `l`, `tsp`, `tbsp`, `cup`, `pt`, `qt`, `gal` |
| COUNT | count | `count` (aliases: `ct`, `each`, `ea`, `unit`, `units`, `pc`, `pcs`, `piece`, `pieces`) |

Chosen to cover the brief §6 worked example's units (lb, oz, g, kg, cups, tbsp, tsp, ml, l,
count/each) plus the volume units (`pt`/`qt`/`gal`) needed to keep the US customary ladder
internally consistent (a recipe's "cups" is one hop from a shopper's "gallons"). Not in
scope: fluid ounces, metric-only rarities (dl, dr), imperial (UK) units, localization/display
units (explicitly out of scope per BACKLOG.md).

**Decision: `oz` is the avoirdupois *mass* ounce, not the fluid ounce.** The brief lists `oz`
alongside `lb`/`g`/`kg` (mass), never alongside `cups`/`tbsp` (volume); domain-model.md's own
example ("Kirkland Greek Yogurt 32 oz") is a US package's printed net *weight*. Registering
both a mass-oz and a fluid-oz under the same symbol would make `lookupUnit("oz")` ambiguous —
exactly the kind of guess this module must never make — so fluid ounces are simply
unsupported. Documented in `registry.ts`'s module header; flagged as a proposed domain-model
note in §6 below.

### Exact conversion factors (all definitional, not measured)

- **MASS:** the international avoirdupois pound is *defined* as exactly `0.45359237 kg`
  (1959 international yard-and-pound agreement) ⇒ `lb = 453.59237 g` exactly;
  `oz = lb/16` exactly; `kg = 1000 g` exactly.
- **VOLUME:** the US liquid gallon is *defined* as exactly 231 cubic inches, and the inch as
  exactly `2.54 cm` ⇒ `gal = 3.785411784 L` exactly. `qt = gal/4`, `pt = qt/2`, `cup = pt/2`,
  `tbsp = cup/16`, `tsp = tbsp/3` — the standard US **culinary** ratios (1 cup = 16 tbsp =
  48 tsp), not the FDA nutrition-label rounded units, since this module serves recipes and
  shopping, not label compliance. `l = 1000 ml` exactly.
- **COUNT:** dimensionless, `count = 1` by construction.

Every factor is stored as a `Rational` (exact `bigint` fraction), derived from these anchor
constants via exact division — never as a decimal literal that could itself be a rounding.

## 2. Public API

```ts
convert(amountMicros: bigint, from: string, to: string): Outcome<ConversionResult>
convertWithBridge(amountMicros: bigint, from: string, to: string, bridge: ConversionBridge): Outcome<ConversionResult>
makeBridge(fromKind: UnitKind, toKind: UnitKind, ratio: number): Outcome<ConversionBridge>
compareQuantities(aMicros: bigint, aUnit: string, bMicros: bigint, bUnit: string): Outcome<-1 | 0 | 1>
addQuantities(aMicros: bigint, aUnit: string, bMicros: bigint, bUnit: string, resultUnit?: string): Outcome<ConversionResult>
neededQuantity(requiredMicros: bigint, requiredUnit: string, onHandMicros: bigint, onHandUnit: string): Outcome<ConversionResult>

lookupUnit(unit: string): Outcome<UnitEntry>
unitKind(unit: string): Outcome<UnitKind>
unitsOfKind(kind: UnitKind): readonly UnitEntry[]

interface ConversionResult { micros: bigint; unit: string; amount: number; exact: boolean }
interface ConversionBridge { fromKind: UnitKind; toKind: UnitKind; ratio: Rational }
```

`ConversionBridge` is the **only** sanctioned way to cross MASS/VOLUME/COUNT kinds — it is
always caller-supplied (a density, a per-item weight, …), never built into the registry.
There is no default density anywhere in this module; absent a bridge, cross-kind conversion
is a typed `INCOMPATIBLE_UNITS` error. `makeBridge` rejects a non-finite, zero, or negative
ratio (`NOT_FINITE`/`INVALID_BRIDGE_RATIO`) since those aren't physically meaningful
densities/weights.

> **Correction (post-review, §11 F2):** at initial submission this claim was incomplete —
> `makeBridge` correctly *rejected* non-finite/zero/negative ratios, but for a finite ratio
> that `String()` renders in exponential notation (e.g. `1e-7`, `1e21`) it **threw** a
> `SyntaxError` instead of returning a typed `Outcome`, because its private ratio parser split
> on `"."` with no exponent handling. Fixed in §11 F2 by reusing `rational.ts`'s
> `decimalToRational`, which already parses the exponent group; `makeBridge` now returns an
> `Outcome` for every finite `ratio`, per its documented never-throws contract, with no
> exception for this earlier bug.

`neededQuantity` is INV-SHOP-1's helper: `max(0, required − onHand)`, expressed in
`requiredUnit`, with `onHand` converted into that unit first (typed error, never a zero-guess,
if the units are incompatible).

## 3. Exactness / rounding policy (and why)

Every conversion computes in exact `Rational` arithmetic end-to-end and rounds to the nearest
`bigint` micro-unit **exactly once**, at the very end, via `roundHalfEven` (round-half-even /
"banker's rounding": ties round to the neighbour with an even last digit — 0.5→0, 1.5→2,
2.5→2, -0.5→0, -1.5→-2, -2.5→-2, -3.5→-4).

**Chosen over round-half-up** because unit conversion in this system is applied repeatedly
over a session — recipe scaling, a shopping-gap calculation running across many ingredients —
and round-half-up biases every exact tie in the same direction; that bias accumulates across
repeated conversions in a way round-half-even's tie-breaking does not (it matches IEEE 754's
default and most languages' `Math.round`-adjacent "round to even" behavior for exactly this
reason). It's a policy choice, not a derived fact, and it is the only place in this module
precision can be lost — every result carries `exact: boolean` so a caller can tell whether
rounding actually happened, rather than assuming either way.

**Alternatives considered and rejected:**
- **Reject any inexact result as a typed error.** Rejected: real kitchen conversions
  routinely need this (`oz → g` is `28.349523125 g` exactly, which needs 9 decimal places —
  more than the 1e-6 micro-unit scale holds). Erroring on every such conversion would make
  the module unusable for the exact recipes it exists to serve; M1-T1's ledger can afford to
  reject unrepresentable *inputs* because those are user-typed quantities meant to be taken
  literally, but a *conversion factor* is a derived constant, not user input, so the same
  argument for rejection doesn't carry over.
- **Round-half-up (arithmetic rounding).** Rejected for the accumulating-bias reason above.
- **Truncate (round toward zero).** Rejected: biases every conversion in the same direction
  (always undershooting), which for shopping-gap math means `neededQuantity` would
  systematically under-estimate how much to buy.

This mirrors `inventory/quantity.ts`'s discipline (exact arithmetic, no silent float
precision loss) while making a different, appropriate choice at the one point where these two
modules' concerns genuinely differ: the ledger's `amountToMicros` is validating **caller
input** it must never alter; this module's `roundHalfEven` is finalizing a **derived
result** it must produce *some* answer for.

## 11. Fixes applied (2026-09-09, post-review)

Independent Opus review verdict: **PASS WITH FIXES**. All required fixes (F1–F4) and the
endorsed barrel-narrowing item applied on this same branch (`m1-t3-units`), same file scope.

### F1 (HIGH, test gap) — ground-truth factor pinning

**Finding:** every existing property/unit test asserted only internal self-consistency (e.g.
`cup = 16 * tbsp`); nothing pinned the anchor constants (the pound, the gallon) against a
value transcribed independently of this module's own code. The reviewer demonstrated that
substituting the imperial (UK) gallon for the US liquid gallon — a ~20% error across every
volume unit — passed the entire existing suite.

**Fix:** `packages/domain/src/units/registry.test.ts` gained a new
`"absolute ground-truth factors"` describe block. Each unit's `factorToBase` is checked by
cross-multiplication (`num * expectedDen === expectedNum * den`, so neither side needs to
already be reduced) against literals typed in by hand from the definitional facts cited in
`registry.ts`'s own module comment (1959 pound-definition, 231-cubic-inch/2.54cm-inch gallon
definition) — **not** copied from or derived through `registry.ts`'s constants. Also added:
negative assertions that the imperial gallon (4546.09 mL), a metric cup (250 mL), and the
imperial cup (284.130625 mL) are **not** what `gal`/`cup` resolve to.

**Test:** `registry.test.ts` → `"absolute ground-truth factors (independent literals, not
derived from this module)"` (11 new `it` blocks: MASS pins, VOLUME pins, COUNT pin, 3 negative
assertions).

### F2 (defect) — makeBridge threw on exponential-notation ratios

**Finding:** `makeBridge`'s private `decimalRatioToRational` built a rational via
`String(value).split(".")` with no handling for `String()`'s exponential output (anything
`< 1e-6` or `>= 1e21`), so e.g. `makeBridge("VOLUME", "MASS", 1e-7)` reached a bare
`BigInt("1e-7")` and **threw** a `SyntaxError` — violating the module's own never-throws
contract (rule: every domain-rule violation is a typed `Outcome`, not an exception).

**Fix:** deleted the private parser; `makeBridge` now calls `rational.ts`'s
`decimalToRational` (which already parses the regex's exponent group correctly), mapping a
`null` result to the typed `NOT_FINITE` error. The zero/negative check now reads
`!isPositive(rational)` on the parsed rational rather than a raw `ratio <= 0` check on the
input `number`.

**Test:** `convert.test.ts` → two new tests in the `convertWithBridge` describe block:
`1e-7` ratio (`1000 ml @ 1e-7 g/ml = 100 micro-g`, exact) and `1e21` ratio (`1 micro-count @
1e21 g/each = 10^21 micro-g`, exact), both asserting `ok: true` and the exact numeric result
— i.e. no throw and correct arithmetic, not merely "didn't crash." Also added a
regression-adjacent test that a *negative* exponential-shaped ratio (`-1e-7`) still correctly
fails `INVALID_BRIDGE_RATIO` rather than being swallowed by the parsing fix.

### F3 (contract violation) — canonical-unit leak in addQuantities/neededQuantity

**Finding:** `addQuantities`'s final `buildResult` call used the raw `resultUnit` parameter
(defaulting to the caller's raw `aUnit` string) instead of the already-canonical unit the
internal `convert()` call had resolved to; `neededQuantity` had the identical bug with
`requiredUnit`. A caller passing an alias (`"pounds"`) or non-canonical case (`"POUNDS"`)
would get that same string back in `ConversionResult.unit` — and since the ledger compares
units by exact string equality, that divergence could cause spurious `MIXED_UNITS` rejections
or a computed quantity that silently stops matching an otherwise-identical canonical balance.

**Fix:** both functions now read the canonical unit off the conversion result they already
computed (`aInResult.value.unit` in `addQuantities`, `onHandInRequired.value.unit` in
`neededQuantity`) instead of echoing the caller's raw string.

**Test:** `convert.test.ts` → new assertions in both the `compareQuantities / addQuantities`
and `neededQuantity` describe blocks, each passing an alias (`"pounds"`) and a differently-
cased canonical symbol (`"LB"`) as the relevant unit argument and asserting the result's
`.unit` is always `"lb"`.

### F4 (endorsed) — compareQuantities was not antisymmetric

**Finding:** `compareQuantities` converted `b` into `a`'s unit (rounding to the nearest
micro-unit of `a`) and then compared the rounded value against `aMicros`. Because rounding
happens on whichever side is *not* picked as the target, `compareQuantities(a, b)` and the
argument-swapped `compareQuantities(b, a)` could disagree near a half-micro-unit boundary —
concretely, `compareQuantities(1n, "tsp", 0n, "cup")` reported `1` (correct) but the reversed
call reported `0` instead of `-1`.

**Fix:** rewritten to convert neither side to micro-units at all: both quantities' exact
rational value in their shared kind's base unit is computed (`amountMicros * factorToBase`,
still exact `Rational`s) and compared directly via `rational.ts`'s `compare` (cross-
multiplication — no division, no rounding, nothing to be non-antisymmetric about).

**Test:** `convert.test.ts` → the literal tsp/cup repro, plus a new property test
(`fast-check`) asserting antisymmetry — `compareQuantities(a, b)` and
`compareQuantities(b, a)` are exact negations of each other (or both `0`) — across every
same-kind unit pair in the registry and micro-amounts in `[-10_000, 10_000]`.

### Endorsed — narrow the root barrel

**Change:** `packages/domain/src/index.ts` no longer re-exports the units module's generic
`Rational` arithmetic primitives (`makeRational`, `add`/`compare`/`divide`/`multiply`/
`subtract`, `reciprocal`, `negate`, `fromInt`, `isZero`/`isPositive`/`isNegative`,
`maxRational`, `rationalToNumber`, `decimalToRational`, `roundHalfEven`,
`RATIONAL_ONE`/`RATIONAL_ZERO`, and the `Rational`/`RoundedInt` types) — they remain exported
only from `packages/domain/src/units/index.ts`. The root barrel now re-exports just the
units-domain-facing surface (`convert`, `convertWithBridge`, `makeBridge`,
`compareQuantities`, `addQuantities`, `neededQuantity`, the registry functions/constants, and
the `ConversionResult`/`ConversionBridge`/`UnitEntry`/`UnitKind`/`UnitError*` types). Rationale
recorded in §7 (Deviations) above. **Note on scope:** the dispatch named "the six renamed raw
Rational helpers"; the code before this fix had five `as`-renamed value exports at root
(`addRational`/`compareRational`/`divideRational`/`multiplyRational`/`subtractRational`) —
I narrowed the *entire* generic-Rational surface (renamed and not) rather than only those
five, since leaving the un-renamed ones (`fromInt`, `isZero`, `makeRational`, …) at root would
have left the same category of thing half-exposed and defeated the stated goal ("smaller
public surface now"). Flagging this interpretation explicitly in case a narrower cut (exactly
the five/six named identifiers) was intended instead — trivial to adjust either way.
