**(c) Check-off.** The round `.chk` control (26px, 9px hitSlop per tokens.md §5) toggles a row;

(`nextIdempotencyKey()`), reused if the same tap is replayed — see §2.

**(e) Already have · skipped.** Dashed rows at the bottom (`SkipRow`), always their own section

Est.", rice) or the literal "sufficient" the DTO licenses via a `null` `haveTier` (soy sauce) — no

**(f) Offline.** `ApiClient.isOffline()`/`subscribeOffline` (new port members).
`FixtureApiClient.setOfflineForDev` is a dev-only toggle (there is no real network to lose in a

for a row with an `itemId` while offline, never queued (the ledger write needs the server); a row
with no `itemId` still opens S9 regardless of connectivity (local navigation, not a network write).

## 2. Queue design

`ShoppingCheckOffQueue` (`src/shopping/queue.ts`) is a plain `Map<rowId, entry>`, no React, no
`ApiClient` — the screen decides whether to enqueue (reading `isOffline()` at tap time) and hands
the queue an `apply` function. **Enqueue**: keyed by row, so a second tap on the same row before
reconnecting *replaces* the pending entry rather than appending a second one — the row's current
desired state is one boolean, and the superseded key was never sent anywhere, so nothing
server-visible is lost by discarding it. **Replay order**: `Map` iteration order, which is a row's
*first*-queued position (re-setting an existing key does not move it), walked front to back.
**Key reuse**: the idempotency key is minted by the caller at tap time (`nextIdempotencyKey()`,
outside the queue) and stored verbatim in the entry; `replay` passes that exact key to `apply`,
never minting a new one. **Failure**: a rejected `apply` call leaves its entry queued (the "Queued"
tag stays visible) but does not stop the walk — one bad entry must not silently strand every entry
after it. A confirmed entry is deleted only if it is still the *same* entry object the replay
started with, so a fresh tap that re-queues the row mid-replay (a new key) is never clobbered by
the older, in-flight replay call for that same row (proven by a dedicated test).

## 4. Deviations and judgment calls

1. **The loop bar never appears for a row that arrives already `done`.** The fixture seeds olive
   oil as already checked off by Dean (matching the static prototype). The prototype's own
   screenshot shows a loop bar for it; this build does not, deliberately — the loop bar is tied to
   *this session's own* check-off action (`activeLoopRowId` state), not to a row's `status` field
   at load time. Rationale: the ticket's prose ("after a check-off the loop bar appears") reads as
   session-scoped, and re-prompting to add something that was already both bought and checked off
   before the session started did not seem like the intended behavior. Flagged as a judgment call,
   not silently decided — if the architect wants a pre-done row to prompt on first render too, that
   is a small, contained change to add.
2. **`menuOriginText`'s "none on hand" rule applies uniformly, including to granola.** The static
   prototype shows granola's zero-stock menu row as bare "yogurt parfait" (no "· none on hand"),
   while broccoli's otherwise-identical zero-stock case does show it. Nothing in the DTO
   distinguishes the two cases (both have `haveMicros: "0"` and a non-null `recipeName`), so
   inventing a per-row exception with no DTO-visible trigger would be exactly the kind of
   undocumented special case rule 3/4 forbids. This build applies form 2 ("{recipe} · none on
   hand") to every zero-stock, recipe-named menu row, including granola — a deliberate, documented
   deviation from the prototype's pixel-exact copy for that one row, not an oversight.
3. **`row-olive-oil`'s `unit` is `"each"`, not the real item's `"bottle"`.** `bottle` is not a
   domain-registry unit at all (`lookupUnit("bottle")` fails), which would break the gap-drift
   test's `neededQuantity` call. Safe only because Add is never offered for a pre-done row (per
   judgment call 1 above) — flagged in `fixture-shopping-list.ts`'s doc comment as something that
   must change (to `"bottle"` plus a registry follow-up, or drop the `itemId`) if a later ticket
   makes Add reachable for a pre-done row.
4. **S9's prefill count is whole-units only.** All three no-`itemId` rows (broccoli, garlic —
   Remove only, granola, paper towels) have whole-number `buyMicros`, so this was never exercised
   against a fraction; a non-integer prefill falls back to S9's own default of 1 rather than
   guessing a rounding rule (S9's stepper has never supported fractions, prefill or not — this is
   an existing S9 limitation, not something this ticket introduces).
5. **No Undo action on the plain check-off toast (online path).** The prototype's `toast(name+'
   checked off · Undo', true)` offers Undo; this build shows no toast at all for a successful
   online check-off (the checkmark turning green plus the buy count moving is the feedback),
   reserving toasts for the offline-queued case and failures. Tapping the check control again
   already un-checks a row, which is functionally equivalent to Undo; scoped down to reduce risk
   given the ticket's own reviewer-attack list is about the queue/idempotency, not toast copy.
6. **`removeShoppingSuggestion` is not restricted to AI-origin rows in the fixture client** (it
   deletes any row by id). The screen only ever calls it for an AI-suggestion row (the Remove
   button only renders there), so this is inert in practice, but it is a real fixture-level gap a
   reviewer should note: nothing stops a differently-written caller from removing a menu/member row
   through this same method.

## 5. What the reviewer should attack first

1. **`addCheckedOffToInventory`'s idempotency dedup** (`appliedShoppingWrites` keyed by
   idempotency key in `FixtureApiClient`) — this is the one path CLAUDE.md rule 10 actually bites:
   confirm a replayed/retried call with the *same* key truly returns the original result rather
   than a second `PURCHASE`, and that a *different* key for a genuinely new tap still appends
   (both covered by tests, but worth an adversarial second look — e.g. what happens if
   `checkOffShoppingRow`'s replay and a manual Add tap race for the same row).
2. **The offline queue's "keyed by row, latest wins" design** (§2) — specifically whether
   discarding a superseded key before it was ever sent is really always safe, and whether the
   "same entry object identity" guard against a stale in-flight replay clobbering a fresh re-queue
   is doing what it claims (there is a dedicated test for it, but it is subtle).
3. **Judgment calls 1 and 2 in §4** — these are places this build differs from the literal
   prototype/ticket text on purpose; the reviewer may weigh the tradeoff differently.
4. **The dev offline toggle's shape** (`hasDevOfflineToggle`, not part of `ApiClient`) — a
   structural choice (feature-detection rather than a port method every client must implement)
   that a reviewer might prefer done differently (e.g. a `ConnectivityPort` the screen always
   receives, fixture-only behind an interface flag).

## 6. Escalations and proposed backlog entries

- **`removeShoppingSuggestion` scope** (§4.6): consider tightening the real (future, M7) endpoint's
  semantics to reject removal of a non-`ai`-origin row server-side, so the fixture's current
  permissiveness does not quietly become the real contract by default.
- **Pre-done-row loop bar** (§4.1): a product/design question, not an engineering one — should
  reopening the app to a row someone else already checked off and added ever re-prompt "add it to
  the pantry?" This worker's reading is no; flagged for the architect/PO if that reading is wrong.
- **`bottle` as an unsupported unit** (§4.3, restates M1-T3's own accepted follow-up: "fl-oz
  disambiguation guard if fluid ounces ever needed") — olive oil's real inventory unit is `bottle`,
  which the domain registry has never supported. This has been quietly fine because nothing before
  this ticket needed to run domain gap math against it; M3-T5 is the first ticket that would break
  if Add ever needed to write against it. Worth a registry decision before any ticket makes that
  path reachable.
