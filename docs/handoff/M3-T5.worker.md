## 2. Queue design

`ShoppingCheckOffQueue` (`src/shopping/queue.ts`) is a plain `Map<rowId, entry>`, no React, no
`ApiClient`; the screen decides whether to enqueue (reading `isOffline()`, or whether the row
already has a pending entry, at tap time) and hands the queue an `apply` function. As of round 1 it
is held in a module singleton (`src/shopping/shared-queue.ts`), not a `useRef`, so it survives the
screen unmounting on a route change. **Enqueue**: keyed by row, so a second tap on the same row
(offline, or online with a still-pending entry) *replaces* the pending entry rather than appending a
second one: the row's current desired state is one boolean, and the superseded key was never sent
anywhere, so nothing server-visible is lost by discarding it. **Replay order**: `Map` iteration
order, which is a row's *first*-queued position (re-setting an existing key does not move it),
walked front to back. **Key reuse**: the idempotency key is minted by the caller at tap time
(`nextIdempotencyKey()`, outside the queue) and stored verbatim in the entry; `replay` passes that
exact key to `apply`, never minting a new one. **Failure**: a rejected `apply` call leaves its entry
queued (the "Queued" tag stays visible) but does not stop the walk, one bad entry must not silently
strand every entry after it. A confirmed entry is deleted only if it is still the *same* entry
object the replay started with, so a fresh tap that re-queues the row mid-replay (a new key) is
never clobbered by the older, in-flight replay call for that same row. **One walk at a time (round
1, F4)**: two overlapping `replay` calls (e.g. two connectivity flaps close together) share one
in-flight promise rather than each starting an independent walk, so an entry is never delivered to
`apply` twice from that alone. **Applying to a freshly loaded list (round 1, F1)**:
`app/shopping.tsx`'s `applyQueuedOverlay` reapplies every still-pending entry's desired state onto
whatever `getShoppingList` returns, on every load, including after a remount, since a queued entry
never actually reached the port and the underlying list would otherwise show the row's pre-check-off
state with no explanation.

## 4. Deviations and judgment calls

Round 1 ruled on all three of round 0's judgment calls; each is restated here with that ruling.

1. **The loop bar never appears for a row that arrives already `done`** (the seeded "Olive oil,
   added and checked off by Dean" row). Tied to *this session's own* check-off action
   (`activeLoopRowId` state), not to a row's `status` field at load time. **Ruling: accepted.**
2. **`menuOriginText`'s "none on hand" rule applies uniformly, including to granola**, even though
   the static prototype shows granola's zero-stock row bare ("yogurt parfait", no "none on hand")
   while broccoli's otherwise-identical case does show it. Nothing in the DTO distinguishes the two
   rows, so this build applies one deterministic rule to both rather than inventing a hidden
   per-row exception. **Ruling: accepted as a recorded deviation; a prototype-style bare form would
   need its own DTO field at M7, not client-side logic guessing which rows get it.**
3. **No Undo action on the plain check-off toast (online path).** The prototype offers one; this
   build shows no toast at all for a successful online check-off (the checkmark turning green plus
   the buy count moving is the feedback). Tapping the check control again already un-checks a row,
   functionally equivalent to Undo. **Ruling: accepted.**
4. **`removeShoppingSuggestion` is not restricted to AI-origin rows in the fixture client** (it
   deletes any row by id). The screen only ever calls it for an AI-suggestion row (the Remove
   button only renders there), so this is inert in practice, but it is a real fixture-level gap.
   Carried into §6 for the M7 endpoint's own semantics.

Two round-0 deviations no longer exist, both closed by round-1 fixes rather than left as accepted
tradeoffs:

- `row-olive-oil`'s `"bottle"` unit mismatch is gone: F7 changed the row to `itemId: null`,
  `haveMicros: "0"`, `buyMicros: "1000000"` (see `fixture-shopping-list.ts`'s doc comment for the
  reframing: `buyMicros` is a fixed fact of the row for the session, the same convention every
  other row already followed, not something that should have been zeroed out for a "done" row).
- S9's prefill amount is no longer integer-truncated before being handed to the stepper (F9): the
  screen now always passes the exact decimal text, and S9's own `prefillCount` only ever
  *recognises* a whole value (`/^\d+$/`), never rounds one, proven against a case
  (`amount: "2.5"`) that a naive `Number.parseInt` would have silently turned into a
  wrong-but-whole-looking `2`, not just against a case that happened to fall back to the default
  anyway.

## 5. What the reviewer should attack first

1. **`addCheckedOffToInventory`'s dedup is now keyed by rowId, not idempotency key** (round 1, F3):
   confirm that "the same row's check-off, added twice regardless of key" is really the right
   business rule (this worker's reasoning: `buyMicros` is a fixed fact of the row for the session,
   so a second Add for the same row is always a real duplicate, never a legitimately-different
   purchase, even across an uncheck/re-check cycle) versus some narrower "only within one
   still-`done` window" rule the reviewer might prefer.
2. **F2's fix (route a new tap through the queue whenever the row already has a pending entry,
   even while online)**: confirm this cannot itself introduce a different race, e.g. two very close
   taps on the same row while a pending entry already exists, both entering the "has pending entry"
   branch before either's `enqueue`/`replay` call lands.
3. **F1's overlay (`applyQueuedOverlay`)**: it reapplies a queue entry's `checked`/initials onto
   whatever the fresh fetch returns, unconditionally. If a *different* member's check-off arrived
   from the server in between (a real multi-member household, not this fixture's single-session
   model), this worker's overlay would still show *this* device's stale queued intent on top of it;
   worth checking whether that is acceptable for M7 or needs a resolution rule.
4. **The dev offline toggle's shape** (`hasDevOfflineToggle` + `__DEV__`, not part of `ApiClient`):
   a structural choice (feature-detection rather than a port method every client must implement)
   that a reviewer might prefer done differently (e.g. a `ConnectivityPort` the screen always
   receives, fixture-only behind an interface flag).
