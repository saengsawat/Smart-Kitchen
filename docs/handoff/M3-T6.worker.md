# M3-T6 worker report: profile and household (S12)

Branch `m3-t6-profile`, final commit `04f1cec45df4a75831a671418814dae9ad0e6ed2`.

## 1. What was built

**(a) Route and entry.** `app/profile.tsx` (new), reachable from the Home header's
account affordance (`src/screens/HomeScreen.tsx`, a small tap target added to
both of Home's existing states without touching either). Back returns to the
previous screen when there is one, else falls back to `/` (the same fallback
`app/add.tsx`'s hub already uses), which the onboarding gate then routes on.

I did not add a second literal entry point on S1: the prototype's own
`avatarTap()` is a ternary between S1 and S12 driven by a dev-only "new user"
toggle, not a button that lives on S1's own markup. In this app the onboarding
gate (`app/_layout.tsx`) already guarantees nobody reaches Home (and so this
screen's only real entry point) unless their household and allergy gate are
already satisfied, so there is no separate "returning user" affordance on S1
to build. Flagged in §5 as a judgment call.

**(b) Identity card.** Fixture path: the owner member's full name (D-022's one
identity is always modelled as the household's owner, in every fixture
construction path), a new `FIXTURE_IDENTITY_EMAIL` constant
(`dean@example.com`, the prototype's own S1 toast string), role, household
name. HTTP path: `HttpApiClient` gained `getCallerSummary()` (initials plus
role, read off the wire's `isCaller` before `householdSyncInputFromSummary`
drops it) so the card shows initials, role and household name, never an email
or a made-up name.

**(c) Household members.** One row per member from `household.members`
(fixture: full names; HTTP: initials, already true of `member.displayName`
since M3-T4d's own mapping). Summary line
(`src/profile/summary.ts#memberAllergySummary`): `"No known allergies · edit"`
or `"{allergen}, {allergen} · severe · edit"` (severe only when any
restriction is severe; allergen labels from `MAJOR_ALLERGEN_LABELS_DTO` or the
member's own wording; never "safe"). Tapping a row expands
`MemberAllergySection` (extracted from `app/onboarding/allergies.tsx`, see
below) inline, scoped to that one member; Save calls
`saveMemberRestrictions(memberId, ...)` for that member alone (closing the
M3-T2 simplification) and updates local state optimistically; the S2 gate
(`isMemberComplete`) still applies, with the exact inline message; Cancel
discards the draft without saving.

**(d) Add a member.** Fixture: a static, non-interactive row, "Add a member" /
"share the join code CHEN-482" (`FIXTURE_JOIN_CODE`), matching the prototype.
HTTP, owner (`getCallerSummary().role === "owner"`): an "Invite" link opens an
inline confirm sheet with the exact copy the ticket gives and **Get new
code**/**Cancel**; confirming calls the new `HouseholdCallerActions.
rotateJoinCode()` (`POST /v1/households/me/join-code`, feature-detected the
same way `hasDevOfflineToggle` is) and shows the result once, "Your join
code: {code}. Save it to invite others." HTTP, member: "Ask the household
owner for the join code." and no Invite link (client-side refusal; a 403
`NOT_OWNER` that reaches the client anyway renders its own exact §8 string,
never the server's). Invite by link/email: two rows carrying the §6
fast-follow badge that only explain themselves on tap (`useToast()`), doing
nothing else.

**(e) Account.** Sign out: a new `ApiClient.signOut()` (both implementations)
clears every household/restriction/preference state the client holds
(`FixtureApiClient` back to `newUser()`'s exact starting point; `HttpApiClient`
the same way through its delegate, plus its own cached caller identity), then
the screen navigates to `/onboarding/account` directly. A one-line note on S1
and in the README say sign-out is local until the auth vendor lands (D-022).

**(f) M3-T2 follow-ups.** `onSubmitEditing` on the custom allergen input;
`firstName()` moved to `allergyGate.ts` and fixed to split on `/\s+/` after
trimming (a single-token name already worked; leading/repeated whitespace
did not); S2's `MemberAllergySection` extracted to
`src/onboarding/MemberAllergySection.tsx` and reused by both screens, not
copied (a new `showHeading` prop lets S12 skip the redundant name heading its
own row already shows).

**(g) Preferences.** Untouched, exactly per the ticket: S12 has no preferences
UI; D-024 row 15 (unit preference) is not built.

## 5. Deviations and judgment calls

- **No literal S1 entry point.** See §1(a). The ticket's "and from S1's
  returning user path where the prototype links it" reads, on inspection of
  the prototype's own JS, as the *same* `avatarTap()` function the Home
  header already calls (a dev-toggle ternary between S1 and S12, not a
  second button drawn on S1). Since this app's gate makes "reachable Home
  with an incomplete household" impossible, I judged there is nothing further
  to build here and did not invent a new S1 affordance. Flagged for the
  reviewer to confirm or correct.
- **Household name in the identity card, not "Chen household".** The
  prototype's sample caption reads "Chen household" (a stylized short form),
  but the actual `HouseholdDto.name` field for the same fixture is
  "The Chens". I rendered the real field (works for any household name) over
  the prototype's hardcoded sample text, since the sample is clearly a
  stand-in for whatever the real name is, not itself a fixed requirement.
- **Per-member edit is an inline expansion, not a second full-screen route.**
  The prototype's row tap navigates to a full `#scr-allergies`; the file
  scope names only `app/profile.tsx` (no nested route file), and the M3-T4a
  test-infrastructure note already flags that `Modal` is unsupported under
  this app's vitest stand-in. An inline expand/collapse under the tapped row
  reuses the same `MemberAllergySection` without either problem.
- **A rotate single-flight ref guard**, mirroring the M3-T4d review's F11
  finding almost exactly (state-only `disabled={...}` takes effect only
  after a re-render, so two same-frame taps both fire): rotation has no
  idempotency key by design (same reasoning as create/join household), so a
  genuine double call could rotate twice and leave the screen showing the
  now-already-stale first response. I did not add the same ref to per-member
  Save: `saveMemberRestrictions` never touches the network in this ticket's
  scope (restrictions are entirely client-local until M2-T4), so a same-frame
  double-fire there has no observable side effect beyond writing the same
  value twice.
- **Home's account button shows a plain circle, not initials.** Matching the
  prototype exactly would need an identity read this placeholder does not
  otherwise make; adding one felt like scope creep into the held S3
  dashboard (OQ-D9), which will already hold that state. Flagged as a
  deferred, low-risk gap, not a missing requirement. The tap itself works.

## 6. What the reviewer should attack first

1. **The owner/member fork.** `isOwner` (client) and the `NOT_OWNER` mapping
   (server, defence in depth) are the two places a member could reach the
   owner-only action; try to reach `rotateJoinCode()` as `fixture.maya.chen`
   through the UI, not just the client method directly.
2. **Per-member save actually stays scoped.** `handleSaveMember` closes over
   `editingMemberId` before the async call; check a fast Cancel-then-tap on a
   different member cannot land the first member's draft on the second.
3. **Sign-out completeness.** Does anything survive it that shouldn't (the
   `rotatedCode`/`inviteConfirmOpen` local React state does not need to,
   since the whole screen unmounts on navigation, but the underlying
   client's household/caller state is the invariant that actually matters)?
4. **The `identityCard`'s fixture-owner assumption.** `household.members.find(
   (m) => m.role === "owner")` as "the caller" is airtight only because every
   fixture construction path models Dean as owner; if that ever changes,
   this silently shows the wrong person's identity with no error.
5. **The confirm-sheet's inline design versus the prototype's sheet.** A
   product/design call on whether an inline expand reads acceptably in place
   of an actual sheet.

## 10. Review fixes (round 1)

Reviewer verdict: PASS WITH FIXES (two majors, eight minors). All ten addressed
below, on this same branch. Ticket premise correction (the reviewer's own
note, recorded here as instructed): S2 already saved restrictions per member
before this ticket; the M3-T2 simplification this ticket closes is the shared
*preferences* block, which Objective (g) correctly keeps shared. The worker
report's §1(c) sentence "closing the M3-T2 simplification that saved one
shared set to every member" overstates this; the real change this ticket
makes is giving S12 a UI to edit a member's already-per-member restrictions
individually, not fixing a shared-restrictions bug that never existed.

**F1 [major] the save target was unpinned.** `profile-screen.test.ts`'s
"editing Maya's allergies changes only Maya's row" now spies on
`saveMemberRestrictions`, asserts exactly one call naming `member-maya`, then
re-reads `getOnboardingState()` from the port itself and asserts Dean's
`restrictions`/`noneConfirmed` are byte-identical to before the edit. A new
HTTP-path test in `profile-screen-http.test.ts` ("editing MC's (Maya)
allergies... review round 1, F1") does the same against `mem-maya`/`mem-dean`.
Both would have caught the id-swap mutation the review described; neither
existed before.

**F2 [major] HTTP sign-out plus Create household made a second household with
no way back.** `app/onboarding/account.tsx`'s `handleContinueWithEmail` now
reads `apiClient.getOnboardingState()` after signing in and calls
`router.replace("/")` for an already-affiliated caller, never showing the
create/join cards; a rejected read fails closed with the §8 read fallback
(new `affiliationCheckError` state), same convention as every other read in
this app. Reuses the existing `requestInFlight` ref so this check, create and
join can never race each other. New tests in `account-screen-http.test.ts`:
the already-affiliated redirect, and the failed-read fallback (both check

**F3 [minor] `HttpApiClient.signOut()` did not clear the inventory cache.**
Now also sets `cachedItems = null` and calls `setStale(false)`. New test in
`client.test.ts`: after sign-out, `isInventoryStale()` reads false immediately
and a failed `getInventoryItems()` call rejects rather than serving the
previous household's cached rows.

**F4 [minor] `summary.ts` had no unit tests, and a real bug behind that gap.**
New `summary.test.ts` (13 cases) pins every form: none confirmed, one
standard-severity restriction (no "severe" word), two severe restrictions,

is a real predicate the review's "force it to `true`" mutant would now fail),

implemented: a member with zero restrictions and `noneConfirmed` still
`false` (the gate not yet answered) now renders **"Allergies not set yet ·
edit"**, never "No known allergies" (that phrase is reserved for the explicit
declaration). This is a new string for copy-deck §7 S12 states, added to §9's
list of verbatim strings by reference here since it was proposed after §9 was
first written.

**F5 [minor] the live rotate tests permanently revoked the seeded CHEN-482.**
Rewritten: `client.live.test.ts`'s rotation test now creates its own
throwaway household under `fixture.new.user` (the same persona and pattern

proves the old one is dead and the new one works (including
