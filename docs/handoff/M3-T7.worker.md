# M3-T7 worker report: typed quantities (S5 amount field, S8 editable package size)

Branch `m3-t7-typed-quantities`, from main at 88881e1. Worker: Sonnet. Objective (a) and (b) only.

## What changed

- `apps/mobile/src/inventory/quantity.ts`: added `parseTypedAmount(text)` (plain non-negative decimal text, at most 6 decimals, at most `MAX_TYPED_QUANTITY_MICROS`, else `null`), `microsToTypedText(micros)`, and `MAX_TYPED_QUANTITY_MICROS` (100,000,000 units, the domain's `MAX_QUANTITY_MICROS` restated because the client cannot import the domain package; a test pins it). The digits become micros text and go through `parseMicros`. No `Number`, `parseFloat` or `toFixed` anywhere.
- `apps/mobile/app/inventory/[itemId].tsx` (S5): the draft amount is a decimal-pad `TextInput` between the stepper buttons. Typing replaces the draft exactly. The stepper steps 0.25 from the typed value (clamped at 0 and the maximum). Unparsable text (including empty) shows the inline hint and disables Save, and `handleSaveCorrection` also refuses. From unparsable text the stepper steps from the last usable amount and replaces the text. Count units accept decimals (no whole-number rule added). `formatDraftAmount` removed (replaced by `microsToTypedText`).
- `apps/mobile/app/add/scan.tsx` (S8 sheet only): the package size line is a `Pressable` (min height 44) that opens a decimal-pad field showing the record's quantity. Typed state is `string | null`: `null` (never touched) and `""` (cleared) both mean the record's own size and tier stand, so merely opening the field does not flip the chip. A usable typed size (above zero) becomes the size with tier KNOWN_FACT and source `user-entry`, the chip beside it reads "✓ Fact", and the "{count} packages of {qty} {unit}" text and the Add amount use it. The unit is the record's and is not editable. An unusable entry keeps the editor open, shows the hint and disables Add (and `handleAdd` refuses). Changing the typed size discards a held idempotency key, as count and location do. The record itself is never changed.
- Tests: `quantity.test.ts` (validator table, property tests), new `item-detail-typed-quantity.test.ts` (S5 on the fixture client), `scan-screen.test.ts` (S8 block). Existing S5 and S8 suites unchanged.

## Deviations and findings (please read)

1. **No lot label exists on the wire.** The ticket says a typed size becomes "the lot's label and size". `CreateItemRequestDto` has no label field, and the created lot's `label` is `null` (seen over HTTP). I did not touch contracts (out of scope). What I did: the visible size line carries "500 g", and the typed size drives the amount (count x size) and `quantityProvenance` tier/source. Nothing stores "500 g" as a label. If a label on the lot is wanted, it needs a contracts and API ticket.
2. **The server overrides the source.** The client sends `source: "user-entry"` but the API records its own stable id (`barcode-scan`, per the contracts comment on `CreateItemRequestDto`), seen over HTTP. Only the fixture client stores `user-entry`. The tier (KNOWN_FACT) does land. So after a reload the tier is right but the source text does not say the person typed it. Needs an owner call if that matters (an API field or a new source id).
3. **Unsupported package units (qt, pt, gal, etc.).** The ticket asks the "{count} packages of {qty} {unit}" text to use the typed size, so the field is editable there too. But in that branch the item is recorded as N "each" and the size is never sent anywhere, so the typed size and its "✓ Fact" chip exist only on the sheet. That could read as more than was saved. I followed the ticket; consider limiting the edit to supported units or recording the size somewhere (ties to finding 1).
4. **No yogurt in the fixture corpus.** The fixture products are tahini, eggs and chicken. The S8 tests use a hand-built OFF-style yogurt (125 g Estimated) shaped like Andy's corn case.
5. **Eggs fixture is 8, not 9.** Typing 9.25 appends +1.25; typing 8.25 appends +0.25. Both are tested (header "9.25 of 12" and "8.25 of 12", since the fixture lot label is "carton of 12").
6. Correction type is `ADJUSTMENT` on the wire (existing behaviour); the ticket says "CORRECTION". Unchanged.
7. A comma is rejected (not read as a decimal separator) because "1,500" is ambiguous. Phones with comma-decimal locales get the hint. Proposed follow-up if Andy wants locale handling.
8. Zero is an unusable S8 size (Add disabled); on S5 zero is allowed (setting an item to 0 is a valid correction).
9. The "reset typed size on a new scan" line in `handleCode` is defensive: the confirm sheet has no in-place rescan today, so there is no UI path to test it. No test for it.
10. `fast-check` is not in the mobile package (rule 11), so the property tests use a seeded bigint LCG (2000 cases, 0 to 6 decimals), no `Math.random`.

## Review fixes (round 3)

Test-only. The screen ban list in `src/lint-rules/no-float-in-quantity-math.test.ts` is stricter: (1) `Math` is allow-listed by name on the two screens: only `Math.min(` and `Math.max(`, and `Math.round(` only as the single expression `Math.round(windowHeight * CAMERA_PANEL_MAX_FRACTION)`; any other `Math.*` call or bare `Math` fails; (2) a leading-plus conversion (a `+` with nothing in front of it before an identifier or `(`) is banned; (3) the plain scale literals `1e6`, `1_000_000` and `1000000` are banned (bigint `n` forms stay allowed). The in-test mutation check now includes `BigInt(Math.round(+draftText * 1e6)).toString()` and `String(Math.round(+microsToAmountText(size.micros) * 1e6) / 1e6)`, plus a check that what the screens legitimately use is not flagged. Both screens pass the stricter guard unchanged.
