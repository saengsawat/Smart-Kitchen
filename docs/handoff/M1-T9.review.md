## Verdict summary
The classifier and wrapper are correct on the two things that matter for a rule-23 ticket: **a business conflict is never retried, and a retry can never double-apply.** Verified on a real Postgres 17.10 throwaway cluster with real driver error objects (not hand-built), including a case the worker had not tested — a `40001` surfacing at `COMMIT` from a `DEFERRABLE INITIALLY DEFERRED` trigger — and 8-way real concurrency on both the locked and unlocked write paths. Every probe clean: contiguous sequences, `inventory_reconciliation.ok = true`, exactly one row per idempotency key, no pool leak, `SET LOCAL ROLE`/`app.household_id` re-established on every retried attempt. The worker's mutation table reproduced exactly (M1 5, M2 5, M3 0, M4 4, M5 6, M6 20) and its M3 "equivalent mutant" claim is correct (static proof + 13-configuration behavioural sweep, byte-identical). One fix was required: the `assumeRole` pass-through — the thing that makes RLS apply to ledger writes — had zero test coverage (deleting it killed 0/37 tests).

## Findings
- **F1 — MEDIUM, required (fixed):** `assumeRole` pass-through untested (mutation M8 survived). Behaviour was correct (probe P2: `current_user = sk_app` and household context on both attempts, distinct `txid_current()`), but an authorization boundary went unpinned. **Fix:** new DB test (g) asserting `current_user`, `app.household_id` and distinct txids on BOTH attempts after a real `40001`. Re-review: M8 now killed; a subtler mutant applying the role on attempt 1 only (M8b) also killed; passing `null` household on retries (M11) killed 2.
- **F2 — LOW (fixed as code):** an injected `sleep` that rejects replaced the ledger error entirely. Now the ledger error is attached as `cause` (identity), pre-existing `cause` not clobbered, non-`Error` rejections pass through.
- **F3 — LOW, backlog:** `delay()` return unvalidated (`-500`, `NaN` pass to `sleep`); benign with the default sleep; caller-owned. Asymmetric with the strict `maxAttempts` validation.
- **F4 — HIGH against the codebase, PRE-EXISTING, NOT this ticket (→ ticket M1-T11):** `appendTransactionToDb` catches the idempotency-key `23505` **without a `SAVEPOINT`** and returns `ok({status:"rejected"})`; Postgres is already in ABORTED state; `withHouseholdTransaction` then issues `COMMIT`, which Postgres answers with the `ROLLBACK` command tag **and no error**. Repro (P9): one `fn`, a clean append then a second append reusing a burnt key → returns `{good:"appended", bad:"rejected"}` as success, and the item's ledger has **0 rows**. Silent loss of work reported as `appended`. The retry helper is structurally blind to it (`fn` "succeeded"). Not reachable in production today (no production callers; only tests and future M2 handlers). Fix belongs in `repository.ts` (`SAVEPOINT`/`ROLLBACK TO SAVEPOINT` around the insert block) and/or `session.ts` (fail loudly when `COMMIT` returns `ROLLBACK`).
- **F5 — INFO:** default `maxAttempts: 3` survives only 3-way contention on an *unlocked* writer (writer *k* needed *k* attempts in P6); the locked production path needed 1 attempt each at 8-way (P5). Record for M9 backoff tuning.
- **F6 — nit (fixed):** a discarded `recordingSleep().calls` array now asserted.
- **F7 — doc (fixed):** header now states `fn` must re-derive DB-read values each attempt, not close over attempt 1's read.
- **F8 — LOW, backlog (from re-review):** the F2 `cause` assignment can itself throw on a frozen/non-extensible rejection (`TypeError: Cannot add property cause`), losing both errors; one-line `try/catch`. Also mutating a caller's shared abort error is a smell.
- **F9 — LOW, backlog (from re-review):** the F2 code path has no test — mutation M12 (delete `throw sleepError`, swallowing the rejection and continuing the loop) kills 0/38. One fake-pool test (reviewer's R1 is a drop-in).
