## Verdict summary
The defect is closed. The reviewer reproduced the original F4 loss on both trees on a real Postgres 17.10 cluster: pre-fix, a clean append followed by a burnt-key append in one transaction returned `{good:"appended", bad:"rejected"}` as a **success with 0 durable rows**; post-fix, same verdict with **1 durable row**, `inventory_reconciliation.ok = true`. Ten further loss-path scenarios (order reversed, double rejection, clamp-key collision, swallowed real `23514`/`23505`, caller-owned savepoints, deferred trigger at COMMIT, savepoint nesting incl. same name, genuine unlocked race, retry with a rejection on every attempt, session-state hygiene on the new un-poisoned release path) found **no remaining path by which work reported `appended` can be lost, and none by which a `rejected` turns out committed**. `retry.ts` byte-identical to main; no existing test edited; no dependency change; the worker's entire mutation table and both gate counts reproduced to the digit.

## Findings
- **F1 — MEDIUM, required (fixed as a test):** `session.ts`'s aborted-at-COMMIT short-circuit is deliberately keyed on a local flag, not `instanceof`, so a `TransactionAbortedAtCommitError` thrown *by `fn`* still takes the real ROLLBACK path. Nothing tested it: mutation M8 (`instanceof`) survived all 785 tests. Hazard probed on a `max: 1` pool: under the mutant the **next borrower** of the connection sees `in-transaction`, `current_user = sk_app`, `app.household_id` = the previous household — an open uncommitted transaction plus a tenancy leak. **Fix:** new DB-gated test in `session.test.ts` (same physical connection via a second `max: 1` pool): error propagates by identity, insert not durable, `pg_current_xact_id_if_assigned() IS NULL`, role and household context cleared. Re-review: M8 now killed (1 failed / 785 passed), by exactly that test with the hazard diagnostic; not tautological (the transaction-state assertion is load-bearing).
- **F2 — LOW, backlog:** the COMMIT tag check is fail-open (throws only on the exact string `ROLLBACK`). Fail-closed `!== "COMMIT"` is behaviourally identical on real Postgres and breaks only `retry.test.ts`'s fake-pool stubs (no `command` field) — outside this ticket's scope.
- **F3 — LOW (fixed as a comment):** the non-idempotency rethrow branch intentionally leaves the savepoint open (transaction is aborted; `RELEASE` would itself fail `25P02`; whole-transaction rollback discards it). Verified at psql.
- **F4 — INFO:** `TransactionAbortedAtCommitError` is non-retryable under `isRetryableLedgerError`; an `fn` that swallows a genuine `40001` is now a hard failure instead of a retry. Loud over silent — correct; no `fn` swallows today.
- **F5 — INFO:** savepoint-hygiene tests assert `3B001` against the literal name, so the *combined* mutant "rename constant + drop success-path `RELEASE`" survives; neither half survives alone.
