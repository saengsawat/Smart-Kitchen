# M2-T3 worker report: household endpoints and item creation over the ledger

Branch `m2-t3-households`, cut from `main` at `c6d8ff6`. Implementation model: Opus-class (as the
ticket says). No architecture conflict found. Three files outside the listed file scope were

## 1. What was built

### Routes (all in `apps/api/src/http/`)

| Route | Declaration | What it does |
| --- | --- | --- |
| `POST /v1/households` | `userRoute` (new) | Trims the name, 1 to 60 characters (code points), no control characters, else 400 `BAD_REQUEST` with its own sentence. Mints the household id and membership id server side (UUIDv7), creates household + owner membership + first join code in one transaction inside the new household's own RLS context. 201 with `{ household: HouseholdSummaryDto, joinCode: { code, issuedAt } }`. The plaintext code is in this response and nowhere else. Audit line `household-created`. |
| `POST /v1/households/join` | `userRoute`, rate limited | Body `{ code }` only. Charges the per-user limiter first (10 per 10 minutes, every attempt counts, reserved synchronously), then normalises (trim, upper-case), hashes and redeems through `app_redeem_join_code`. Unknown, rotated, malformed: one 404 `JOIN_CODE_INVALID` with one message. Already a member: 200, `alreadyMember: true`, no second row, no audit line. New member: 200, audit line `joined-by-code`. 429 `RATE_LIMITED` beyond the limit, even for the right code. |
| `GET /v1/households/me` | `householdRoute` | The session's household with members as `HouseholdMemberSummaryDto[]`: `memberId` (the membership id, not a user id), `displayInitials`, `role`, `isCaller`. No names, no email, no `restrictions`, no `noneConfirmed`. |
| `GET /v1/households/mine` | `userRoute` | Every household the caller belongs to, most recently joined first, `current: true` on the one requests run as. Empty list for a household-less caller. The set is the identity port's `caller.memberships`; the database only supplies names. |
| `POST /v1/households/me/join-code` | `ownerRoute` (new) | Owner only (a member gets 403 `NOT_OWNER`, from the declaration and again from the handler). Revokes the live code and issues a new one under a transaction advisory lock, so concurrent rotations leave exactly one live code. 200 with the new code. Audit line `join-code-rotated`. |
| `POST /v1/inventory/items` | `householdRoute` | `CreateItemRequestDto`. One transaction: item + one lot + first ledger row (`PURCHASE` for `BARCODE`, `INITIAL_STOCK` for `MANUAL`). 201 on create, 200 on replay, 409 `CONFLICT`/`IDEMPOTENCY_KEY_CONFLICT` on a changed payload under a used key. Returns `InventoryItemSummaryDto`. |

Authorization (`authorization.ts`) now resolves a `Caller` (user plus every membership) from the
port and derives the session from it. New declaration kinds: `userRoute(reason)` (signed in,
household optional, must say why) and `ownerRoute()` (owner only, refusal code `NOT_OWNER`). A
signed-in caller with no household gets 403 on every household route (new denial reason
`no-household`).

### Item creation (`apps/api/src/db/inventory/create-service.ts`)

- `planCreation` validates everything before any SQL: client key (same rule as M2-T2, restated),
  display name (trimmed, 1 to 120, printable), unit (must be in `CREATE_ITEM_UNITS_DTO` and resolve
  in the domain registry), amount (exact decimal text to micros, positive), quantity tier (Known
  Fact or Estimated; AI interpretation refused), quantity `confidence`/`recordedAt` must be null,
  `productRef` required for `BARCODE` and refused for `MANUAL`, best-by date and best-by provenance
  come together or not at all, best-by must parse.
- Ledger key is `<clientKey>/lot/0`, the planner namespace M2-T2 uses, so the household-scoped
  unique index is the backstop for both endpoints and undo finds the row with the existing rule.
- Replay is decided by comparing the stored row, item and lot with the request field by field
  (type, micros, unit, tier, source, actor, name, location, productRef, expiry, expiry tier). All
  equal: replay. Anything different, including a key an M2-T2 write already used: 409.
- Concurrent creates under one key serialise on `pg_advisory_xact_lock(household, key)`: one 201,
  the rest replays (tested with five in parallel).
- The item, lot and row go through `insertInventoryItem` and `appendTransactionToDb`; a rejection
  throws and rolls back the whole transaction, so there is never an item without its row.
- Row provenance: tier from the request, source is the server's `barcode-scan` or `manual-entry`.
  Lot `expiry_tier` is the request's `bestByProvenance.tier`, passed through (any of the three);
  no best-by means no tier. `acquiredAt` and the row's `occurredAt` are the server clock, because
  the request carries no `occurredAt`.

## 2. Migration 0008 up and down

Approved for local and CI databases only (rule 16). Explained in the file header too.

**Up.** Creates `household_join_codes` with `code_hash text PRIMARY KEY CHECK (~ '^[0-9a-f]{64}$')`
(unique across all households and all codes, revoked included, and the plaintext shape cannot be
stored), `household_id` FK to `households` ON DELETE CASCADE, `created_by` FK to `users`,
`created_at`, `revoked_at` with `revoked_at >= created_at`. Partial unique index
`household_join_codes_one_live (household_id) WHERE revoked_at IS NULL`. BEFORE UPDATE trigger
`household_join_codes_revoke_only`: an update must set `revoked_at` from null to a value and touch
nothing else. RLS policy `household_join_codes_current` (same shape as 0006). Grants to `sk_app`:
SELECT, INSERT, UPDATE (`revoked_at`) only; no DELETE. Three SECURITY DEFINER functions with
`search_path` pinned, EXECUTE revoked from PUBLIC and granted to `sk_app`:

- `app_create_household(household, name, owner, membership)`: refuses (42501) unless the
  transaction's `app.household_id` is the new id; plain INSERT into `households` (an existing id
  is a unique violation, never a join) and one owner membership.
- `app_redeem_join_code(code_hash, user, membership) -> (household_id, joined, member_role)`: finds
  a live code `FOR SHARE`, inserts one `member` membership `ON CONFLICT DO NOTHING`, returns the
  caller's role there. Unknown or revoked: no row.
- `app_user_memberships(user) -> (household_id, role, joined_at, household_name)`: newest first.

`sk_app` still has no INSERT on `households` or `household_memberships`; these functions are the
only runtime path to a membership.

**Down.** Revokes and drops the three functions, revokes the table grants, drops the policy, the
trigger and its function, and the table. Every issued code is lost. Households and memberships
created through the functions remain (they are ordinary 0002 rows). Re-running up gives an empty
code table: existing households have no live code until an owner rotates or the dev seed runs.

Both directions are exercised: `db/households/households.db.test.ts` rolls back exactly 0008 and
re-applies it, and the existing `migrations.test.ts` full round trip now includes 0008.

## 3. Security notes

- **Code hashing.** HMAC-SHA-256 of the normalised code under `SK_JOIN_CODE_PEPPER` (at least 32
  characters), lowercase hex. Plain SHA-256 was rejected: the code space is about 1.7e8
  (24^4 x 8^3), which enumerates in seconds, so a leaked table would be a leaked set of live codes.
  In fixture environments an unset pepper falls back to a public constant
  (`DEVELOPMENT_JOIN_CODE_PEPPER`), the same trust level as the fixture tokens; elsewhere the API
  refuses to start. Node's built-in `crypto`, no custom crypto, no new dependency.
- **Codes never logged.** No request body is ever logged (M2-T1). On top of that the redaction
  denylist gains exact keys `code`/`codes` and substrings `joincode`/`codehash`, and a shape scan
  replaces `XXXX-NNN` in any string with `[redacted-join-code]`. The HTTP suite collects every log
  line of the run and asserts no issued code (either case) and no code hash appears. Audit lines
  carry `actorUserId`, `householdId`, `role`, `change`, `correlationId`, never a name.
- **Rate limiting.** Per user, 10 attempts per 10 minutes, every attempt counted, slot reserved
  before the code is looked at. A 25-request concurrent burst yields exactly ten 404s and fifteen
  429s. In-memory and per process (see escalations).
- **Enumeration resistance.** One status, one code, one message for unknown, revoked and malformed
  codes (tested for byte-equal bodies apart from the correlation id). The 429 comes before any
  lookup, so the eleventh attempt says nothing about the code. Code hashes are unique across
  households, and a collision on issue is a silent redraw, so an issuer learns nothing about other
  households. A malformed code skips the database, so it answers slightly faster than a
  well-formed wrong one; that only reveals whether the input matched the public format.
- **RLS.** New table fails closed with no context (tested). A household cannot read, insert,
  revoke or delete another household's code rows, cannot un-revoke its own, cannot hold two live
  codes, cannot insert memberships or households directly, and cannot aim `app_create_household`
  at an existing household or run it outside the new household's context. The HTTP mutation test
  swaps in a tenant runner with no household context: `GET /me` finds nothing (404), rotation and
  item creation fail with nothing written.
- **Identity only from the port.** Every body schema is `additionalProperties: false` with
  `removeAdditional` off; bodies naming `householdId`, `userId`, `role`, `lotId`, `itemId` or
  `actorUserId` are 400 and write nothing (tested). `x-household-id` and `?householdId=` are
  ignored (tested on `/me` and `/mine`).

## 5. Deviations and judgment calls

1. **Files outside the listed scope.** (a) `apps/api/src/app.ts`: the composition root has to
   build the database-backed membership directory, the membership runner, the join-code hasher and
   the limiter, and pass them in; there is no way to wire new routes or a DB-backed port without
   it. Also moved the fixture-environment check (`chooseIdentityAdapter`) to the top so the
   production refusal still wins over a missing `DATABASE_URL`. (b)
   `apps/api/src/db/telemetry/view.test.ts`: it assumed 0007 is the last migration; it now rolls
   back two and expects `[0008, 0007]`. (c) `apps/api/src/db/inventory/tenancy.test.ts`: the "every
   household-scoped table has RLS" list gains `household_join_codes` (stronger, not weaker). Also
   `apps/api/src/http/tenancy.db.test.ts` (in scope) now expects four users.
2. **`HouseholdSummaryDto` instead of `HouseholdDto`/`MemberDto`.** The ticket says members as
   `MemberDto[]` with restrictions omitted, but `MemberDto.restrictions` and `noneConfirmed` are
   required and the mobile onboarding gate reads them. Making them optional would change the
   client (out of scope); sending `[]`/`false` would read as "no known allergies". So the server
   answers a smaller type that simply lacks them. `MemberDto` is unchanged.
3. **Initials only, no display name** on the wire, per the ticket's "display initials". Computed
   from `users.display_name` with the existing `displayInitials` helper, `"?"` when absent.
4. **Every join attempt counts toward the limit**, success included, not just wrong ones. Needed
   so the count is reserved before the outcome is known (concurrency).
5. **Codes are case-insensitive on the server** (trim, upper-case). The mobile fixture compares
   exactly; the server is friendlier to phone keyboards. The guess space is unchanged.
6. **No expiry.** The ticket says "invalid, expired or revoked codes answer 404" but specifies no
   expiry policy and the table has no expiry column. I did not invent a TTL. Codes live until
   rotated. Raised below.
7. **Row provenance source is server-chosen** (`barcode-scan` / `manual-entry`), not the request's
   `quantityProvenance.source` (the client sends free text like "scanned barcode"). The tier is the
   request's. `confidence` and `recordedAt` must be null or 400.
8. **AI interpretation refused as a quantity tier**, allowed (passed through) as a best-by tier,
   matching "tier from the request's provenance, never invented" for the lot and rule 8 for the
   ledger row.
9. **Units:** only `CREATE_ITEM_UNITS_DTO` (the S9 picker's list), stored as sent. `gal`, `grams`
   and `G` resolve in the registry but are refused.
10. **Replay from a different member** with the same key and body is 409 (actor is part of the
    comparison). Keys are household-scoped, so this is a conflict, not Maya replaying Dean's tap.
11. **Status codes:** create item 201, replay 200; create household 201; join 200 both ways.
12. **A signed-in user with no household** gets 403 `FORBIDDEN` on household routes, not 404.
13. **A caller already in a household can create another**, and their session moves to it (most
    recently joined). The ticket does not forbid it; it is the (g) rule applied.
14. **For the architect (added after review, no change made):** best-by provenance keeps only
    the tier on the lot (`inventory_lots.expiry_tier`; source, confidence and time are dropped,
    OQ-E2), and an `AI_INTERPRETATION` best-by lands on the lot unconfirmed. That is a decision
    for the architect, not something this ticket changes.
15. **Bug found and fixed during testing:** `await reply.code(201)` on a Fastify reply waits for
    the reply to be sent (a reply is thenable), which hung each create for the full test timeout.
    Now `await reply.code(...).send(body)`.

## 6. What the reviewer should attack first

1. `app_redeem_join_code` and `app_create_household` (0008): SECURITY DEFINER bodies, the context
   check, `#variable_conflict use_column`, the `FOR SHARE` read against a concurrent rotation.
2. The authorization hook's new `user` kind and `sessionFor`: can any path reach a household route
   with a session the port did not produce, or a `userRoute` handler act in a household without
   going through `tenantSession`?
3. The join handler builds a `Session` from the database's own redeem result to read the household
   back (`household-routes.ts`). The id comes from the code lookup, not the request; check that
   holds.
4. Creation replay comparison (`sameCreation`): a field that should be compared and is not, or a
   canonicalisation mismatch (best-by instants) that turns a true replay into a 409 or a changed
   payload into a replay.
5. Brute force: in-memory limiter keyed by user id only; many accounts multiply the budget
   (vendor-era concern, see escalations).
6. The redaction shape scan (`\b[a-z]{4}-[0-9]{3}\b`, case-insensitive) may over-redact harmless
   strings like `test-123`; I judged over-redaction acceptable.

## 7. Escalations and proposed backlog entries

- **OPEN QUESTION (PO): join code expiry.** Should codes expire (and after how long), or live
  until rotated? Needs a column or a policy; nothing invented here.
- **Shared rate limiter before a second API instance.** Move the join window to Postgres (a small
  attempts table) or a shared cache with deployment. Also consider a per-IP or global join budget
  once real accounts exist, since per-user limits multiply with signups.
- **Rate-limit household creation.** `POST /v1/households` is unlimited per user (ARCHITECTURE
  §7.11 says per-user limits in general).
- **Consolidate the client-key rule.** `CLIENT_KEY` is now stated in both `write-service.ts` and
  `create-service.ts`; export one from a shared module (a one-line change in `write-service.ts`,
  outside this ticket's "creation service only").
- **Household switching** (out of scope): `/mine` exposes ids and `current`; a switch needs a
  validated selection inside the tenant session (OQ-E1).
- **Client wiring** for `HttpApiClient.createItem`, `createHousehold`, `joinHousehold` against the
  real endpoints (mobile ticket). Note the join response is `{ household, alreadyMember }` with
  `HouseholdSummaryDto`, not the client's `HouseholdDto`.
- **Users provisioning** for the real auth vendor: a membership needs a `users` row; today the
  seed provides it.
- **`app_user_memberships` visibility:** any `sk_app` code path can list any user id's household
  ids and names. Only the port and `/mine` call it with a session's user id. Acceptable now; worth
  a note in the threat model.
- **Copy deck:** new strings (section 8).
- **From the review (N1): household create has no idempotency key.** A retried tap makes two
  households and the session moves to the newer one; a Chen member who creates a household cannot
  get back, because re-joining does not bump `joinedAt`. Proposal: refuse create for a caller who
  already has a membership until switching exists, and add a client key to the create body.
- **From the review (N2): tie the pepper's dev fallback to the fixture adapter**, not to
  `NODE_ENV` alone, and refuse a configured pepper equal to the development constant (vendor
  ticket).
- **From the review (N4): a future remove-member ticket** must re-check membership inside the
  tenant transaction, since the port's membership read happens in its own transaction first.
- **From the review (N5): a test pinning the `FOR SHARE` redeem-versus-rotation race** in
  `app_redeem_join_code`.
- **From the review: rate-limit rotation** as well as creation.
- **From the review: a unit alias map for real scans (M2-T4).** The product corpus has units such
  as `gal`, `bunch` and `ct` that `CREATE_ITEM_UNITS_DTO` refuses today.

## 9. Review fixes (round 1)

Independent review verdict: PASS WITH FIXES. All three fixes are on this branch; no scope growth.

**F1 [major], best-by accepted anything `Date.parse` liked.** `"1"` and `"March 7"` were stored
as dates in 2001, at midnight in the server's own time zone. Fix in
`apps/api/src/db/inventory/create-service.ts`: new exported `canonicalBestBy(text)` accepts
exactly a bare `YYYY-MM-DD` (read as UTC midnight, and refused if the date does not exist, so
`2026-02-30` does not roll over to March) or an ISO instant with an explicit offset (the domain
ledger's `ISO_INSTANT_RE`, restated because the domain does not export it). Anything else is 400
`INVALID_TIMESTAMP` on `bestByDate`; the message now says "ISO-8601 date (YYYY-MM-DD) or an
instant with an offset". Tests: `create-service.test.ts` gains refusal rows for `"1"`,
`"March 7"`, `"2026-10-12T00:00:00"` (local time, no offset), `"2026-02-30"` and `"2026/10/12"`,
plus a `canonicalBestBy` block (bare date to UTC midnight, `+02:00` instant to UTC, six
refusals). `households.db.test.ts` gains the same three refusals from the review (`"1"`,
`"March 7"`, local-offset string) over HTTP, each asserting nothing is written. Commit `84fc6d8`
(fix) and `e7ed277` (HTTP tests).

**F2 [minor], three replay comparisons were unpinned.** No behaviour change. Tests added in

**F3 [minor], rotation accepted any body.** Fix in `apps/api/src/http/household-routes.ts`: the

<Okafor> }`, `{ code }` and `{ anything }` each answer 400 and the set of live codes across all
households is unchanged. Commit `e7ed277`.
