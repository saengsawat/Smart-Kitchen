## 2. Semantics as implemented

### 2.1 Signature

```ts
planLotConsumption(item: InventoryItem, request: ConsumptionRequest): Outcome<ConsumptionPlan>
// ConsumptionRequest = { policy: "FEFO" | "FIFO" } & ({ qtyMicros: bigint } | { amount: number })

consumptionInputsFromPlan(plan: ConsumptionPlan, base: ConsumptionInputBase)
  : Outcome<readonly TransactionInput[]>
// ConsumptionInputBase = Omit<TransactionInput, "lotId" | "qtyDelta">
```

The request carries the policy (the BACKLOG shape `planLotConsumption(item, { qtyMicros | amount, policy })`);
the union is exclusive at compile time *and* re-checked at runtime, because callers reach the domain from
JSON boundaries where the type guarantees nothing.

**No `asOf`, no clock.** Expiry ordering needs no "now": an expired lot is simply the earliest `expiresAt`.
*Whether* to consume expired stock is a caller decision and is deliberately not a selection rule here.

### 2.2 Ordering

| Policy | Key 1 | Key 2 | Key 3 |
|---|---|---|---|
| `FEFO` | `expiresAt` ascending, **undated last** | `acquiredAt` ascending, **undated last** | position in `item.lots` |
| `FIFO` | `acquiredAt` ascending, **undated last** | position in `item.lots` | — |

- Every comparator ends in the lot's position, so the order is *total* and does not depend on the sort
  implementation's stability.
- "Undated last" is implemented as an explicit two-part comparison (`hasDate`, then millis), never as
  `Infinity` or `NaN`. A lot whose `expiresAt`/`acquiredAt` is present but unparseable is a **typed
  rejection** (`INVALID_TIMESTAMP`, `field` = the lot id), never a `NaN` that silently reorders the list.
  The ISO-8601 shape accepted is the ledger's own regex (see §8 gap 1 — it is duplicated, not shared).
- FIFO ignores `expiresAt` entirely (pinned by a test where the two policies produce opposite orders).

### 2.3 Balances, skipping and the corruption guard

- Balances are **derived from the rows** (`sumLotDeltaMicros`), never read from `lot.currentQty`.
- Before anything is planned, the aggregate must pass `reconcile()`: snapshot == Σ deltas at item *and*
  lot level, no negative balance, every row attributable, sequences contiguous, keys unique. Any problem is
  returned as that problem's own `LedgerError` (typically `CORRUPT_LEDGER`) — the planner refuses rather
  than planning on either number, because a plan built on a corrupt aggregate moves real food.
- Lots with a non-positive balance are skipped and **reported** in `plan.skippedLots`
  (`{ lotId, balanceMicros, reason }`) rather than silently dropped. `reason` is `ZERO_BALANCE`, or
  `NEGATIVE_BALANCE` for a balance that cannot occur — `reconcile` has already refused that aggregate.
  The classification is defence-in-depth if that guard ever moves (see the M6 mutation note).

### 2.4 Allocation, shortfall and the no-clamp guarantee

Walking the ordered candidates, each takes `min(remaining, lotBalance)`. Therefore:

- every allocation is `< 0` and `|allocation| ≤ lotBalanceBeforeMicros` ⇒ applying a plan can never trigger
  an `OVER_CONSUMPTION` clamp (INV-LEDGER-4 preserved by construction, property P3);
- `Σ |allocations| = allocatedMicros = min(requested, on hand)`, and
  `allocatedMicros + shortfallMicros = requestedMicros`;
- an over-request drains every lot and reports the remainder in `shortfallMicros` — never a negative
  allocation, never invented stock, never a zero allocation. What to do with a shortfall (record it anyway
  and accept the clamp, warn, or stop) is left to the caller, which is the only layer that knows whether the
  user is asserting a fact about the world or requesting a withdrawal.

Plans are deep-frozen; the input aggregate is never mutated (property P4).

### 2.5 Derived idempotency keys

Scheme: **`<base.idempotencyKey>/lot/<allocation index>`** (`PLAN_KEY_INFIX = "/lot/"`, exported).

- Never contains the ledger's reserved `::`, so `appendTransaction` accepts it (a base key containing `::`
  is rejected with `INVALID_IDEMPOTENCY_KEY` before any key is derived).
- A base key that already contains `/lot/` is **rejected**. That rejection is what makes
  `(baseKey, index) → derivedKey` injective: with `/lot/` absent from every accepted base, the first
  occurrence of `/lot/` in a derived key always delimits the base, so two different bases can never collide;
  within one plan the index keeps rows distinct.
- Replaying the full derived set is a no-op per row (`duplicate`, INV-LEDGER-3). A *partial* replay under a
  changed plan conflicts loudly (`IDEMPOTENCY_KEY_CONFLICT`) instead of double-consuming, because index *n*'s
  key is bound to the payload it was first written with — pinned by a test.

### 2.6 Base-input copying and validation

Fields are copied by **explicit list** (`lotId`, `type`, `qtyDelta`, `unit`, `actor`, `occurredAt`,
`recordedAt`, `provenance`, `idempotencyKey`, plus `reason`/`correlationRef` when present) — never by
spreading the caller's object. This is the M1-T1 review **F1** finding applied one layer earlier: nothing
undeclared, and in particular nothing the ledger treats as its own marker, can ride in. `actor`,
`provenance` and `correlationRef` are rebuilt as the planner's own objects, so the caller's objects are
never carried into the ledger and are never frozen by our `deepFreeze`.

`base.type` must be a **decreasing** type — `CONSUME | USE_IN_MEAL | DISCARD | EXPIRE | DONATE`, checked via
`transactionDirection(type) !== "decrease"`. `ADJUSTMENT` (signed) and the increase types are rejected with
`INVALID_FIELD`: splitting a correction or a purchase across lots by an expiry rule is meaningless, and a
signed `ADJUSTMENT` would turn the plan's negative deltas into a legal write.

`consumptionInputsFromPlan` also re-checks each allocation on the way out (negative, non-zero, within
`MAX_QUANTITY_MICROS`, `|delta| ≤ lotBalanceBeforeMicros`, no lot twice), so a **hand-built** plan cannot use
this door to overdraw a lot or double-book one.

### 2.7 Rejection table (no new error codes)

| Condition | Code |
|---|---|
| item / request not an object, `lots`/`transactions` not arrays | `INVALID_FIELD` |
| unknown or missing `policy` | `INVALID_FIELD` |
| both or neither of `qtyMicros`/`amount`; `qtyMicros` not a bigint | `INVALID_FIELD` |
| request == 0 | `ZERO_DELTA` |
| request < 0 | `WRONG_SIGN` |
| `amount` not finite / >6 dp / request above the ledger range | `NOT_FINITE` / `PRECISION_EXCEEDED` / `QUANTITY_OUT_OF_RANGE` |
| aggregate fails `reconcile` (drift, negative, unattributable rows…) | the reported problem, normally `CORRUPT_LEDGER` |
| lot date present but unparseable | `INVALID_TIMESTAMP` (field = lot id) |
| base `type` unknown or not decreasing | `INVALID_FIELD` |
| base key empty / contains `::` / contains `/lot/` | `INVALID_FIELD` / `INVALID_IDEMPOTENCY_KEY` ×2 |
| hand-built allocation: zero / positive / over range / over balance / duplicate lot | `ZERO_DELTA` / `WRONG_SIGN` / `QUANTITY_OUT_OF_RANGE` / `WRONG_SIGN` / `INVALID_FIELD` |

The request cap at `MAX_QUANTITY_MICROS` is what keeps every derived `qtyDelta` inside the ledger's
representable range: an allocation is at most the whole request.

## 3. Tests (33 new; suite 527 → 560 passing without a DB)

**Worked example (the ticket's):** lots A (exp 2026-09-20, 1.0 lb), B (exp 2026-09-15, 0.5 lb), C (undated,
2.0 lb) — FEFO 1.2 ⇒ `B -0.5`, `A -0.7`, C untouched; FIFO (A acquired first) ⇒ `A -1.0`, `B -0.2`;
request 4.0 ⇒ all three drained, `shortfallMicros = 500000n`; `qtyMicros` and the equivalent `amount` give
byte-identical plans; the plan is deep-frozen and the aggregate is unchanged.

**Ordering:** FEFO expiry tie → `acquiredAt`, then lot order; FEFO with both keys tied → lot order; FEFO
undated-expiry lots last and ordered among themselves by `acquiredAt` (never-dated last of all); FIFO ignores
expiry (opposite order from FEFO on the same item); FIFO undated-acquisition last, then lot order; empty and
already-drained lots skipped **and reported**; "nothing on hand" ⇒ empty plan, full shortfall, zero inputs,
`appendTransactions` no-op.

**Rejections:** the whole §2.7 table, including the drifting-snapshot aggregate (`CORRUPT_LEDGER`), the
`"next tuesday"` expiry and a nonsense `acquiredAt` (`INVALID_TIMESTAMP`), and `null` item/request/base.

**Derivation & apply:** explicit-field copy asserted field by field; a base carrying a forged `systemFlag`
and a `smuggledField` produces inputs containing neither, and the caller's `provenance` object is neither
reused nor frozen; optional fields omitted when absent; all five decreasing types accepted, the three others
rejected; apply through `appendTransactions` ⇒ every result `appended` with `clampAdjustment` **undefined**,
per-lot derived balances exactly as planned, `reconcile().ok`, no key contains `::`, replay ⇒ `duplicate`
for every row and the identical aggregate instance; over-request drains the item to exactly `0n` with no
`systemFlag` row anywhere; partial replay under a changed plan ⇒ `IDEMPOTENCY_KEY_CONFLICT`, nothing written.

**Properties (fast-check, generated items of 1–5 lots over a deliberately small date pool so ties are
common, stock 0–2.0, requests 1–9e6 micro-units, both policies):**

| # | Property |
|---|---|
| P1 | every allocation is `< 0` and `≤` its lot's *derived* balance, lots are distinct, `Σ|alloc| = allocatedMicros = min(requested, on hand)`, `allocated + shortfall = requested` |
| P2 | allocations are non-decreasing in an **independently re-derived** policy key (undated last), and any positive-balance lot left out sorts after every allocated one (and only when the request was fully met) |
| P3 | applying the plan never clamps: every result `appended`, `clampAdjustment` undefined, no `systemFlag` row, balance moves by exactly `allocatedMicros`, stays `≥ 0`, `reconcile().ok` (guarded by a non-vacuity counter) |
| P4 | determinism (two calls deep-equal and byte-equal) and no mutation of the deep-frozen input aggregate |
| P5 | derived keys are unique, free of `::`, prefixed by the base, and replay as `duplicate` for every row |
| P6 | a *second* plan on the already-consumed item still never clamps, and every skipped lot is `ZERO_BALANCE` |

**M6 survives and is a genuine equivalent mutant**, reported honestly: the `reconcile` guard (M7) has
already proved `snapshot == Σ deltas` for every lot by the time the balance is read, so the two expressions
are provably equal *there*. The guard is what makes that true, and removing the guard is killed (M7, the
drifting-snapshot test). Reading the derived value is still the correct source of truth and is what the
tests assert against (P1 compares `lotBalanceBeforeMicros` to `sumLotDeltaMicros`).

**M8 survives** because `Array.prototype.sort` is specified stable (ES2019+) and candidates are built in
`item.lots` order, so the explicit final tie-break is redundant *today*. It is kept because it makes the
comparator a total order in its own right rather than borrowing that from the engine; no test can
distinguish the two without exporting internals, which did not seem worth the API surface.

## 8. Proposed backlog items (not fixed here — rule 21)

1. **Share the instant parser and the value-object copiers.** `ISO_INSTANT_RE`/`instantMillis` and
   `copyActor`/`copyProvenance`/`copyCorrelationRef` now exist in both `ledger.ts` (private) and
   `lot-selection.ts`. A small internal `internal/instants.ts` + `internal/copy.ts` would remove the
   duplication; out of this ticket's file scope. Sonnet, low risk, tests exist on both sides.
2. **Shortfall policy for the meal-log caller (M8).** The planner deliberately reports `shortfallMicros` and
   stops. The product decision — record the user's full statement anyway (and accept an `OVER_CONSUMPTION`
   clamp on the last lot, which is the honest correction-rate signal) versus refuse and prompt — belongs to
   the PRD/UX, and should be written down before M8 wires this up.
3. **Surface the plan in the API layer (M2).** `skippedLots` and the per-allocation lot metadata
   (`expiresAt`, `expiryTier`) exist so a UI can say *why* a lot was picked; the read model for that is not
   designed yet.
4. **Expired-stock filtering, if the product wants it.** Today FEFO merely *orders* by expiry; nothing
   refuses to consume an already-expired lot, because the domain has no clock. If "never auto-consume
   expired stock" becomes a requirement it needs a caller-supplied `asOf` and a PO decision, not a default.
5. **Performance note, not a bug.** Balances are re-derived per lot, so planning is O(lots × rows) on one
   item — the same trade `findByIdempotencyKey` documents, fine at household scale, wrong for a bulk path.
   If a bulk consumption path ever appears, derive all lot balances in one pass.

## 9. Honest gaps

- **Nothing is wired.** This is a pure planner; no persistence, no API, no meal-log integration (out of
  scope by the ticket). Its only proven consumer is the test suite.
- **Two mutation survivors**, both analysed in §4 (M6 provably equivalent under the `reconcile` guard, M8
  equivalent under a stable sort). No test was weakened to hide either.
- **`NEGATIVE_BALANCE` is unreachable today** — `reconcile` refuses such an aggregate first. It is kept as a
  classification so the skip stays honest if that guard ever moves, and it is therefore untested by
  construction.
- **Unit conversion is not attempted.** The planner works entirely in the item's own unit; a base input whose
  `unit` differs from the item's is rejected by `appendTransaction` (`MIXED_UNITS`) at apply time, not here,
  since the planner is not given the base when it plans.
- DB-gated suites were **skipped locally** (no `DATABASE_URL`, no Docker in this environment); they are
  unaffected by this ticket and run in CI.
