# BUG-006 worker report: a checked-off shopping row keeps the amount that was bought

- Branch: `ticket/BUG-006` (from origin/main 08af99d)
- Implementation model: Opus (as the ticket says)
- Status: implemented, tests passing locally against a native throwaway Postgres 17 cluster. Not reviewed yet.

## What changed

`apps/api/src/db/shopping/service.ts`

- The row SQL (`ROW_COLUMNS` / `ROW_JOINS`, shared by the list read, the one-row read-back and the row lock) now `LEFT JOIN`s the row's own PURCHASE: `inventory_transactions AS pt ON pt.household_id = r.household_id AND pt.item_id = r.item_id AND pt.id = r.added_transaction_id`, and selects its `qty_delta_micros`, `unit` and `type`. Read only; `FOR UPDATE OF r` still locks the shopping row alone.
- New exported pure function `rowBuyMicros(unit, landed, liveBuyMicros)`. No landed PURCHASE (`added_transaction_id` null): returns the live gap from `computeRowGap`, unchanged (INV-SHOP-1). Landed: returns the ledger row's `qty_delta_micros`. No arithmetic, no recomputation, nothing from the client.
- A landed row whose join finds nothing, or whose ledger row isn't a positive PURCHASE in the row's unit, throws `LedgerIntegrityError` (`CORRUPT_LEDGER`) and never falls back to the live gap. The 0009 guard and the ledger's MIXED_UNITS check should make this unreachable.
- `toRowDto` uses `rowBuyMicros` for `buyMicros`. Status logic is unchanged and still follows the live gap, so an open row with a live gap of 0 still reads `skipped`.
- The add path, the PURCHASE amount, the derived ledger key, idempotency and `gap.ts` are untouched.

`packages/contracts/src/shopping.ts`: the `buyMicros` doc comment only (see below).

## Proposed doc wording (architect applies, rule 30)

For wherever `ShoppingRowDto.buyMicros` semantics are described (the M7 shopping API notes in the architecture docs, and the INV-SHOP-1 entry in testing-strategy.md if it states the formula for every row):

> `buyMicros` is the domain's `neededQuantity(need, have)` against the live snapshot until the row's PURCHASE lands. Once `added_transaction_id` is set, it is that PURCHASE's `qty_delta_micros`, read from the ledger and never recomputed. An undo on S5 doesn't change it. INV-SHOP-1 covers rows with no landed PURCHASE. The row's status still follows the live gap: an open row whose live gap is 0 reads `skipped`.
