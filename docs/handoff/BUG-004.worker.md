## Deviations (flag for the architect)

1. The ticket says "`ApiError` with a dedicated code". No `ApiError` class exists in `client.ts`, and `NOT_AVAILABLE` is not in contracts' `API_ERROR_CODES` (contracts is out of scope). I used the existing typed error, `LedgerRefusedError` (src/inventory/errors.ts, already imported by client.ts), with a client-local code string. Its code falls through to the generic fallback in `ledgerErrorMessage`, which is the wanted copy. If you want a real `ApiError`, that is a separate small ticket.
2. I edited `src/inventory/item-detail-screen.test.ts` (outside the file scope list). Its "Confirm (Objective (g))" test only passed because `HttpApiClient.confirmAiProposal` fell through to the fixture delegate and the test's item id happened to be a fixture id. With the fix it would fail, so the test now stubs `apiClient.confirmAiProposal` to resolve (and asserts it was called with the item id). Same test intent (S5 reloads after a confirm). I did not touch the S5 screen.
3. The unhandled-rejection guard does not use `process.on("unhandledRejection")`: the repo's lint rule bans the `process` global in apps/mobile (tests included). The S4 reject test relies on vitest's own unhandled error reporting, which fails the run (exit 1, "Errors 1 error"). I checked this by mutation: with the catch replaced by `catch (e) { throw e; }`, the reject test fails and vitest reports "Unhandled Rejection" and exits non-zero. Restored afterwards.
4. The S4 tests use `getAllByLabelText("Confirm Strawberries")[0]`: the fixture list renders the item both in the tray and as a list row, both with that label. The reject test asserts the button count is unchanged afterwards.
