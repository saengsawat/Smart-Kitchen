# BUG-002 review: API CORS allowlist (D-027)

Reviewer: Opus (independent session, read-only). Base: 09873a2. Branch: bug-002-api-cors @ 4ac8af1 (round 1), re-checked @ 04a88cd.

## Verdict: PASS WITH FIXES (round 1); PASS on re-check

Round 1. The core security property holds, verified rather than taken from the report. With no allowlist, the API sends zero CORS headers and `OPTIONS` stays a 404: checked through `buildApp`, through the composition root with `NODE_ENV=test`, at the unit level for `production` and its variants, against the compiled server, and in real headless Chrome. Matching is exact. `*` is never sent and neither is a credentials flag. The preflight is a declared `publicRoute` that never touches identity or the session. The header hook runs before authorization, so 401, 403, 404 and 500 responses stay readable. The four-token matrix is identical with and without an origin. Two fixes were required: F1, the architect's ruling R1 (`Vary: Origin` on every response once an allowlist exists), and F2, the R2 condition that a refusal never echoes a secret (the message printed a URL password verbatim). F3 and F4 were optional test pins.

## Findings
- F1 [major, ruling R1] `apps/api/src/http/cors.ts:209-212, :190`: `Vary: Origin` was only sent when the origin matched. `GET /v1/households/me` with `Origin: http://localhost:80900`, or with no Origin, against the dev API answered 200 with no `Vary`; confirmed on the compiled server. Fix: once `allowedOrigins` is non-empty, stamp `Vary: Origin` on every response and add allow-origin only on a match.
- F2 [minor, R2 condition] `cors.ts:117, :126, :132, :137`: every refusal interpolated the raw entry. With `SK_CORS_ORIGINS=https://user:s3cretpw@app.example.test` the password went to stderr, reproduced against `dist/http/cors.js`. Fix: refuse entries with credentials without echoing them, name entries by position, add tests asserting the message does not contain the secret.
- F3 [minor] `apps/api/src/app.ts:201-206`: no test covered the development startup log line; the mutant `if (false)` survived.
- F4 [nit] `app.ts:133`: moving `registerCorsPreflight` above `registerAuthorization` fails no test; behaviour identical while the declaration is intact; the request-time guard still answers 403 for an undeclared preflight.
- Judgements: a preflight with `Access-Control-Request-Method: DELETE` still lists `GET, POST, OPTIONS` and the browser refuses DELETE itself (correct; no route uses another method). `OPTIONS /healthz` from an allowed origin answers 404 with allow-origin but no allow-methods (harmless).
