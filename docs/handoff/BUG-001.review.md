# BUG-001 review: S2 Continue update-depth loop

Reviewer: Opus (independent session, read-only). Base: 74371f1. Branch: bug-001-s2-update-depth @ 81bd33c.

## Round 1 verdict: PASS WITH FIXES

The root cause and the loop fix are right and confirmed. The old layout unmounted `<Slot />` to express a hold, and that is what looped. The new test fails on the old `_layout.tsx` with exactly "Maximum update depth exceeded". The worker's smoke script fails on 74371f1 at S2 Continue with the same stack and passes on the fix. CI from an empty build state is green. But the cover is weaker than the unmount it replaces, in two ways shown in a real browser: (1) on web, keyboard focus goes under the cover (behind the failed-read cover the reviewer tabbed into the hidden S9 form, typed a name, pressed Enter on the hidden "Add to inventory", and an item was written); (2) the covered screen now mounts and runs its mount effects before the gate decides (a household-less cold-start deep link to `/add/scan` requests the camera under the cover; on 74371f1 it made no camera call). Three requirement-level properties are also unpinned. No architecture change is needed.

## Findings
- F1 [blocker] `apps/mobile/app/_layout.tsx:189-195`: `pointerEvents="none"` and `aria-hidden` stop mouse clicks and the accessibility tree, not Tab focus or keyboard activation. Probe: demo mode, headless Chrome, `getOnboardingState` forced to reject, cold start at `/add/manual`; Tab 1 to 8 focused Back, Item name, Mass, Volume, Count, Decrease, Increase, g, all under the hidden wrapper; typing filled the name; Enter on the hidden "Add to inventory" ran `createItem`, the hidden screen did `router.replace("/inventory")`, and the hidden S4 listed "Probe milk 1 g". Over HTTP a household-less user would get 403; a user with a household but an incomplete S2 would get the write through. Fix (verified): react-native-web 0.21.2 forwards `inert` on View; `inert={covered}` on the wrapper, web only; after that Tab reached only "Try again".
- F2 [major] `apps/mobile/app/_layout.tsx:119-124, 170, 196`: on 74371f1 the cold start rendered nothing so the destination never mounted; now `<Slot />` mounts the deep-linked screen under the cover. Evidence: cold-start `/add/scan` with no household fires `permissions.query("camera")` (74371f1: none); with a 3 s read, `permissions.query` then `getUserMedia` under the cover; with a rejected read the camera screen stays mounted behind the error cover. If permission was already granted the camera turns on behind the cover and `onBarcodeScanned` stays live. The worker's justification ("screens tolerate mounting before the gate") came from the F18 home-stale case, an onboarded user, never a household-less one. Fix: before the first Slot mount keep 74371f1's mechanism (nothing while `read === null`, the fallback without Slot on a cold-start failure, `<Redirect>` in place of Slot on the first decision); after the first mount never unmount, cover instead; for in-session navigations either a "gate covered" signal that S7 checks before requesting the camera or rendering `CameraView`, or accept the residual in writing.
- F3 [major, rule 13] `root-layout.test.ts` and the test set: mutations surviving all 14 tests: the cold-start hold flipped; the cover's `backgroundColor` set to transparent; the effect's deps removed (replace on every render); the toast host rendered unconditionally; `accessibilityViewIsModal` removed. Fix: a never-resolving cold-start read test; assert the cover colour and `left: 0, right: 0`; assert one replace across a same-decision re-render; assert the toast host absent while covered; the `inert` assertion.
- F4 [minor] `_layout.tsx:191`: the `pointerEvents` prop logs a deprecation on web; use the style form.
- F5 [minor] `apps/mobile/scripts/web-demo-smoke.mjs`: a crash guard, not a flash or keyboard check; headless Chrome cannot see a camera prompt; ES2018 syntax and a `/* global */` line are workarounds for the missing `apps/*/scripts` eslint block.
- F6 [note] `emulateNavigatorStore` is a model of the real navigator inferred from the browser trace; it reproduces the exact error on the old layout and the browser smoke corroborates it; a model, not expo-router.
