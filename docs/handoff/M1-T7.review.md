The reviewer ran a real Postgres 17.10 throwaway cluster, migrated it with the repo's tooling, seeded ledgers through the real repository write path, and ran an independent probe suite plus a 9-mutation battery against the view SQL and the read function. Every tenancy property holds at runtime: `security_invoker=true` is present in `pg_class.reloptions`; `has_table_privilege('sk_app', view, X)` is false for INSERT/UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER and `relacl` is exactly `{postgres=arwdDxtm/postgres,sk_app=r/postgres}` (no PUBLIC); a session in household A asking for household B gets an empty result; all caller values are bound parameters (three injection payloads rejected by type parsing, ledger intact). ## Findings (none blocking)
- **F1 — LOW:** the defence-in-depth `WHERE household_id = $1` in `correction-rate.ts` is untested independently of RLS (mutation M9 neutralising it with arity preserved survives all 14 tests). Behaviour verified correct by hand (session A asking for B ⇒ empty). Coverage gap only → backlog B1.
- **F2 — INFO:** `statement_count` keys on `system_flag_kind IS NULL` rather than "not a clamp"; identical today (the CHECK permits only `OVER_CONSUMPTION`) but a second `SystemFlag` variant would silently leave the denominator → backlog B4.
- **F3 — LOW:** `view.test.ts` Beta tenancy test asserts row count only, not `household_id` identity (Alpha's does) → fold into B1.
- **F4 — INFO (property worth recording):** `correction_rate ∈ [0, 1]` by construction — every clamp sits immediately after exactly one causing non-clamp row (reserved-marker CHECK), so `others ≥ clamps`. Recorded in ARCHITECTURE §8 at acceptance.
- **F5 — INFO:** the `NULL` rate branch is unreachable through the view (zero-transaction items produce no row; clamp-only groups are impossible) and is exercised only by the read function's empty-period household aggregate (confirmed `null`). The `CASE` guard stays.
- **`55000` vs `42501` (ticket 1d):** the worker's judgment is correct — the aggregate view is structurally non-updatable for every role, so write attempts fail before privilege checks; the load-bearing proof is `has_table_privilege(...)=false` + `relacl`, independently verified. Closed. The worker's self-disclosure of this limitation in code comments and report is exemplary rule-19 behaviour.
