# BUG-001 worker report: S2 Continue crashes with "Maximum update depth exceeded"

Branch `bug-001-s2-update-depth`, off `origin/main` at `74371f1`. Fix commit
`c5043d1`, smoke script commit `91a05a6`, this report is the final commit.

## 1. Reproduction

Reproduced for real, in a browser, before touching any code.

- Web build in demo mode: `npx expo start --web --port 8091` in `apps/mobile`
  (no `EXPO_PUBLIC_API_URL`, so the fixture client), after `pnpm typecheck` so
  `packages/contracts/dist` exists for Metro.
- Headless Chrome (the installed `C:\Program Files\Google\Chrome\Application\chrome.exe`)
  driven over the DevTools protocol. First by hand with `npx -y chrome-devtools-axi`
  (npx cache only, not a repo dependency) to read the screens, then with the
  script in section 5, which taps by `aria-label` with real mouse events.
- Steps: open `/` (lands on S1), type a household name, tap Create household
  (demo goes straight to S2), on S2 tap the first member's Peanut chip, the
  second member's "No known allergies for Maya" (the demo household has two
  members, Dean and Maya, and Continue stays disabled until both are set),
  tap the Vegetarian preference chip, tap Continue.
- What I saw: an uncaught `Error: Maximum update depth exceeded. This can
  happen when a component repeatedly calls setState inside
  componentWillUpdate or componentDidUpdate...`, stack `getRootForUpdatedFiber`,
  `enqueueConcurrentRenderForLane`, `forceStoreRerender`, a `batchUpdates`
  loop, `commitHookEffectListMount`, `commitHookLayoutEffects`: the same
  stack Andy reported. The page stayed at `/onboarding/allergies`. No app log
  before it. Selecting chips produced no error; only Continue did.
- A temporary `console.log` in the root layout (removed before committing)
  showed the loop itself: after Continue the layout rendered with pathname
  `/` and pathname `/onboarding/account` alternately, dozens of times, the
  read always still the stale one tagged `/onboarding/allergies` with route
  `s2`, until React aborted.

Not reproduced on Android (no device or emulator here). The stack Andy saw on
Android is the same one, and the mechanism below is platform independent.

same path over HTTP and would have hit the same loop.

## 3. Root cause in plain words

The root layout expressed "not yet" by unmounting the navigator. When the
pathname was not under `/onboarding`, the read was stale and the stale route
was not `home`, it returned `null` instead of `<Slot />`. `<Slot />` is
expo-router's navigator, so S2's `router.replace("/")` was immediately
followed by the navigator being torn down. With the navigator gone, the
router store lost its navigation state and reported `/onboarding/account`;
the layout saw an onboarding pathname, stopped holding and mounted
`<Slot />` again; the remounted navigator restored the URL's `/`; the layout
held again and unmounted it. Every one of those steps is a store update fired
from a layout effect, so React ran them synchronously back to back and the
fresh read for `/` never got a turn to land and break the cycle. React stopped
it at its nested update limit.

The same hazard existed, unexercised by this flow, on the other two branches
that swapped `<Slot />` out: the failed-read fallback (on a later navigation)
and `<Redirect />` rendered in place of `<Slot />`.

## 4. The fix

One file, `apps/mobile/app/_layout.tsx`. Rule: the layout never unmounts the
navigator to express a hold, a failure or a redirect.

- `<Slot />` is rendered at one fixed tree position for the layout's whole
  lifetime. The only branch without it is the fonts-not-loaded `null`, which
  can only precede the first mount (fonts never go back to unloaded).
- "Covered" = failed read for this pathname, OR pending hold (no read yet, or
  the same stale non-home off-onboarding condition as before), OR a redirect
  about to be issued. While covered: an opaque full-screen view
  (`testID="root-gate-cover"`, sand background, absolutely positioned, absorbs
  touches) sits on top; the navigator's wrapper gets `pointerEvents="none"`,
  `aria-hidden`, `accessibilityElementsHidden` and
  `importantForAccessibility="no-hide-descendants"`; the tab bar and the toast
  host are not rendered (toast state lives in `ToastProvider`, so it survives).
- The failed-read fallback ("Couldn't load your household.", the §8 read
  fallback, Try again) renders inside the cover, same strings and styles.
- Redirects go through `router.replace(redirectTo)` in an effect keyed on
  `[navigatorRendered, redirectTo, pathname]`, so once per decision, and only
  after the fonts branch has rendered the navigator (a read can land before
  the fonts, and expo-router refuses to navigate before a navigator is
  mounted). `redirectTo` still comes from `resolveLayoutRedirectForRead`, so a
  stale read never redirects. `router` is left out of the deps on purpose,
  same convention as `allergies.tsx`.

Why this is the smallest change that keeps every pinned property:

- M3-T4d F2 (fail closed): a rejected read for the current pathname covers
  the app with the fallback; nothing behind it is visible or tappable; no
  redirect is computed from a failed read.
- M3-T4d round 2 (pending window): the hold condition is byte for byte the
  old one plus the cold start (`read === null`), and it now covers instead of
  rendering nothing. A deep link to /inventory or /add is still not usable
  before the gate decides. One behavioural difference, stated plainly: the
  covered screen is now mounted (hidden, inert) while the gate decides, where
  before it was not mounted at all. Screens were already required to tolerate
  mounting before the gate (M3-T2 review note on the F18 frame), and the
  ones that navigate on their own read (S2 with no household, profile)
  produce the same end state the gate does.
- M3-T2 F18 (stale read never redirects; home-stale shows the destination for
  one frame): unchanged logic, still in `route.ts`, untouched.
- M3-T6 F2 (S1 routes an affiliated caller to `/`): S1 is untouched; the
  `router.replace("/")` it issues now lands without the loop.
- A user who completed S2 lands on Home: verified in the browser (section 6).

No change to `route.ts`, any screen, or any other file. No dependency.

## 5. The guard tests

`apps/mobile/src/onboarding/root-layout.test.ts`, 5 existing tests kept with
their scenarios, 3 added (8 total). The `expo-router` mock now has a tiny
external store behind `usePathname`, a recording `useRouter().replace`, and a
`Slot` that counts its mounts and unmounts.

Changed assertions (rule 13, mechanism versus requirement): the old tests
asserted `queryByText("SLOT_RENDERED")` is null while blocked, and
`REDIRECT_RENDERED:/onboarding/account` for redirects. Both encoded the old
mechanism (unmount the navigator, render `<Redirect>`), which is the bug. They
now assert the requirement through `expectScreenBlocked`: the cover is up,
opaque and full-screen, and the navigator's subtree is `pointerEvents="none"`,
`aria-hidden`, hidden from accessibility, with no tab bar; and redirects as
`replaced` containing the target. Every scenario, fallback string and Try
again check is kept. One test name changed from "holds (no Slot, no
redirect)" to "holds (covered, no redirect)".

New tests:

1. **S2's Continue to / while the S2-routed read is still stale settles on
   Home with one navigator mount and no update-depth loop.** With
   `emulateNavigatorStore` on, the `Slot` mock does what the browser trace
   showed the real navigator doing to the router store: on unmount the store
   falls back to `/onboarding/account`, on mount it restores the URL's
   pathname, both inside layout effects. On the old layout this test fails
   with exactly `Maximum update depth exceeded` at the Continue step; on the
   fix it holds (covered), then shows Home when the fresh read lands, with
   one mount and zero unmounts.
2. **Keeps one navigator mount across every gate state** (redirect, S1,
   failed read on a deep link, Try again, onboarded).
3. **Does not issue a redirect before the navigator has rendered** (read
   lands while fonts are still loading).

All 8 fail on the old layout. Mutations on the fix, each run against the file:
dropping the stale-route hold fails 2; forcing `pointerEvents="auto"` fails
7; removing the `router.replace` call fails 5; removing the fonts guard on
the redirect fails 1 (test 3).

Manual browser check: `apps/mobile/scripts/web-demo-smoke.mjs` (new, no
dependency, not part of `pnpm test`). It launches the installed Chrome
headless with a throwaway profile, uses Node's own WebSocket for the DevTools
protocol, and fails on any console error or uncaught exception. Usage, also in
its header:

```
pnpm --filter mobile start
node --experimental-websocket apps/mobile/scripts/web-demo-smoke.mjs http://localhost:8081/
```

(`--experimental-websocket` is needed on Node 20; Node 22+ has the global.)
`CHROME_PATH`, `SMOKE_HEADED=1` and `SMOKE_VERBOSE=1` are optional. It is
written in ES2018-safe syntax with a `/* global */` line because no block in
`eslint.config.js` covers `apps/mobile/scripts` (see section 8). On `74371f1`
it fails with `Maximum update depth exceeded`; on the fix it passes.

## 8. Deviations, escalations, status

- No architecture conflict. No ADR, DECISIONS, INV-* or `route.ts` change.
- Files changed: `apps/mobile/app/_layout.tsx`,
  `apps/mobile/src/onboarding/root-layout.test.ts`,
  `apps/mobile/scripts/web-demo-smoke.mjs` (new), this report. All in scope.
- Behaviour note for the reviewer: while the gate decides, the destination is
  now mounted under the cover rather than not mounted (section 4). I judged
  that the requirement ("not usable before the gate decides") is met by
  "not visible, not tappable, hidden from accessibility". On web, keyboard Tab
  can in principle still reach a focusable element under the cover, because
  react-native-web has no `inert`; the window is the pending read, and the
  previous code had no such window only because it unmounted the navigator,
  which is the bug. Flagging it rather than adding web-only focus handling.
- Follow-up for the backlog (not done, outside scope): `eslint.config.js` has
  no block for `apps/*/scripts/**/*.mjs`, so the smoke script lints under
  ESLint's ES2018 defaults. A one-line addition to the existing
  `scripts/**/*.mjs` block would let it use modern syntax.
- Follow-up suggestion: run the smoke script as part of acceptance for any
  ticket that touches `_layout.tsx` or onboarding navigation; the component
  tests could not see this bug on their own because the old mock `Slot` did
  not behave like a navigator.
- Proposed status line for the architect: `BUG-001: fix ready for review on
  bug-001-s2-update-depth (introduced by 8d1217b M3-T4d pending-window hold;
  root layout now covers instead of unmounting the navigator; browser repro
