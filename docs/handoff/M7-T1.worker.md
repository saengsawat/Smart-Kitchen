## 1. What was built

### (a) Migration 0009 (`apps/api/db/migrations/0009_shopping_rows.sql`)

| Object | What it is |
| --- | --- |
| `shopping_rows` | One row per thing to buy. The ticket's columns plus `default_location`, `removed_at` and `removed_by` (section 7). Quantities are `need_micros` bigint only; the gap is never stored. |
| `shopping_row_writes` | One row per idempotency key the check and add endpoints have accepted, household-scoped primary key `(household_id, idempotency_key)`, insert-only for `sk_app`. Replay versus conflict is decided against it; it doubles as the check-off audit trail. |
| `shopping_rows_guard` trigger | Freezes every column except status, check-off, purchase and removal; keeps a removed row removed; makes `added_transaction_id` write-once and checks it names a PURCHASE on the row's own item correlated to the row; refuses an insert that claims a purchase. |
| `household_memberships_household_id_key` | `UNIQUE (household_id, id)` so the new tables can reference a member through a composite foreign key that carries the household. |
| RLS and grants | 0006 shape on both tables. `sk_app`: SELECT and INSERT on both, UPDATE of `status, checked_off_by, checked_off_at, added_transaction_id, removed_at, removed_by, updated_at` only, no DELETE anywhere. |

CHECKs: `origin_kind IN ('member')`; `unit` in the ten `UNITS_BY_KIND_DTO` symbols (a consistency
test in `packages/adapters` reads the SQL and compares); `need_micros > 0`; `status` open, done,
skipped; stored `skipped` if and only if removed; done has a check-off, open has none; who and when
travel together; a purchase needs an item. Composite foreign keys tie `item_id`,
`origin_member_id`, `checked_off_by` and `removed_by` to the row's own household. The row's unit is
deliberately not tied to the item's unit.

### (b) `GET /v1/shopping` (`apps/api/src/http/shopping-routes.ts`, `apps/api/src/db/shopping/service.ts`)

Any member. Rows in insertion order (`created_at, id`, both `clock_timestamp()`), removed rows
excluded. Per row, `computeRowGap` (`apps/api/src/db/shopping/gap.ts`) takes the item's snapshot
from `readInventorySnapshot`, the same read S4 uses, so micros and tier are exactly S4's. Members
come from `readHousehold`. `syncedAt` is the database's `clock_timestamp()` as an ISO UTC string.

### (c) `POST /v1/shopping/rows/{rowId}/check`

Body `{ checked, idempotencyKey }`, answer 200 `ShoppingRowDto`. Set-state under the row lock.
Checking a done row, or unchecking an open one, changes nothing but records the key. Records the
caller's membership id and `clock_timestamp()`. Replay (same key, row, `checked` and caller) is 200
with no write; any difference is 409 `CONFLICT` with `ledgerCode: IDEMPOTENCY_KEY_CONFLICT`.
Unchecking never touches `added_transaction_id`.

### (d) `POST /v1/shopping/rows/{rowId}/add-to-inventory`

Body `{ idempotencyKey }`, answer `InventoryWriteResponseDto` (the existing contract): 201 when the
PURCHASE was appended, 200 when it already existed. Order of answers under the row lock:
recorded key (replay or 409), no item (409 `ROW_HAS_NO_ITEM`), PURCHASE already landed for this
row and generation (200, the original transaction, the new key recorded against it), not checked
off (409 `CONFLICT`), otherwise one PURCHASE (section 4).

### (e) `POST /v1/shopping/rows/{rowId}/remove`

No body (`{}` or `null` accepted, anything else 400, the rotation rule). Any member; answers 204.
Sets `status = skipped`, `removed_at`, `removed_by`; a repeat is 204 and changes nothing; a
removed row is 404 to check and add. A row whose PURCHASE landed can be removed and the PURCHASE
stays. The origin rule is stated in code as well as by the CHECK.

### (f) Seed (`apps/api/src/seed/fixture-shopping.ts`, wired in `seed-fixture.ts`)

Chen gets chicken breast (Dean's own add, 2 lb, tied to the seeded chicken item, FRIDGE), paper
towels (Maya, 1 each, no item, PANTRY) and olive oil (Dean, 1 each, no item, checked off by Dean at
a fixed instant). Runs as `sk_app` in the Chen context after the inventory seed; derived ids and
`ON CONFLICT (id) DO NOTHING`, so re-runs insert nothing and never touch a row someone changed.
The production refusal is the existing one in `runFixtureSeed`, before anything connects. The
output line now ends `shopping rows created N, already present M.`

### (g) Client (`apps/mobile/src/api/client.ts`)

`HttpApiClient.getShoppingList`, `checkOffShoppingRow`, `removeShoppingSuggestion` and
`addCheckedOffToInventory` against the routes above. The caller's key is sent as is and reused on
the one network retry (writes only; the read is not retried). A write refusal becomes
`LedgerRefusedError("IDEMPOTENCY_KEY_CONFLICT")` for that code and `LedgerRefusedError("INTERNAL")`
for everything else, so S11 renders the §8 conflict sentence or the generic save fallback. A failed
or malformed read rejects and S11 shows the read fallback. Shopping requests feed the existing
connectivity signal (unreachable marks offline, any answer marks online), so the in-session queue
and banner work over HTTP; the queue replays through `checkOffShoppingRow` unchanged. The fixture
path is untouched.

### (h) Contracts (`packages/contracts/src/{shopping.ts,errors.ts,index.ts}`)

`SHOPPING_PATH`, the three route patterns and their path helpers, `ROW_HAS_NO_ITEM` appended to
`API_ERROR_CODES`, `CheckShoppingRowRequestDto`, `AddShoppingRowToInventoryRequestDto`, one new
export block appended to `index.ts`. The `haveTier` doc comment now states the "sufficient"
convention. No response DTO was added: check answers the existing `ShoppingRowDto`, add answers the
existing `InventoryWriteResponseDto`.

## 2. Migration 0009 up and down

Up, in order: the membership constraint; `shopping_rows` with its CHECKs, composite foreign keys and

existing migration-list tests now expect 0009.

## 3. Gap math and tier rules as implemented

`computeRowGap(row, item)` in `gap.ts`, pure, 10 unit tests including a property test against the
domain:

- Counted only when `item.unit === row.unit` as exact stored strings. That is the ledger's own
  comparison (`MIXED_UNITS`), so a row in `each` over an item in `count` is a mismatch even though
  the registry lists `each` as an alias of `count`.
- Counted: `haveMicros` is the snapshot's micros, `haveTier` the snapshot's quantity tier (the
  latest ledger statement's tier, `null` passed through).
- Not counted (no item, or a unit mismatch): `haveMicros` 0, `haveTier` null.
- `buyMicros` is always `neededQuantity(need, row.unit, have, row.unit)`, including when have is 0,
  so the domain is the only subtraction and its identity conversion the only conversion.
- Status on the wire: stored `done` stays `done`; stored `open` with buy 0 answers `skipped`
  ("already have enough" is computed, never stored).
- "Sufficient": kept as the documented convention, no new field. The server always returns the
  snapshot's tier with a counted amount, so it never emits `haveTier: null` with non-zero
  `haveMicros` today (stated in the contract doc comment).
- The add-to-inventory PURCHASE is `computeRowGap` again, under the item's lock, from
  `readInventoryItemSummary` (the single-item twin of the list read), so it equals what the list
  showed unless the balance moved.

## 4. Once-per-row design

- **Row lock first.** Every write takes `SELECT ... FOR UPDATE OF r` on the shopping row, then (add
  only) the item's `FOR UPDATE`. Lock order is always row then item; no other path locks rows.
- **Derived ledger key.** The PURCHASE's key is `shopping-row/<rowId>/generation/<n>`. It contains
  `/`, which no client key can, and no `/lot/`, so it cannot collide with an M2-T2 write's rows;
  S5's undo still finds it (a key with no infix groups by itself). It sits under the household-scoped
  unique index on `inventory_transactions`.
- **Same transaction.** Append, `UPDATE shopping_rows SET added_transaction_id`, and the key record
  commit together or not at all. The PURCHASE carries provenance `KNOWN_FACT` / source
  `shopping-check-off`, actor the caller, correlation `shopping-item` / the row id, occurred and
  recorded at the database's `clock_timestamp()` taken under the lock.
- **Second call.** A waiter re-reads the row after the lock is granted (READ COMMITTED re-evaluates
  a `FOR UPDATE` row), sees `added_transaction_id`, and answers that transaction with nothing
  appended, whatever its key.
- **Backstops.** The guard trigger makes `added_transaction_id` write-once. If a row under the
  derived key already existed without the row knowing (only possible by bypassing this service),
  the ledger refuses a second row under it and the add answers 500, not a second PURCHASE (tested).
- **Generation.** Stored, default 1, part of the ledger key and of every key record. Nothing in this
  ticket bumps it and the guard freezes it, so a reopened gap is a new row today (tested: a second
  row on the same item gets its own PURCHASE). Unchecking and rechecking is not a reopen.
- **Concurrency tests.** Five concurrent HTTP adds with five keys from two members: one 201, four
  200, one id, ledger +1, five key records. Five concurrent adds under one key: one 201, four 200,
  ledger +1, one key record. Two connections held open by hand: the second add is still pending
  300 ms after the first appended, and after the first commits it answers `replayed` with the same
  transaction id.

## 7. Deviations and judgment calls

1. **`shopping_row_writes`, a second table.** The ticket lists `shopping_rows` columns only, but a
   409 on a changed payload needs the key and its payload stored somewhere, and keying it
   `(household_id, idempotency_key)` is the M2-T2 convention the ticket asks for. Insert-only.
2. **Extra `shopping_rows` columns.** `default_location` (the DTO requires `defaultLocation` and an
   itemless row has nowhere else to get it; inventing PANTRY in code would be a guess) and
   `removed_by` (the ticket says removal is `status = skipped` plus `removed_at` and "actor
   logged"; the column makes the actor durable, the log line carries it too).
3. **Remove is allowed on member rows**, as objective (e) says, which reads against the M3-T5 note
   "remove rejects non-AI rows". I followed the ticket. S11 only offers Remove on AI rows, so the
   route is reachable by API only today.
4. **First add answers 201**, replays 200 (the create endpoint's convention). The client treats both
   the same.
5. **An add on an open row is 409 `CONFLICT`** with its own sentence, no new code (the ticket names
   only `ROW_HAS_NO_ITEM`). An add whose gap has become 0, or whose units mismatch, is the ledger's
   own 400 (`ZERO_DELTA`, `MIXED_UNITS`), not a new code.
6. **A second add after uncheck** still answers the original PURCHASE (200): the row rule wins over
   status, which is what "no reversal on uncheck" plus "once per row" add up to.
7. **Key comparison includes the caller.** The same key from another member is a conflict, as the
   ledger's replay comparison and M2-T3's create comparison both do. A check-off key reused for an
   add is a conflict too.
8. **`checked` is validated as a bare `enum: [true, false]`.** The instance keeps AJV `coerceTypes`
   (architect ruling at M2-T2); with `type: "boolean"` a body `{"checked": null}` would coerce to
   false and uncheck a row. Tested with `null`, `0`, `""`, `"false"`, `"true"`.
9. **Client error mapping collapses codes.** Passing `ZERO_DELTA` through would render S5's "Enter
   an amount to record a change." on S11, so everything but the conflict becomes `INTERNAL`
   (generic save fallback), per objective (g)'s wording.
10. **Connectivity.** Shopping requests call the existing private `setStale`, so S11's offline state
    works over HTTP. S4 is not affected: it reads `isInventoryStale` right after its own fetch.
11. **Scope.** `households.db.test.ts` expected 0008 to be the last migration; its round trip now
    rolls back 0009 first. Same one-line kind of change as the in-scope `view.test.ts`. In
    `client.ts`, three private helpers (`shoppingRequest`, `shoppingRefusal`, `shoppingPost`) sit
    directly above the four methods and two type guards (`isShoppingListResponse`,
    `isShoppingRow`) directly below the class; no other method was touched, reordered or
    reformatted. Import lists gained names in place.
12. **Chicken's origin** is Dean (the prototype draws it as a menu gap; menu rows do not exist).

## 8. What the reviewer should attack first

1. The add path's ordering under concurrency: row lock, item lock, the READ COMMITTED re-read
   claim, and whether any path reaches `appendTransactionToDb` without the row lock.
2. Key replay comparison fields (kind, row, `checked`, actor) and whether a recorded key can
   replay across generations or after removal (removal answers 404 first by design).
3. `toRowDto`'s derived `skipped` and the tier pass-through: can `haveTier` ever be non-null with
   `haveMicros` from a different unit, or null with a counted amount?
4. The guard trigger's invoker-rights lookup of `inventory_transactions` (RLS applies under
   `sk_app`) and the write-once rule against the owner role.
5. The client's `setStale` coupling and the `INTERNAL` collapse.
6. Log lines: they carry `actorUserId`, route, counts and flags; never the key, name or quantity.

## 9. Escalations and proposed backlog entries

- **M7-T2, add-row UI on S11 (outline).** `POST /v1/shopping/rows` with `{ name, group, needAmount,
  unit, itemId | null, defaultLocation, idempotencyKey }`, server-minted UUIDv7 id, origin the
  caller's membership, key recorded in `shopping_row_writes` (widen its `kind` CHECK to `create`);
  S11 add sheet reusing S9's unit picker; tests for the 409 on a reused key and the tenancy matrix.
  Needs a copy-deck string set.
- **M7-T3, queue persistence and a real connectivity probe (outline).** ADR-010 option C: persist
  the check-off queue and the last list across restarts; a connectivity port that probes (for
  example `GET /healthz` on an interval or on app foreground) instead of borrowing request
  outcomes, because today an offline client only comes back online when some request succeeds; a
  rule for entries that fail permanently (409 or 404 today stay queued until the row drops off a
  fresh list).
- **Generation bump.** Define when a gap reopens (menu regeneration, D-020) and write the bump:
  a later migration grants `UPDATE (generation)` and amends the guard so a bump clears
  `added_transaction_id`.
- **Remove on AI rows only.** When `ai` and `menu` origins land, decide per origin who may remove
  (the M3-T5 note versus this ticket's member rule) and widen the CHECK and the code guard together.
- **AJV `coerceTypes` and booleans.** Any future boolean body field has the `null` to false problem;
  consider a shared `strictBoolean` schema fragment or switching coercion off for bodies.
- **Contracts, optional.** A `ShoppingRowResponse`/add response DTO is not needed (existing DTOs are
  reused). An explicit `sufficient` field stays unneeded while the server never emits the form.
- **Member leave.** `shopping_rows` references memberships (origin, checker, remover) with no
  `ON DELETE` action; whichever ticket adds leaving a household must decide what happens to those.
- **Unique-index oracle note.** `shopping_rows.id` is a global primary key like `inventory_items.id`;
  M7-T2 must mint ids server-side so a client cannot probe other households' ids by collision.
