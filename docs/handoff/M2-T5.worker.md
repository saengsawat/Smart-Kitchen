## The rows-and-columns statement (what the ticket wants versus what the schema allows)

The ticket wants a confirmation to write `provenance_confirmed_by` (and in effect the tier and source) on the `inventory_transactions` row(s) that carried `AI_INTERPRETATION`, with no quantity column touched and no new ledger row with a delta. The schema forbids every way of doing that:

1. **Updating the existing ledger row is impossible at two layers.** `sk_app` holds only `SELECT, INSERT` on `inventory_transactions` (0006: "UPDATE and DELETE are not withheld pending a hardening milestone, they are simply never granted"). The `inventory_transactions_no_mutation` BEFORE UPDATE trigger (0004) raises `0A000` for any role, the owner included. `apps/api/src/db/inventory/append-only.test.ts` pins both ("refuses an UPDATE as sk_app", "refuses an UPDATE as the owner"). `provenance_confirmed_by` exists in 0003, but it is write-once at INSERT: it can only be set on a row that is already confirmed when it is appended.
2. **Appending a zero-delta "confirmation" row is impossible.** `inventory_transactions_qty_nonzero` CHECK (`qty_delta_micros <> 0`). The ticket rules it out too.
3. **No other table holds the quantity tier.** The summary read (`apps/api/src/db/inventory/snapshot.ts`, `ITEMS_SQL` and `ITEM_BY_ID_SQL`) takes the item's quantity tier and source from the latest ledger row by `sequence`. The columns `sk_app` may update (`inventory_items`: display_name, storage_location, product_ref, ingredient_ref; `inventory_lots`: label, acquired_at, expires_at, expiry_tier) carry no quantity provenance, and using any of them would be a hack. The `ai_observations` table in the data-model.md sketch does not exist yet.

So a confirmation that flips the summary to `KNOWN_FACT` needs a new place to be recorded, which means a migration.

### Second, smaller conflict in the same requirement

The ticket says the confirmation's actor is `ai-confirmed` with `modelRef` from the original provenance. The `inventory_transactions_actor_shape` CHECK requires `actor_model_ref IS NOT NULL` for `ai-confirmed`. The seeded receipt rows (`apps/api/src/seed/fixture-inventory.ts`, Strawberries and Mushrooms) carry provenance `{ tier, source }` only, no `modelRef`, and a `system` actor (`fixture-seed`). So even with somewhere to record it, there is no model ref to copy for the two items the acceptance criteria name. The ruling needs to say either that the model ref is nullable on a confirmation (recorded when present) or that the seed gains a model ref on its AI rows (the seed file is outside this ticket's scope).

## Options for the architect (my analysis, PROPOSED, not decided)

- **A. New append-only table `inventory_confirmations` (recommended).** Roughly: `id`, `household_id`, `item_id`, `transaction_id` (the AI row being confirmed; a composite FK `(household_id, item_id, transaction_id)` so a confirmation can never point across households, which needs a matching UNIQUE on the ledger table), `confirmed_by` (users), `model_ref` (nullable, copied from the row's provenance), `client_key`, `confirmed_at DEFAULT clock_timestamp()`. RLS policy like the ledger tables; `sk_app` gets `SELECT, INSERT` only; a no-mutation trigger like 0004's. `UNIQUE (household_id, transaction_id)` makes a second confirm with any client key a no-op by construction (`INSERT ... ON CONFLICT DO NOTHING`, then read back). The summary read joins the latest ledger row's confirmation: when present, the DTO shows `KNOWN_FACT` with source "{original source} · confirmed by {initials}". The ledger stays exactly as it is, INV-LEDGER-2 is untouched, and the confirmation becomes the evaluation-data record ai-architecture.md §5 asks for. Cost: one migration, plus changes to the two summary statements and the detail read.
- **B. Relax append-only for `provenance_confirmed_by` only** (a column UPDATE grant plus a trigger that allows a NULL-to-value change on that one column). Not recommended: it edits a ledger row, weakens INV-LEDGER-2 and the permanent owner-level append-only test (rule 13 forbids weakening it), and the row would no longer read as the fact as recorded.
- **C. A zero-delta ledger row type for confirmations.** Not recommended: it changes the ledger's core shape (every row moves a quantity), touches the domain types, the reconciliation views and the correction-rate telemetry, and the ticket excludes it.

### Questions the ruling should also answer

- Which row is confirmed: only the latest ledger row (the one the summary shows), or every `AI_INTERPRETATION` row on the item? With the latest-row read, an item whose AI row is followed by a user CONSUME already reads as `KNOWN_FACT`, so the 409 `NOT_A_PROPOSAL` test becomes "the latest row is not `AI_INTERPRETATION`, or it is already confirmed" (the second case should be the idempotent 200, not a 409).
- Migration number: M2-T6 is written to claim `0010`. If M2-T5 becomes a migration ticket, one of them takes `0011` and the order has to be agreed before they run in parallel.
- Model routing: a migration next to inventory history is on the rule-23 list, so Opus/Opus stays right.
