## Resolution (D-028)

The first version of this ticket asked for `provenance_confirmed_by` to be set on the existing AI-interpreted ledger rows. I stopped before coding and reported an ARCHITECTURE CONFLICT (commit `24c984c`). That needs an UPDATE of a ledger row, which the 0006 grants, the 0004 `inventory_transactions_no_mutation` trigger and INV-LEDGER-2 forbid, and a zero-delta confirmation row is refused by `qty_nonzero`. A second, smaller gap: an `ai-confirmed` actor needs a model ref the seeded receipt rows do not carry.

The architect ruled D-028 (PROPOSED, built as proposed; PO ratifies) and amended the ticket:

- a new append-only table `inventory_confirmations` (migration 0010);
- one row for every not-yet-confirmed `AI_INTERPRETATION` transaction of the item, all in one database transaction;
- reads join it, so a confirmed row presents as `KNOWN_FACT`;
- the `ai-confirmed` actor kind is not used, and the seed is untouched;
- a fully confirmed item answers the same idempotent 200;
- 409 `NOT_A_PROPOSAL` only when the item has no AI transaction at all;
- M2-T6 moves to 0011.

This report describes the build against the amended ticket.

## Exactly what a confirmation writes

- **One table, insert only:** `inventory_confirmations`.
  - One row per `inventory_transactions` row of the item with `provenance_tier = 'AI_INTERPRETATION'` and no confirmation yet.
  - `household_id`, `item_id` and `transaction_id` are copied from the ledger row.
  - `confirmed_by` is the session's user.
  - `model_ref` is the ledger row's own `provenance_model_ref` (NULL for the seeded rows).
  - `client_key` is the request's key.
  - `id` and `confirmed_at` come from their defaults (`gen_random_uuid()`, `clock_timestamp()`).
- **Nothing else is written.**
  - No `inventory_transactions` row is inserted or changed.
  - No `inventory_items` or `inventory_lots` column changes.
  - No quantity is read for a decision or written.
- **The item lock** (`SELECT ... FOR UPDATE` on the item row, the same lock the ledger writes take) writes nothing.
- **Pinned by tests:** `confirmations.test.ts` compares every row of all three inventory tables through `row_to_json` before and after (row counts and full rows). `inventory-confirm.db.test.ts` does the same for the ledger across its whole HTTP run. On the running API, after the curls: 15 ledger rows (the seed's 15), `provenance_confirmed_by` set on none, 2 confirmation rows.

## What changed and why

### Migration `apps/api/db/migrations/0010_inventory_confirmations.sql`

- **`UNIQUE (household_id, item_id, id)` on `inventory_transactions`.** It exists only so the new composite foreign key has something to reference. `id` is already the primary key, so no row is read or written.
- **Table `inventory_confirmations`:**
  - composite FK `(household_id, item_id, transaction_id)` to the ledger row, so a confirmation can never name another household's row, or a row under a different item;
  - `confirmed_by` as a composite FK to `household_memberships (household_id, user_id)`, so only a member of the row's household can be recorded (stronger than the ruling's plain "user"; see Deviations);
  - nullable `model_ref`;
  - `client_key` with the M2-T2 key shape CHECK;
  - `confirmed_at DEFAULT clock_timestamp()`;
  - `UNIQUE (household_id, transaction_id)`.
- **Trigger `inventory_confirmations_ai_only`** (AFTER INSERT, invoker rights): refuses a confirmation of any row whose tier is not `AI_INTERPRETATION`. This is the ticket invariant "never promotes a tier other than AI_INTERPRETATION" in the schema, not only in the service.
- **Append-only, both layers:**
  - `sk_app` has SELECT and INSERT only;
  - `inventory_confirmations_no_mutation` and `..._no_truncate` raise `0A000` for every role, the owner included.
- **RLS** with the 0006 shape.
- **Down:** reverts all of it and leaves the ledger as it was (tested).

### API

- **`apps/api/src/db/inventory/confirmations.ts` (new).** The three statements: lock the item, count its AI rows, and `INSERT ... SELECT` the missing confirmations with `ON CONFLICT DO NOTHING` as a backstop. All are household-filtered in SQL as well as by the policy.
- **`apps/api/src/inventory/confirm-service.ts` (new).** In order:
  1. validates the key (`CLIENT_KEY`, M9-T0);
  2. locks the item;
  3. 404 if it is not visible;
  4. 409 if it has no AI row;
  5. inserts the missing confirmations;
  6. reads the item detail back.

  No arithmetic and no model anywhere (rule 7).
- **`apps/api/src/inventory/confirm-route.ts` (new).** The handler: body schema `{ clientKey }` with `additionalProperties: false`, a household route for any member, and the 404, 409 and 400 answers. It logs the route, a row count and a replay flag, never a name, a key or a source.
- **`apps/api/src/http/routes.ts`.** The route declaration only: one `registerConfirmRoute(...)` call.
- **`apps/api/src/db/inventory/confirmed-provenance.ts` (new).** The one presentation rule both reads share:
  - a confirmed `AI_INTERPRETATION` row presents as `KNOWN_FACT` with source `"{original source} · confirmed by {initials}"`;
  - `confidence` and `recordedAt` stay as recorded;
  - a row stored with any other tier is never relabelled, even if a confirmation is somehow there;
  - a confirmer the users policy hides reads `"{source} · confirmed"`.
- **`snapshot.ts`.** The two summary statements LEFT JOIN the latest ledger row's confirmation and the confirmer's display name. The list tier flips only when the latest row is a confirmed AI row, which is the tier S4's tray keys off.
- **`detail.ts`.** The history statement LEFT JOINs each row's confirmation the same way. The actor is unchanged: confirming is not authoring.
- **`initials.ts` (new).** `displayInitials` moved out of `detail.ts` unchanged, so `snapshot.ts` can use it without an import cycle. `detail.ts` re-exports it, so every existing importer is untouched.

### Contracts (`packages/contracts`)

- `ConfirmAiProposalRequestDto { clientKey }` and `ConfirmAiProposalResponseDto { item: InventoryItemDetailDto }`.
- `INVENTORY_ITEM_CONFIRM_ROUTE` and `inventoryItemConfirmPath`, exported from the index.
- `NOT_A_PROPOSAL` added to `API_ERROR_CODES` in `errors.ts`.
- The response carries no replay flag on purpose, so a retry answers a byte-identical body.

### Client (`apps/mobile/src/api/client.ts`)

- **`HttpApiClient.confirmAiProposal`** calls the endpoint:
  - one key per call, reused on the one network retry (the M3-T4a rule);
  - a coded refusal becomes a `LedgerRefusedError` carrying only the code;
  - a malformed 200 body is an error.
- **Cache invalidation:** the item's entry in the summary cache is replaced with the server's post-confirm summary. The stale fallback (copy-deck §7 S4) can then never serve the pre-confirm AI tier, and the tray drops the row on reload even if that reload falls back to the cache. I replaced the entry rather than dropping the whole cache: dropping it would turn an offline reload right after a confirm into the cold-start error screen.
- **`FixtureApiClient` is unchanged.** Comment-only edits elsewhere in the file are listed under Deviations.

## Semantics as built

| Case | Answer | Writes |
|---|---|---|
| Member confirms an item with unconfirmed AI rows | 200, `{ item }` with the confirmed rows as KNOWN_FACT | one confirmation per unconfirmed AI row |
| Same again, same key or any other key, any member | 200, byte-identical body | nothing |
| AI row appended after an earlier confirm | 200 | one row for the new AI row; the earlier confirmation untouched |
| Latest row not AI, older AI row unconfirmed | 200, summary unchanged, the history row reads confirmed | one row |
| Item has no AI row at all (or no rows) | 409 `NOT_A_PROPOSAL`, no `ledgerCode` | nothing |
| Item of another household, or no such item, or a non-uuid id | 404 `NOT_FOUND`, identical bodies | nothing |
| Key outside `^[A-Za-z0-9._-]{1,128}$` | 400 `BAD_REQUEST`, `ledgerCode: INVALID_IDEMPOTENCY_KEY`, field `clientKey` | nothing |
| Unknown body property (`householdId`, `confirmedBy`), empty or missing key | 400 | nothing |
| No or unknown token | 401 | nothing |

## Deviations (each small, flagged for the reviewer)

1. **The service lives in `apps/api/src/inventory/` and the SQL in `apps/api/src/db/inventory/confirmations.ts`.** This keeps the existing rule that every statement lives under `src/db`, and both directories are in scope.
2. **`packages/contracts/src/errors.ts` gained `NOT_A_PROPOSAL`.** The ticket names only `inventory.ts`, but an error code must be an `ApiErrorCode`; M7-T1 set the same precedent with `ROW_HAS_NO_ITEM`.
3. **Permanent invariant test touched: `append-only.test.ts` "refuses a TRUNCATE as the owner".** The new FK makes a plain `TRUNCATE inventory_transactions` fail before the trigger ("cannot truncate a table referenced in a foreign key constraint", still 0A000). The test now asserts both:
   - the plain TRUNCATE is refused (0A000);
   - `TRUNCATE inventory_transactions CASCADE` (the form that gets past the FK check) is refused by the ledger's own trigger, with the original INV-LEDGER-2 message assertion kept.

   I believe this is stricter, not weaker, but rule 13 makes it the reviewer's call.
4. **`apps/api/src/db/shopping/shopping-http.db.test.ts`: the 0009 round trip hard-coded "down 1 is 0009".** It now computes the later migrations from the directory (the M9-T0 b pattern), with the same assertions. M2-T6's 0011 would have hit the same thing.
5. **`apps/mobile/src/inventory/item-detail-screen.test.ts`: the S5 Confirm test relied on the fixture delegate knowing its id.** Its fetch stub now answers the real POST with `{ item }`, and it asserts the confirm URL. Behaviour pinned as before.
6. **`client.ts` comments outside the method changed:** the module doc paragraph, the `ApiClient.confirmAiProposal` doc, the `HttpApiClient` class doc and one constructor comment line. Without these they would be false (rule 15). The `FixtureApiClient.clearHouseholdUntilServerSaysOtherwise` doc still says the method has no endpoint; I left it because `FixtureApiClient` is out of scope.
7. **`confirmed_by` references the membership `(household_id, user_id)`, not just `users`.** It is stronger: a non-member can never be recorded. The cost is that deleting a membership will be blocked by its confirmations, the same position `shopping_rows` is already in (the remove-member ticket must decide).
8. **The body field is `clientKey`, as the ticket says.** Every other write body names it `idempotencyKey`; I followed the ticket. If the architect prefers consistency, it is a two-file rename now (contracts and route schema) and harder later.
9. **`displayInitials` moved to `initials.ts`.** Re-exported from `detail.ts`, so it is not a behaviour change.
