# M1-T6 — Allergen screening: malformed allergen containers fail closed — worker report

**Branch:** `m1-t6-allergen-malformed` (from `main` @ `4eaad2f`) · **Implementation model:** Opus (per ticket) ·
**Ticket:** BACKLOG.md → Epic M1-E3 → M1-T6 · **Origin:** `docs/handoff/M1-T4.review.md` §"Mandatory pre-M4 follow-up".

Rule-29 record. Requirements live in the ticket; this is the audit trail of what
was done, what it means, and what it is measured to be worth.

---

## 1. The bug, stated plainly

`screenSubject` coerced a structurally malformed `allergens` field to "no
assertions". A product whose allergen list arrived as `"peanut"`, `5`, `{}`,
`null` or `["peanut"]` therefore looked *clean* — the locus carried no
uninterpreted data, its `KNOWN_FACT` completeness declaration was honoured, and
the verdict was **`ALLOWED`** for a peanut allergy on a product whose allergen
data we had never actually read. Absence-of-data is never absence-of-allergen
(SR-2); this was worse — it was *unreadable* data being reported as absence.

The fix makes malformed data **uninterpreted** data, which the engine already
knows how to handle: `licensesAbsence` refuses the absence licence on any
uninterpreted entry, `UNRECOGNIZED_ALLERGEN_DATA` is raised, and the restriction
degrades to `UNKNOWN` ⇒ `ALLOWED_WITH_UNKNOWNS`. No new verdict, no new warning
code, no new public function.

## 3. Semantics as implemented

Three shapes of the `allergens` field are now distinguished, deliberately:

| Field value | Classified as | Effect under a valid sourced `KNOWN_FACT` full declaration |
|---|---|---|
| absent / `undefined` | no assertions (honest) | `ALLOWED` — unchanged |
| `[]` | no assertions (honest) | `ALLOWED` — unchanged |
| `"peanut"`, `5`, `true`, `{}`, `null`, any non-array | **malformed container** | `ALLOWED_WITH_UNKNOWNS`, reason `MALFORMED_ALLERGEN_DATA`, detail `allergens is a string, expected an array` |
| `["peanut"]`, `[null]`, `[5]`, `[false]`, `[["peanut"]]`, `[undefined]` | **malformed element** | `ALLOWED_WITH_UNKNOWNS`, reason `MALFORMED_ALLERGEN_DATA`, detail `allergens[0] is null, expected an assertion object` |

Decisions inside that, and why:

- **`null` is malformed, not absent.** Only `undefined` (field never supplied)
  is absence. A recorded `null` is a value someone wrote; it is not a claim we
  can read. Fails closed.
- **A non-object element includes a nested array** (`[["peanut"]]`). An array is
  `typeof "object"`, so the pre-existing code would have taken it as an
  assertion object with a missing kind; it is now named for what it is. Both
  paths refuse the licence, so this is precision, not a verdict change.
- **`undefined` / holes inside the array** are malformed elements. `[,]`
  (a sparse array) is data recorded and lost, not data never recorded.
- **An empty object element `{}` is *not* malformed** — it is structurally an
  assertion object with an unreadable kind, and keeps its existing
  `UNRECOGNIZED_ASSERTION_KIND` classification. Both refuse the licence.
- **Malformed data is never evidence.** `allergens: ["peanut"]` against a peanut
  allergy yields `UNKNOWN`, not `MATCH`: we do not know what that string was
  meant to assert (it could have been a `MAY_CONTAIN` row, or a "free from"
  claim from a vendor with a different schema). Reading it as a `CONTAINS`
  would be inventing data. It is reported, loudly, as unreadable. See §9 item 1
  for a proposed follow-up that would *add* a warning here.
- **First uninterpreted entry wins the reason**, as before; ordering inside a
  locus is input order, so `[contains("milk"), null, 5]` reports
  `allergens[1] is null, …`.

Invariants held: `BLOCKED` is unreachable from this change — the only transition
it can cause is `ALLOWED` → `ALLOWED_WITH_UNKNOWNS` (pinned by the property test
and by the mixed-array tests, which still block). `screenSubject` remains total.

Acceptance criterion (5) — "reverting the fix fails ≥1 test per malformed shape"
— is met with a margin of 8× per shape. Two honest notes:

- Under M-2 the totality case `[new Date(0)]` does **not** fail: a `Date` is an
  object, so the pre-fix path classified it `UNRECOGNIZED_ASSERTION_KIND` and it
  already failed closed. The M1-T6 change only makes the *reason* accurate there.
- Under M-1/M-3 the control tests (empty list, absent field) keep passing, as
  they must — they are the guard against over-correction, so they are
  deliberately *not* mutation-sensitive.

## 6. The one existing test I changed (and why it is not a weakening)

`regressions.review.test.ts` → F4 → "does not iterate a string allergens field
character by character" asserted `unknowns[0].reason === "NO_ALLERGEN_DATA"` for
`allergens: "peanut"`. That expectation *was* the bug in test form: the field is
plainly present. The assertion is now `MALFORMED_ALLERGEN_DATA` plus a new
`unknowns.length === 1` check; the verdict assertion is unchanged. It fails
under M-1/M-3, i.e. it is now pinned by the fix. No INV-* invariant test was
touched, weakened or deleted; no test was removed.

## 8. Proposed doc updates (rule 30 — architect applies at acceptance)

   > `MALFORMED_ALLERGEN_DATA` — the locus's allergen data is present but
   > structurally unreadable: the `allergens` field is not an array
   > (`"peanut"`, `5`, `{}`, `null`), or an array entry is not an assertion
   > object (`["peanut"]`, `[null]`). Unreadable data is **not** absence of
   > data: it is recorded as uninterpreted, so it refuses the absence licence
   > and raises `UNRECOGNIZED_ALLERGEN_DATA`, exactly as an unrecognized
   > assertion code does. A missing field and an empty array remain honest

## 9. Proposed backlog items (found, deliberately **not** fixed here)

1. **Scan malformed entries' raw text for terms (warn-only).** Today
   `allergens: ["peanut"]` against a peanut allergy is `UNKNOWN`. Scanning the
   raw string with the curated terms and emitting a *warning* (never an
   `ALLOWED` and never silently a `MATCH`) would surface "this unreadable field
   mentions your allergen", which is the rule-9-safe direction. Needs a decision
   on whether it should escalate to `POSSIBLE_MATCH`; out of this ticket's
   scope, and arguably an M4 adapter-hygiene issue instead (the adapter should
   not be emitting that shape at all).
2. **Only the first uninterpreted entry per locus is reported.** A locus with a
   malformed element *and* an unrecognized code reports one reason. It never
   affects the verdict (any uninterpreted entry refuses the licence), but a UI
   showing "what is unknown" sees a partial list. Cheap to widen to all entries;
   changes the `unknowns` cardinality, so it wants its own ticket.
3. **`tests/fixtures/recommendations/README.md` cites a file that does not
   exist**: "`packages/domain/src/allergens/fixtures.test.ts` reads every file
   in this directory". It does not — the domain package is I/O-free and the
   cases are mirrored in `corpus.test.ts`. M1-T10 item (i) is building exactly
   the consistency check that would make this sentence true from a package that
   may read files; the sentence should be corrected in that ticket rather than
   drive-by here. (I added only the index entry my ticket called for.)
4. **`packages/adapters` product-lookup mapping** is the natural next place to
   ask whether a malformed upstream `allergens` payload should be rejected at
   the port boundary rather than travelling as far as the screening engine. Not
   in scope (M1-T6 is domain-only); relevant to M4.

## 10. Honest statement of what is *not* covered

- Nothing here validates *who* supplied the malformed data, or stops an adapter
  minting a declaration next to garbage — that is D-017's open item and pre-M4
  gate (b).
- A getter that throws on property access (`{ get allergens() { throw … } }`)
  would still throw out of `screenSubject`, because the throw happens at
  property read in the caller's own object graph, before any code in this module
  runs. Out of scope and, I'd argue, not meaningfully defensible at this layer;
  noted for completeness rather than proposed as work.
- The engine still cannot tell a *truncated* well-formed list from a complete
  one: `allergens: [contains("milk")]` with a `COMPLETE_FOR_MAJOR_ALLERGENS`
  declaration is trusted. That trust is the declaration's job (P5/D-017), not
  this ticket's.
- No live provider calls, no DB, no network were involved in this ticket.
