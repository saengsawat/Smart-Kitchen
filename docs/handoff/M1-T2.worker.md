## 2. Tooling choice

**Chosen: `node-pg-migrate` 9.0.0 (MIT) + `pg` 8.23.0 (MIT), raw SQL migrations, in `apps/api` only.** `packages/domain` gained nothing.

*Why.* The load-bearing parts of this schema are things a TypeScript schema DSL cannot express: row-level security policies, **column-level** grants, a `SECURITY DEFINER` trigger function with a pinned `search_path`, `DEFERRABLE INITIALLY DEFERRED` constraint triggers, and `WITH (security_invoker = true)` on views. In any DSL every one of those lands in a raw-SQL escape hatch — at which point the DSL is contributing nothing but a second dialect to review. What we actually need from a tool is ordered up/down execution, a record of what has run, an advisory lock, and one transaction per migration; `node-pg-migrate` is that and little else. It adds two production dependencies, both MIT, both already ubiquitous (`pg` is the driver any of these options would pull in anyway). `pnpm audit --audit-level=high`: clean.

*Alternative considered — Kysely + its migrator.* The closest call, and the one to revisit at **M2** when ADR-002's query-layer question is actually answered. Kysely's value is the typed query builder, not its migrator (which is a bring-your-own-runner API needing its own CLI wiring). Adopting it now would mean choosing the query layer as a side effect of choosing a migration runner, on a ticket whose queries are eleven hand-written statements. Nothing here blocks it later: the migrations are plain SQL and the repository is thin.

*Rejected — Drizzle.* Generating DDL from a TS schema is the wrong direction when the DDL is the specification and much of it (grants, policies, definer functions) has no schema-object representation; we would maintain the TS model *and* the SQL, with drift between them.

*Rejected — Prisma* (also discouraged in the dispatch, and I agree): engine binaries in the install, historically awkward RLS/session-variable support, and a client that wants to own the connection — a poor fit for a design whose isolation depends on `set_config('app.household_id', …, true)` running on the same connection inside the same transaction.

*Migration naming.* Numeric `0001_…` prefixes rather than node-pg-migrate's default UTC timestamps: this is a small team on one branch at a time, and a reviewer reading six files wants them in dependency order. A test asserts the prefixes stay contiguous. If parallel migration authorship ever becomes real, switch to timestamps (they sort identically).

## 3. Schema decisions

### 3.1 Snapshot maintenance — **DB trigger** (closes ADR-008's open question; M1-T1 §8.4)

data-model.md §3 left "application-level, or trigger — decide in M1-T2" open. **Decision: trigger**, with the application transaction still doing the domain work.

`inventory_ledger_apply()` fires per inserted ledger row and is the only thing in the system that can move `inventory_items.current_qty_micros`, `inventory_lots.current_qty_micros` or `next_sequence`. Reasons, in order of weight:

1. **CLAUDE.md rule 10 becomes structural.** "No code path mutates quantities outside a transaction append" as an application convention is one forgotten `UPDATE` away from being false — from the M2 API, a receipt importer, a backfill, or a person at a psql prompt. As a trigger plus column-level grants it is *true*: `sk_app` holds no `UPDATE` privilege on any snapshot column, and the trigger function is `SECURITY DEFINER`, so appending is the only route.
2. **Atomicity by construction**, which is what the acceptance criterion "snapshots updated in the same DB transaction as the append" is really asking for. There is no ordering for a caller to get wrong.
3. **Concurrency.** The trigger's `SELECT … FOR UPDATE` on the item serialises concurrent appends. An application-level snapshot update needs the same lock, and silently corrupts the snapshot the day someone omits it. Tested: two concurrent `appendTransactionToDb` calls on one item both succeed, with sequences 1 and 2 and no lost update.

The **domain still decides**: whether a decrease overshoots and what the clamp row contains is safety-critical arithmetic and stays in `appendTransaction` (rule 7). The trigger maintains derived totals and enforces ordering; it never invents a row.

**`AFTER INSERT`, not `BEFORE`** — and this was a real finding, not a preference. As a `BEFORE` trigger it ran ahead of RLS's `WITH CHECK`, and being `SECURITY DEFINER` it answered questions about rows the caller could not see: aiming an insert at another household's item id returned *"sequence 1 is not item X's next sequence (7)"*, disclosing the item's existence and its ledger length before any policy rejected the write. Moving to `AFTER` puts every policy and foreign key in front of it. (Exploiting it needed a guessed UUID, so the practical risk was small — but "isolation survives application bugs" should not have an asterisk.)

> **Correction (review finding F2, applied 2026-09-09).** The paragraph above originally claimed this closed the oracle. It did not — it closed only the trigger's half. Unique indexes are checked *before* foreign keys and AFTER-triggers, and `UNIQUE(item_id, sequence)` was not household-scoped, so probing a foreign item with ascending sequence numbers still flipped from duplicate-key to foreign-key violation exactly at that ledger's length. Fixed by scoping the key; see §12 F2. The claim as first written was wrong and is left visible here rather than quietly edited.

### 3.2 Never-negative is a **deferred** constraint trigger

INV-LEDGER-4 says no *committed* state is negative. An over-consuming decrease is recorded at full magnitude and compensated by its clamp in the same transaction, so the snapshot is legitimately negative *between* the two inserts. A plain `CHECK` fires on the first insert and makes the domain's settled policy unimplementable. `DEFERRABLE INITIALLY DEFERRED` constraint triggers on both `inventory_items` and `inventory_lots` test the invariant at COMMIT — and re-read the row rather than trusting `NEW`, because a deferred trigger carries the row image from when it was queued, not from commit time. Clamping stays per lot (a lot may not borrow from a sibling), matching domain-model.md §4.2; tested.

Both functions are `SECURITY DEFINER` — see §12 F1, where they were not, and the invariant could be evaded by changing the request's household context before COMMIT.

### 3.3 Reconciliation is a **view + test**, not a commit-time check

I considered extending the deferred trigger to re-sum the item's whole ledger at every commit. Rejected: it adds O(rows-per-item) work to every append to guard against drift that the apply trigger already makes structurally impossible (the trigger is the only writer, in the same statement as the row). The detector is `inventory_reconciliation` / `inventory_lot_reconciliation` — the SQL mirror of the domain's `reconcile()`, checking snapshot == Σ deltas, non-negativity, and sequence contiguity (`max(sequence) == count(*)` and `next_sequence == count(*) + 1`). If the architect prefers the stronger-but-costlier commit-time check, it is a small migration; I would want a measurement first.

### 3.4 `SystemFlag` as typed columns, not JSONB

`residualMicros` is a `bigint` whose exactness is the entire point, and JSON numbers cannot carry it — in JSONB it would be a stringly-typed, unvalidated field. Typed columns also let a `CHECK` enforce the property M1-T1 established in memory: a system flag may exist **only** on a well-formed, ledger-authored clamp — `ADJUSTMENT`, actor `system`/`inventory-ledger`, residual equal to its own delta, key exactly `<cause>::over-consumption-clamp`, sequence exactly one past its cause — and no other row may use the reserved `::` namespace at all. A self-referential foreign key on `(household_id, caused_by_idempotency_key) → (household_id, idempotency_key)` means a clamp cannot exist without the transaction it compensates. That is `validateStoredRow`'s unforgeability rule, restated where the application cannot reach around it. Five tests attack it directly.

### 3.5 Composite foreign keys carry `household_id` — and the unit

`inventory_transactions` references `(household_id, item_id, unit) → inventory_items(household_id, id, unit)` and `(household_id, item_id, lot_id) → inventory_lots(household_id, item_id, id)`. Two consequences worth stating:

- Linking a row to another household's item is a **referential integrity failure**, not a policy decision. RI checks run as the table owner and bypass RLS, so this holds even if policies are misconfigured — a genuinely independent second layer.
- **Mixed units are unstorable.** domain-model.md §2 and data-model.md §3 require "one unit per item, never silently converted"; putting the unit in the key makes that a key constraint rather than a convention. Item `unit` and `household_id` are additionally immutable after creation (guard trigger), since changing either would silently reinterpret recorded history.

### 3.6 `text` + `CHECK` instead of Postgres `ENUM`

The sketch writes `ENUM(...)`. Enum values cannot be added and used in the same transaction, and removing one means recreating the type — which makes reversible migrations (this ticket's acceptance criterion) markedly harder. A `CHECK` list is diffable against the TypeScript union it mirrors and drops/re-adds cleanly. Proposed as a data-model.md amendment (§4 below).

### 3.7 Both quantity forms, pinned to each other

`qty_delta_micros BIGINT` (authoritative; the only column any arithmetic touches) and `qty_delta NUMERIC(24,6)` (the sketch's display form), with `CHECK (qty_delta = qty_delta_micros::numeric / 1000000)`. Same pair on both snapshot tables. The write path sends the decimal as exact decimal *text* built from the bigint by integer arithmetic — no float ever touches the value. The read path reads **both columns independently** and lets `validateStoredRow` compare them; recomputing one from the other would have made the round-trip test tautological.

Range is capped at `MAX_QUANTITY_MICROS` (1e14) per delta, mirroring the domain. Accumulated balances are uncapped by design (M1-T1 §8.5) and could in principle overflow `bigint` after ~92,000 appends at the maximum delta; Postgres raises on bigint overflow, so that failure is loud rather than silent. Noted, not defended against.

### 3.8 Timestamp normalisation at the write boundary

`timestamptz` has no memory of the offset it was written with and `Date` carries milliseconds, so a row written as `2026-03-06T20:00:00+02:00` reads back as `2026-03-06T18:00:00.000Z`. If that conversion happened on the *read* path, an idempotent replay's payload comparison would fail against its own stored row. So the repository canonicalises `occurredAt`, `recordedAt` and `provenance.observedAt` **before** the domain records the fact: the recorded fact and the stored fact are then byte-identical, and a reload is exact. The cost is sub-millisecond precision, discarded once, at the boundary, deliberately — this is the normalisation point ADR-010 already notes (M1-T1 §8.3). Tested explicitly.

### 3.9 Two roles

`sk_app` (runtime) is created `NOLOGIN` by migration 0001; tests and any in-process job assume it with `SET ROLE`, which is what makes RLS apply (policies bind the *current* role, and a non-superuser current role does not bypass them). Giving it a password would mean a credential in the repo (rule 12); provisioning a `LOGIN` role with a real secret is deployment's job (M2). Roles are cluster-scoped, so 0001's down migration **revokes** in-database privileges rather than dropping the role — a concurrent database in the same cluster (as with the per-file test databases) may still need it. A test asserts zero `sk_app` grants remain after a rollback.

Grants: `SELECT` on identity tables; `SELECT, INSERT` on the three inventory tables; **column-scoped** `UPDATE` on item/lot metadata only; `SELECT` on the two views. No `UPDATE`/`DELETE` on `inventory_transactions`, ever — not withheld pending hardening, simply never granted.

## 4. RLS spike outcome — evidence for ADR-003

**Result: adopt RLS. No disqualifying obstacle was found.** One accommodation was needed and it was cheap.

Implemented: `app_current_household()` reads `current_setting('app.household_id', true)`; policies on `households`, `household_memberships`, `inventory_items`, `inventory_lots`, `inventory_transactions` compare `household_id` to it. `users` is not household-scoped and gets the nearest equivalent — visible only to a session sharing a household with that user. Unset context ⇒ `NULL` ⇒ every comparison is `NULL` ⇒ nothing readable, nothing writable. **Isolation fails closed**, which is the property worth having: a code path that forgets to establish context reads zero rows rather than everyone's.

The one accommodation: **views run as their owner unless created `WITH (security_invoker = true)`**. Without it, the reconciliation views would have been a clean read straight past every policy — a hole big enough to have sunk the whole approach if it had shipped unnoticed. A test asserts `reloptions` on both views, not just their behaviour.

17 tests in `tenancy.test.ts`, each negative paired with a positive control (the owner *can* see both households; Alpha *can* see its own rows), so no assertion passes for the wrong reason. Covered: cross-household reads of items, lots, ledger rows, households, memberships and users; reads through the views; **aggregates** (`SELECT sum(...)` returns a scalar, so a policy that only filtered row output would leak totals); cross-household inserts of items and ledger rows; relabelling a row with one's own `household_id` to smuggle it past the policy (refused by the composite FK); cross-household `UPDATE` (affects zero rows); no-context reads and writes; and context not leaking between pooled transactions.

**PROPOSED wording for ADR-003** (architect to apply at acceptance):

> **Status:** DECIDED (2026-09-__) — PostgreSQL.
>
> **Open question "Adopt RLS or app-layer-only isolation?" — resolved: adopt RLS, in addition to the app-layer rule.** Evidence: M1-T2 implemented policies on all household-scoped tables keyed on a transaction-local `app.household_id`, exercised as the runtime role `sk_app` (17 tests, `apps/api/src/db/inventory/tenancy.test.ts`). Isolation fails closed when the setting is absent. The ORM friction this ADR anticipated did not materialise — the schema is driven by raw SQL and a thin mapper. One real cost was found and paid: views must be created `WITH (security_invoker = true)` or they read past every policy. Defence in depth is doubled by composite foreign keys that carry `household_id`, which hold even where RI checks bypass RLS. RLS does **not** replace the app-layer mandatory-household-context rule or M2's authz matrix; INV-TENANT-1 needs both halves.
>
> **Still open:** managed provider (with hosting, M2, cost-driven). Schema remains vendor-portable — it uses no extension beyond `pgcrypto`'s built-in `gen_random_uuid()`.

**PROPOSED addition for ADR-008** (snapshot maintenance):

> **Resolved in M1-T2: snapshots are maintained by a database trigger** (`inventory_ledger_apply()`), in the same statement as the ledger insert, with the application transaction holding the item lock and making all domain decisions. The runtime role holds no `UPDATE` privilege on any snapshot column, so appending a transaction is the only way a quantity can change — CLAUDE.md rule 10 enforced structurally rather than by convention. Non-negativity is a deferrable constraint trigger, because an overshoot and its clamp are legitimately negative between inserts. Reconciliation remains a query (`inventory_reconciliation`) plus an invariant test, not a commit-time check.

Everything in the property test goes through the real write path as `sk_app` under RLS — so the round-trip also exercises the policies, the grants, the trigger and the locking on every run.

**What stays application-enforced, asserted as such** (`constraints.test.ts` §"what the schema deliberately leaves to the application"):
- *Actor membership.* A ledger row's `actor_user_id` is FK-checked against `users` but **not** against `household_memberships`. A membership FK would make leaving a household either impossible or history-rewriting; authorship is authorised in the service layer (M2 authz matrix).
- *Unconfirmed AI-tier rows.* An `AI_INTERPRETATION` row without `confirmedBy` is storable, per M1-T1 §8.2's reading that INV-CONF-1 binds at the `AIObservation` boundary. If the architect rules otherwise it is a CHECK plus a migration.
- *Payload-equality on replay* (`IDEMPOTENCY_KEY_CONFLICT` vs duplicate) is a domain judgement; the DB only enforces key uniqueness.
- *Lot ordering.* Lots read back ordered by `(created_at, id)`, which is deterministic but not insertion order; the aggregate does not treat lot order as meaningful, and the round-trip test compares lots by id.

### Local skip design

Docker is absent, but a **native PostgreSQL 17.10 is installed** on this machine, so rather than developing blind I ran a throwaway cluster from the existing binaries: `initdb` into the session scratchpad, `pg_ctl` on port 55432 with trust auth, entirely separate from the installed `postgresql-x64-17` service (which I did not touch, and whose credentials I do not have). Nothing was installed; the cluster lives in temp and is gone with the session. **This does not change the ticket's design** — `DATABASE_URL` is still unset by default, the suites still skip locally, and CI is still the gate.

The skip is loud in three ways: a one-line stderr notice per suite (written to `process.stderr` directly, because vitest's default reporter drops `console` output from passing tests — the original `console.warn` was invisible in exactly the run that needed it); vitest's own `83 skipped`; and a named `SKIP NOTICE — <suite> did not run` test per file.

**And the skip cannot happen in CI.** `noteDbSuiteSkipped` throws when `CI` or `GITHUB_ACTIONS` is set, and every database suite calls it from a test of its own — so a skipped suite fails *that suite's own file, by name*, with no log reading required. `ci-guard.test.ts` additionally fails if `DATABASE_URL` is missing and opens a real connection to prove the service container answers. Verified by running the suite locally with `CI=true` and `DATABASE_URL` unset: **8 failures across all 7 database files.**

## 9. Deviations from the ticket

**None from the ticket's requirements or file scope.** Files touched: `apps/api/**`, `.github/workflows/ci.yml` (service container + one `env:` block on the `quality` job, no other workflow change), `.env.example` (one line, name only), `pnpm-lock.yaml`, and this report. `packages/**` and `docs/**` were read-only; the untracked `docs/architecture/workflow-diagrams.md` was left alone.

Three judgement calls worth flagging explicitly, all inside scope:

1. **Migrations live in `apps/api/db/migrations/` but tests live in `apps/api/src/db/`.** The root `vitest.config.ts` only collects `apps/*/src/**/*.test.ts` and is outside this ticket's scope, so tests had to be under `src`. The runner resolves the migration directory relative to its own module (identical depth in `src/` and `dist/`), not `process.cwd()`.
2. **A database per test file**, created from `template0` and dropped afterwards, rather than one shared database — again because root vitest config is out of scope, so files run in parallel and would otherwise migrate each other's schema away mid-run.
3. **`fast-check` added to `apps/api` devDependencies.** Already in the lockfile via `packages/domain`; the property test is the ticket's key integration test and needs it.

## 10. Open questions for the architect

1. **`SECURITY DEFINER` owner.** `inventory_ledger_apply()` runs as whoever ran the migrations — in CI, the superuser. Its body is fixed, parameterised only by `NEW`, and its `search_path` is pinned, so this is not exploitable, but the *principle* is wrong: an `sk_app` insert executes superuser-privileged code. Production should run migrations as a dedicated non-superuser owner role. Backlog item below; needs a deployment decision (M2).
2. **Commit-time reconciliation** (§3.3) — accept the view-plus-test detector, or pay for a deferred re-sum on every append?
3. **`users` RLS.** I chose "visible only to a session sharing a household". ## 12. Fixes applied (post-review, 2026-09-09)

Independent Opus review returned **PASS WITH FIXES**: F1 and F2 blocking, F3–F5 taken in the same pass, F6–F7 report-level. Applied on `m1-t2-schema`, same file scope. Verified against a second throwaway cluster (port 55433, deleted afterwards). Fix commit `8f09817`; CI run [34408059667](https://github.com/saengsawat/Smart-Kitchen/actions/runs/34408059667) success.

Because these migrations have never run anywhere but throwaway CI containers and throwaway local clusters, the fixes edit the original migrations in place rather than adding corrective ones — the schema under review is the schema that ships.

### F1 (blocking) — INV-LEDGER-4 failed **open**

`inventory_items_nonnegative()` / `inventory_lots_nonnegative()` were `SECURITY INVOKER`, so the `SELECT` that verifies the balance was itself filtered by the caller's row-level security context. A caller could append an over-consuming decrease, clear `app.household_id` before COMMIT, and the check would find no row — and `IF FOUND AND …` treated "no row" as "nothing to complain about". A negative balance committed. This is the worst failure mode available to a safety invariant: silent, and in the permissive direction.

Both functions are now `SECURITY DEFINER` with `SET search_path = pg_catalog, public`, and `NOT FOUND` **raises** instead of passing. With the definer's view there is no legitimate way for the row to be missing except deletion inside the same transaction that moved it — which no application path does and which we would want to hear about regardless.

I reproduced the finding before and after rather than taking it on trust (rule 19), driving the reviewer's exact repro through psql on a fresh migrated database:

| | balance after the evasion attempt |
|---|---|
| shipped (fixed) functions | COMMIT raises `INV-LEDGER-4: … negative quantity (-40000000 micro-units)`; balance stays `10000000` |
| pre-fix functions restored via `CREATE OR REPLACE` | COMMIT **succeeds**; balance `-40000000` |

Regression tests in `constraints.test.ts`: one clears the household context before COMMIT, one switches to another household's, and both additionally assert the stored balance is untouched afterwards.

*Note on the fail-closed choice:* an item created and deleted inside a single transaction that also moved its quantity would now raise. No path does this (ledger rows reference items, so a used item cannot be deleted at all), and the alternative is the fail-open behaviour just removed.

### F2 (blocking) — the ledger-length oracle was only half closed

Detailed in the correction note in §3.1. `UNIQUE(item_id, sequence)` → `UNIQUE(household_id, item_id, sequence)`. Semantically identical: the composite foreign key already guarantees a transaction's household matches its item's, so all rows for an item share one `household_id`. The point is *when* the check runs — unique indexes fire at insert time, ahead of foreign keys and AFTER-triggers, so an attacker's row (carrying their own `household_id` to satisfy the policy) used to collide with the victim's rows and stopped colliding exactly past their ledger length.

Reproduced both ways on a fresh database, probing a foreign household's item as `sk_app`:

| probe | shipped key | pre-fix key restored |
|---|---|---|
| `sequence = 1` (within victim's ledger) | FK violation | **duplicate key** |
| `sequence = 2` (past it) | FK violation | FK violation |

Regression test in `tenancy.test.ts`: sweeps sequences 1–4 against a foreign item, collects `code/constraint` for each, and requires exactly one distinct answer — equal to the answer for a UUID that does not exist at all.

### F3 — latent disclosure in an error message

The household-mismatch `RAISE` in `inventory_ledger_apply()` echoed `v_household_id`, another tenant's identifier read through a `SECURITY DEFINER` function that is not subject to the policies. Unreachable today (the composite FK rejects the row first, and the trigger is now `AFTER`), but one schema change from being live. The message now names only values the caller supplied.

### F4 — stored snapshots were read and ignored

`loadInventoryItem` selected `current_qty_micros` and `next_sequence` and did nothing with them. It now compares the item snapshot, `next_sequence`, and **every lot snapshot** against the ledger the domain just replayed, returning `CORRUPT_LEDGER` on any drift. This is what turns "the trigger is the only writer of a snapshot" from an assumption into something checked on every read. (The reviewer asked for the item-level comparison; lots are the same three lines against data already fetched, and lot drift is exactly as dangerous.)

Two tests disable the guard trigger inside a rolled-back transaction, move a snapshot by hand, and require the read path to refuse.

### F5 — three corruption-refusal tests pinned

Disagreeing delta representations; a user row wearing the reserved `::over-consumption-clamp` key; a gap in the sequence. Each drops the blocking constraint or disables the blocking trigger **inside a transaction that is always rolled back** — Postgres DDL is transactional, so both the schema change and the corrupt row vanish. Needing that hammer to construct the rows is itself the evidence that the write path cannot produce them. Plus a positive control asserting an honest item still loads, so the suite cannot pass by refusing everything.

### F6 — the retry helper must handle two error codes (backlog note)

Recorded here for backlog item 4. The concurrency loser does **not** always surface as `40001`. Two paths exist:

- caller took the item lock (the repository's write path) → blocks, re-reads, finds its sequence stale → the trigger raises `40001`;
- caller did not → the unique index rejects it first with **`23505`** on `inventory_transactions_item_sequence_key`.

Both are retryable and mean the same thing. A retry helper keyed only on `40001` would surface the second as a hard failure. The constraints suite asserts both codes for their respective paths, so the distinction is pinned rather than folklore.

### F7 — blast radius of the programmatic rollback

`migrateDown(url)` defaulted to rolling back **every** migration while `node-pg-migrate down` on the command line rolls back **one** — the same word with opposite blast radii depending on where it was typed. `migrateDown` now requires an explicit `count`, and `migrateDownAll` is a separate, self-describing function. Also corrected the comment on the `ALL` sentinel, which described it as a count of the repo's migrations rather than an upper bound.

### F11 (found while verifying, not reported by the reviewer) — `CREATE ROLE` race

Verifying the fixes on a **pristine** cluster surfaced a defect the first cluster had masked: migration 0001 used check-then-create for `sk_app`, and roles are cluster-scoped, so parallel test databases migrating simultaneously both passed the `IF NOT EXISTS` check and collided on `pg_authid`. Three of seven suites failed. An advisory lock cannot fix it — advisory locks are per-database — so the migration now creates and tolerates `duplicate_object`/`unique_violation`. This was a latent CI flake that would only ever have appeared on a fresh server; CI had been passing on luck of worker timing. Test teardown is also optional-chained now, so a `beforeAll` failure reports its own error instead of a teardown `TypeError` stacked on top.
