## 2. The classifier

`isRetryableLedgerError(error)` reads `code`/`constraint` via the repository's own `pgErrorCode`/`pgConstraint` (imported, not duplicated — the ticket text says "or move nothing," so they stayed in `inventory/repository.ts` and are imported from there):

- `code === "40001"` → retryable, regardless of what (if anything) the error names as a constraint.
- `code === "23505"` → retryable **only** when `constraint === "inventory_transactions_item_sequence_key"`.
- everything else (every other SQLSTATE, and anything that isn't a driver-error-shaped object at all: `undefined`, a string, a number, a plain `Error` with no `code`) → not retryable.

**Why these two codes are the same thing, per `docs/handoff/M1-T2.worker.md` §F6:** a concurrent append to one item can lose the race two different ways. If the loser took the item lock (the repository's `SELECT … FOR UPDATE` write path), it blocks, re-reads after the winner commits, and migration 0004's `inventory_ledger_apply()` trigger raises `40001` because the sequence it's about to insert is no longer the item's next one. If the loser skipped the lock, the unique index on `(item_id, sequence)` — `inventory_transactions_item_sequence_key` — rejects the collision first, as `23505`, before the trigger's own check ever runs (`constraints.test.ts`'s "rejects a repeated sequence" test pins exactly this). Both mean "you raced someone and lost"; both are safe to retry from scratch.

**Why `inventory_transactions_idempotency_key`'s `23505` is excluded, deliberately and by name, not just "by not matching the other constraint":** it's a terminal business conflict — a caller reusing an idempotency key for a materially different write — which `appendTransactionToDb` already catches and converts into the typed `IDEMPOTENCY_KEY_CONFLICT` rejection (`repository.ts` lines 409–435). Retrying it changes nothing (the key is used, full stop), and treating it as transient would let a business conflict masquerade as one. The classifier names the sequence-key constraint as the *only* retryable `23505`, rather than naming the idempotency-key constraint as the *only* excluded one, so that a third, future unique constraint on this table defaults to **not retryable** unless someone deliberately adds it to the allow-list. That is the safer default for a helper whose whole job is "don't retry a business decision."

## 3. The wrapper

`withRetriedHouseholdTransaction(pool, householdId, fn, options)`:

- Wraps `withHouseholdTransaction` in a loop, up to `options.maxAttempts` (default 3) attempts.
- Each attempt is a **fresh call** — fresh `BEGIN` (via `withHouseholdTransaction`), fresh invocation of `fn` — not a resumed one. There is no partial state to carry between attempts because the failed attempt's transaction was rolled back before the wrapper ever sees the error.
- On a retryable error: records it as `lastError`, and if attempts remain, awaits `options.sleep(options.delay(attempt))` before looping. Default `delay` is `25 * 2 ** (attempt - 1)` ms (25, 50, 100, …) — deterministic, **no `Math.random`** anywhere in the module, per the ticket. Both `delay` and `sleep` are injectable; tests never wait on real time.
- On a non-retryable error: rethrows the exact same error object (`throw error;`, no wrapping) after exactly one attempt.
- On exhaustion (every attempt up to `maxAttempts` failed retryably): throws `LedgerRetryExhaustedError`, a real `Error` subclass carrying `attempts` (always `=== maxAttempts` on this path) and `cause` (the last attempt's error, both as the ES2022 `Error.cause` and as an explicit readonly property so callers don't need to know that convention).
- `options.assumeRole` (from `HouseholdSessionOptions`) passes straight through to every attempt's `withHouseholdTransaction` call.
- `maxAttempts` is validated (`Number.isInteger` and `>= 1`) and rejected *before* touching the pool at all — not asked for by the ticket text, but "up to `maxAttempts` (default 3)" reads as assuming a sane positive count, and a caller passing `0` deserves a clear error over a wrapper that silently never calls `fn`.

**Why re-running `fn` from scratch is safe** (module header, cites INV-LEDGER-3 per the ticket): replaying any ledger write with the same idempotency key is a no-op (`testing-strategy.md` §2). A retried attempt either lands exactly as it would have the first time, or — if some part of it already committed under a *different* key derivation than the caller intended — collides with itself and surfaces the same typed conflict a genuine duplicate would. Either way, nothing double-applies. `fn` itself still has to hold up its end (no side effects outside the transaction it's handed), but that's the same contract `withHouseholdTransaction` already places on every caller; the retry wrapper doesn't loosen or tighten it.

## 4. Tests

**`retry.classifier.test.ts`** (pure, no DATABASE_URL gate) — table-driven over `{code, constraint}`:
- `40001` retryable with no constraint, the sequence key, the idempotency key, and an unrelated constraint (any constraint at all, by design).
- `23505` retryable only for the sequence key; not for the idempotency key, not for any other constraint, not with no constraint named.
- every other SQLSTATE the schema actually raises (`23503`, `40P01`, `42501`, `55000`, `23514`, `0A000`) never retryable, with and without a sequence-key constraint attached (to prove the constraint alone doesn't flip it).
- non-driver-error inputs: `undefined`, `null`, a string, a number, a plain `Error` with no `code`, an object whose `code`/`constraint` isn't a string, an empty object — all `false`.

**`retry.test.ts` — control flow (fake pool, no DB, runs unconditionally):** a minimal fake `Pool`/`PoolClient` (every `query` resolves trivially) exercises the wrapper's own logic without touching Postgres: first-attempt success with no sleep; retry-then-succeed on both retryable shapes (with recorded delay); non-retry on the idempotency-key `23505` and on a plain `Error`, both asserted by object identity; exhaustion at the default `maxAttempts = 3` with `cause`/`attempts` checked; a custom `maxAttempts`/`delay` pair; `maxAttempts = 1` (no sleep at all); and the `maxAttempts <= 0` guard rejecting before `fn` is ever invoked. This is the "fake-pool unit test... welcome" option from the ticket — it does not replace the DB suite below, it only lets the wrapper's own branching be pinned cheaply and run in every environment.

**`retry.test.ts` — against real Postgres (DATABASE_URL-gated, harness SKIP-NOTICE pattern):**

- **(a)** Two concurrent appends to one item through the *locked* repository path (`appendTransactionToDb`, mirroring `idempotency.test.ts`'s own concurrency test), wrapped in the helper instead of bare `withHouseholdTransaction`: both succeed, sequences `[1, 2]`, `nextSequence = 3`. (The `FOR UPDATE` lock serialises these before either ever raises anything, so this specific pair doesn't actually exercise a retry — it proves the helper is a safe drop-in for the existing locked write path, which is exactly what production call sites need it to be.)
- **(b)+(f)** A raw pre-seeded row at sequence 1 (constructed the same way `constraints.test.ts`'s "rejects a repeated sequence" test does — this is the concrete shape of an unlocked-caller collision, not a hypothetical), then `fn` deliberately re-guesses sequence 1 on attempt 1 (colliding, `23505` on the sequence key) and the real next sequence (2) on attempt 2, both inserts sharing **one** idempotency key. Retried, succeeds on attempt 2, `sleep` recorded exactly `[25]`. Afterward: exactly one row exists for the shared key (attempt 1's insert never committed — the whole transaction rolled back), and the item reconciles (`next_sequence = 3`, `current_qty_micros` = the sum of the two committed rows only).
- **(c)** An idempotency-key conflict, constructed via two real `appendTransactionToDb` calls sharing a key across two different items (the same cross-item scope `idempotency.test.ts` exercises) — routed through the retry wrapper. Because the repository absorbs this `23505` internally and returns a typed `IDEMPOTENCY_KEY_CONFLICT` **rejection value**, not a thrown error, the wrapper's `fn` call simply resolves; `attempts === 1`, `sleep` never called, and the outcome carries the repository's own error code. (The fake-pool tests above additionally throw a raw idempotency-key `23505` directly at the wrapper, to pin the classifier boundary itself rather than only its effect once the repository has already absorbed it.)
- **(d)** A permanently failing `fn` — `RAISE SQLSTATE '40001'` in a `DO` block, a real driver error each attempt, not a hand-built one — exhausts after the default 3 attempts: `LedgerRetryExhaustedError.attempts === 3`, `.cause` is exactly the third attempt's error object (captured and compared by identity, not just by code), and `sleep` recorded `[25, 50]`.
- **(e)** A non-retryable real database error (`42501`, migration 0004's snapshot-column guard firing on a direct `UPDATE inventory_items SET current_qty_micros = …`) propagates after exactly one attempt, the exact same error object the driver threw.

## 5. Mutation check (revert-and-measure, restored afterward)

Baseline for this table: the 37 tests in `retry.classifier.test.ts` + `retry.test.ts`, run with `DATABASE_URL` set so both the pure/fake-pool tests and the real-Postgres tests are exercised together.

| # | Mutation | Killed by |
|---|---|---|
| M1 | classifier retries on *any* `23505`, not just the sequence-key constraint | **5** (4 classifier + 1 fake-pool identity test) |
| M2 | classifier's `23505` branch checks the **idempotency**-key constraint instead of the sequence key (inverted) | **5** (2 classifier + 2 fake-pool + DB test (b)) |
| M3 | outer loop bound `attempt < maxAttempts` weakened to `attempt <= maxAttempts` | **0 — equivalent, see below** |
| M4 | inner exhaustion check `attempt >= maxAttempts` weakened to `attempt > maxAttempts` (off-by-one, one extra attempt before giving up) | **4** (3 fake-pool + DB test (d)) |
| M5 | retry re-uses the first attempt's promise instead of re-invoking `fn` (`cached ??= withHouseholdTransaction(...)`) | **6** (4 fake-pool + DB tests (b) and (d)) |
| M6 | `isRetryableLedgerError` always returns `true` | **20** (17 classifier + 3, incl. DB test (e)) |

**M3 survives and is a genuine equivalent mutant, reported honestly rather than dropped.** The outer `while` condition only needs to be true often enough for the loop to reach `maxAttempts` attempts; the *inner* `if (attempt >= maxAttempts) break;` already exits the loop the instant `attempt` reaches `maxAttempts`, before the outer condition is ever re-evaluated with a larger value. Weakening the outer bound to `<=` therefore never has a chance to admit an extra iteration — the inner check always fires first. I looked for an input that could distinguish the two (e.g. a case where the inner break's condition is skipped) and found none: the break is unconditional on the retryable-error path once attempts are exhausted, so the outer bound is redundant *given* the inner one. It is kept anyway because it makes the loop's own invariant ("run at most `maxAttempts` times") legible without having to reason about the break, and removing it entirely (in favour of `while (true)`) would remove that legibility for a mutation nobody can currently observe — not a change I made unilaterally since it isn't dead code in the sense of being unreachable, only redundant with the current break placement.

Mutations M1/M2/M6 (classifier) and M4/M5 (control flow) all reproduce the exact failure category the ticket names — retrying a business conflict, not retrying a real race, an off-by-one on the attempt budget, and a retry that doesn't actually re-run the write — each caught by more than one independent test, which is the coverage the ticket's acceptance criteria ask for.

## 10. Fixes applied (post-review)

Independent Opus review returned **PASS WITH FIXES**: one required fix (F1), taken in the same pass along with three optional nits (F6, F7, F2) the reviewer flagged as foldable if trivial. All four are test-only or doc/defensive-only — no change to the classifier's or the wrapper's retry decision logic. `apps/api/src/db/repository.ts`/`session.ts` were not touched (the reviewer's separate finding there — an aborted-transaction `COMMIT` after the idempotency `23505` catch — is out of this ticket's scope, being ticketed separately by the architect).

### F1 (required) — the `assumeRole` pass-through was unpinned by any test

The reviewer's mutation (`sessionOptions` forced to `{}` regardless of `options.assumeRole`) killed **0 of 37** tests before this fix: every DB test in the suite connects `db.pool` as the migration/owner role, which can write to every table regardless of RLS or `SET LOCAL ROLE`, so a dropped `assumeRole` never changed what any existing assertion could observe. This is exactly the authorization boundary the wrapper is supposed to preserve per attempt — `SET LOCAL ROLE sk_app` is what makes the RLS policies from migration 0006 apply at all.

Added `retry.test.ts` describe block **(g)**: `fn` runs `SELECT current_user, current_setting('app.household_id', true) AS hh, txid_current()::text AS txid` on *every* attempt (recording each row) and forces a real retryable error (`RAISE SQLSTATE '40001'`) after the probe on attempt 1 only. Asserts: `attempts === 2`; `current_user === 'sk_app'` on both attempts; `hh` equals the seeded household on both attempts; the two `txid`s differ (proving each attempt got its own fresh `BEGIN`, not a resumed one).

**Confirmed by mutation** (reverting the fix — `const sessionOptions: HouseholdSessionOptions = {};`, dropping the pass-through — then restoring it): **1 of 38** tests now fails, and it is exactly the new (g) test (`current_user` comes back as the connecting owner role instead of `sk_app`, since no `SET LOCAL ROLE` runs without `assumeRole`). Reverted immediately after confirming; `grep -n "MUTATION" apps/api/src/db/retry*.ts` is clean afterward.

### F6 (optional, applied) — a discarded `recordingSleep().calls` array

`retry.test.ts`'s "retries on 23505 scoped to the sequence-key constraint" test built a `recordingSleep()` inline as `{ sleep: recordingSleep().sleep }`, throwing away the `calls` array the same helper returns — so the one wait this test forces was never checked against the default backoff. Now captures `{ sleep, calls }` and asserts `calls` equals `[25]`.

### F7 (optional, applied) — header line on re-deriving DB-read values

Added a sentence to the module header's discussion of why re-running `fn` is safe: `fn` must re-derive any value it reads from the database (a sequence, a balance, a lock) freshly on every call, never close over an earlier attempt's read — the whole point of retrying is that the earlier read may already be stale.

### F2 (optional, applied as a code fix rather than documentation-only) — a rejecting injected `sleep` used to silently replace the ledger error

`await sleep(delay(attempt))` sat inside the same `catch` block as the ledger error, unguarded — if the injected `sleep` itself rejected, that rejection propagated out of `withRetriedHouseholdTransaction` in place of the ledger error that triggered the wait, with no trace of the original error left anywhere. Rather than only documenting this (the reviewer's "either...or"), the wait is now wrapped in its own `try`/`catch`: if `sleep` rejects and the rejection is an `Error` that doesn't already carry a `.cause`, the ledger error is attached as `.cause` before the rejection is rethrown. `RetryOptions.sleep`'s doc comment states this behavior. No existing test relied on the old (undocumented) silent-replacement behavior, so nothing needed updating; no new test was added for this path specifically since it is a defensive/diagnostic improvement rather than new externally-observable retry semantics (every existing test's injected `sleep` either always resolves or is asserted to never be called).
