## 3. The three make-or-break flows (tap sequences, zero dead taps)

**Flow 1 — Onboard → first item.** Dev switch "New user" → S1 (`scr-account`) → tap "Create household" → S2 (`scr-allergies`, Maya's peanut/sesame severe pre-set) → tap "Continue" (allowed immediately, since a non-empty allergy set already satisfies the not-skippable gate; tapping straight to "No known allergies" also passes) → S3 Home, first-run state (`scr-home.firstrun`, empty-inventory teaser) → tap "Scan your first item" → S6 Add hub (`scr-add`) → tap "Scan barcode" → S7/S8 (`scr-scan`, match sheet already showing) → tap "Add 2 to Fridge" → `confirmAdd()` clears the first-run state and lands on S4 Inventory, now showing the seeded, populated list (the closest a static prototype can get to "a new item now exists").

**Flow 2 — Scan → confirm (the trust builder).** S6 → "Scan barcode" → S7/S8 default (matched) state: Known Fact chip on identity, Estimated chip on best-by, per-field allergen note, quantity stepper, location chips → "Add … to Fridge" → S4. Branch A (no match): tap "Simulate: no match" in the scan header → the sheet swaps to the miss panel (scanned code shown, retained-for-enrichment copy) → "Enter it manually" → S9 (`scr-manual`, code-retained note visible) → fill fields (each badged Known Fact) → "Add to inventory" → S4. Branch B (permission denied): dev switch "Camera denied" → S7/S8 shows the permission-denied panel instead of the viewfinder → "Enter manually" → S9 (no code note) → "Add to inventory" → S4.

**Flow 3 — Recommend → shop → close the loop.** Recipes tab → tap the top card → recipe detail (`scr-recipe-detail`, ALLOWED variant) → "Cook this" → cook-confirm sheet lists the FEFO allocation per ingredient (including the shortfall banner for chicken: "This recipe needs 2 lb… only 1.25 lb is on hand… record and flag") → "Record & flag, log meal" → toast + S4. Separately, the shopping-list loop: Shopping tab → check off "Chicken breast" → toast with Undo → the existing "Olive oil checked off · add it to the pantry?" banner → "Add" → toast confirming the pantry add (unchanged from the pre-existing pattern, which also does not navigate away — kept for continuity). Offline variant: dev switch "Offline" → Shopping shows the stale banner and check-offs read "queued · will sync" instead of "checked off by DC".

## 8. Design decisions / simplifications (disclosed honestly)

- **S1 vs S12 split.** The ticket names both "S1 … reached from the Home avatar" and a separately-reached S12. Read literally that is under-specified (both would compete for the same tap target). I resolved it as: the avatar routes to **S12** (profile & household) in the normal/returning-user state, and to **S1** (sign-in + create/join) only while the "New user" dev switch simulates a fresh install — matching ux-plan's own framing of S1 as the onboarding screen. This is the one interpretive call in the ticket I'd most want the reviewer to check.
- **Recipe-detail content only has three worked examples** (chicken stir-fry / miso salmon / Thai noodles), matching the three verdict states. The fourth recipe row on the Recipes screen (yogurt berry parfait) does not open a fourth detail screen — tapping it opens a toast explaining the reuse rather than showing mismatched content (wrong photo/title against real ingredients). Building a fourth full detail screen was judged not worth the added file size against the ticket's actual acceptance bar (three verdict states, not "every card has bespoke detail content").
- **Numeric continuity.** The chicken-breast numbers (2.0 lb bought, 0.75 lb used, 1.25 lb on hand) are reused verbatim across S4 (inventory row), S5 (ledger + clamp context), Shopping (gap math), and the recipe-detail shortfall case, tying the brief's own worked example (§7) through the whole prototype. The recipe-detail ingredient row states "need 2 lb" for tonight's stir-fry (a doubled batch, to justify the shortfall demonstration the ticket explicitly asks for) even though the compact card badge elsewhere just shows a plain "have" checkmark — the compact badge is a binary summary, the detail screen is the precise figure; not a contradiction, but a design choice, flagged for the reviewer.
- **Dev switches are additive, not mutually exclusive.** "Camera denied" and "Recipes: none/blocked" etc. can technically be combined with other switches in ways a real app would never allow simultaneously (e.g. camera denied while the no-match toggle is also active). Acceptable for a review tool; not shippable behaviour.
- **44px tap targets.** This is a pre-existing gap in the adopted v3 design system, not something introduced here: `.chip`, `.loc`, `.seg button` and my new `.sevbtn`/`.allergychip` all sit around 34–36px tall, following the established visual language exactly. A full audit/resize of every chip-style control across the whole prototype (existing screens included) was out of this ticket's scope; flagging it as a backlog item below rather than silently claiming full P9 compliance.
- **Back-button accessibility labels.** Existing `.iconb` back buttons (all screens, pre-existing pattern) have no `aria-label`. New screens follow the same existing pattern for visual consistency rather than being singled out for a fix that the rest of the file doesn't have.
