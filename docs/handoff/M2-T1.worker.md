## 2. The authorization model, as implemented

### 2.1 How identity flows

```
Authorization: Bearer <token>
        |
        v
  onRequest hook (http/authorization.ts)
        |  bearerToken() parses the header. Nothing else is read:
        |  not x-household-id, not a query parameter, not a body field.
        v
  IdentityPort.resolveSession(token)
        |  null  -> 401
        |  Session -> role checked against the route's declaration
        v
  request.session = { userId, householdId, role }
        |
        v
  handler: requireSession(request) -> tenantSession(session, fn)
        |
        v
  withHouseholdTransaction(pool, session.householdId, fn, { assumeRole: "sk_app" })
        |  BEGIN
        |  SET LOCAL ROLE sk_app
        |  SELECT set_config('app.household_id', <session household>, true)
        |  ... the handler's SQL, with WHERE household_id = $1 as well ...
        |  COMMIT (checked for the ROLLBACK command tag, M1-T11)
```

The household a request can reach is a pure function of the token. There is no code path by which a request field reaches either the RLS setting or the SQL predicate.

### 2.2 Where denial happens

Five gates, in order:

1. **Registration time.** An `onRoute` hook throws `MissingAuthorizationDeclarationError` the instant a route is registered without `config.authorization`. Routes are registered inside `buildApp`, so this is a boot failure, named and immediate. Tested three ways (no config at all, an empty config object, and the accepted case).
2. **Request time, undeclared route.** The `onRequest` hook answers 403 for a matched route with no declaration. Unreachable while gate 1 is installed, which is exactly the point: a future refactor that registers routes on an instance the `onRoute` hook never saw falls back to denial, not access. Tested against a bare Fastify instance carrying only the hook.
3. **Request time, no credential.** Missing `Authorization` header, or one that is not a well-formed `Bearer <token>`, is 401. The parser is deliberately strict: no trimming, no case folding, no second token, so "nearly right" is wrong.
4. **Request time, unknown credential.** The port returning `null` is 401.
5. **Request time, wrong role.** A role outside the route's declared list is 403.

401 and 403 bodies are the same shape and say nothing about why. The difference between "that token is unknown" and "that household is not yours" is itself information about another household, in the same family as the tenant-inference oracle the M1-T2 review closed in migration 0003. The reason is recorded in the log instead, where only we can read it (`authorization.denied` with a fixed enumerated `reason`, the route, the status and the actor when one resolved, per ARCHITECTURE §7.10).

A denied request opens no database session at all. That is asserted, not assumed: the test harness records every session the routes actually scope a transaction for, and it is empty on every denial path.

An unrouted path answers 404, not 403: denying there would turn every typo into a 403 and reveals nothing useful. No household state is reachable through the not-found handler.

### 2.3 How the RLS context is set

`createTenantSessionRunner(pool)` wraps M1-T2's `withHouseholdTransaction` and **always pins `assumeRole` to `sk_app`**, whatever the pool is connected as. In a deployment that connects as `sk_app` it is a no-op. In the test harness, which connects as the database owner so it can seed across households, it is what makes the policies bind at all, and an owner connection that skipped it would read every household's rows while every test passed. Pinning removes the difference between the two, so the isolation the tests prove is the isolation production gets.

Handlers never see the `Pool`. They are handed the session and the runner, so the only SQL they can issue is SQL already inside a transaction scoped to that caller's household. No SQL in this ticket runs outside one.

The read also carries `WHERE household_id = $1` from the session. Both layers are present and neither is treated as making the other unnecessary (data-model.md §5). The tenancy suite removes each one separately and shows the other still holding.

### 2.4 The endpoint

`GET /v1/inventory/items` returns one row per item with:

- exact quantity as `{ unit, micros, amount }`, micros as decimal text for `BigInt` and `amount` as the canonical exact decimal. No arithmetic, no conversion and no float anywhere in the read path;
- `provenance.quantity` = tier, source, confidence and `recordedAt` of the **most recent ledger statement** on the item, found by a lateral join ordered on `sequence` (the ledger's authoritative order, never `occurred_at` or `recorded_at`);
- `provenance.earliestExpiresAt` = the `expiry_tier` of the soonest-expiring lot;
- each lot with its own quantity and `expiresAtProvenance`.

A stored `storage_location` or provenance tier outside the contract's union raises rather than being forwarded. Quietly passing an unrecognised tier to a client that renders provenance chips is how a tier stops meaning anything (design principle P2).

The response never names a household. There is no `householdId` anywhere in the contract, in either direction.

### 2.5 Logging and redaction

Fastify's built-in pino does the writing. The policy around it:

- `genReqId` mints a UUIDv7 per request from `src/ids/uuidv7.ts`, echoed on every response as `x-correlation-id` and present on every log line as `reqId`. A caller-supplied request id is ignored, so a caller cannot choose what their requests are filed under or collide with somebody else's deliberately.
- Fastify's own request logging is **off** (via `logController`, the non-deprecated form of `disableRequestLogging`). It serialises the whole `req`, headers included, and the bearer token lives in a header. We emit one `request.completed` line built from an explicit allowlist instead: correlation id, method, matched route pattern, status, duration, and the session's opaque ids when one resolved. The raw URL is never logged, so the query string never is.
- `formatters.log` runs the denylist over every merged object anyway, as a second layer. Keys are matched on a normalised form (lowercased, non-alphanumerics stripped) so `display_name`, `displayName` and `DISPLAY-NAME` are one key. Strings are additionally scanned for an email address and for a `Bearer …` credential wherever they appear, which is the only thing that catches a value assembled somewhere else, such as a Postgres unique violation quoting the conflicting tuple.
- The `err` serializer is replaced for exactly that reason: pino's default emits the raw message and stack.
- Opaque identifiers are deliberately **not** redacted. `userId`, `householdId`, `correlationId` carry no personal data alone and they are what makes a denial auditable.

### 5.1 The mutation test, and its sibling

The ticket asks for a mutation-style test proving the endpoint returns nothing when the tenant context is removed, so the isolation is RLS and not application luck. There are two, one per layer:

- **Tenant context removed, role still pinned.** The session runner is replaced with one that opens the transaction with no `set_config('app.household_id', …)`. Same SQL, same session, same role. The endpoint returns `{ items: [] }` where the control returns two items, because `app_current_household()` is NULL and every policy therefore denies (migration 0006, fail-closed).
- **Role unpinned, context correct.** The pool stays connected as the database owner, which the policies do not bind, so RLS is effectively off. The endpoint still returns only the Chen items, because `WHERE household_id = $1` is doing its job.

Together they show the two layers hold independently, which is what "defence in depth" has to mean to be worth the cost.

## 7. Open questions the ticket surfaced (not resolved by me)

1. **One user, several households.** `Session` carries exactly one `householdId`, which is what the fixture map can express and what the endpoint needs. The schema allows a user to be a member of several households (`household_memberships` is keyed on the pair). Whether a real session pins one household, or the client selects one and the API validates the membership, is an M2-T3 / auth-vendor design question. I did not decide it. If it becomes "the client selects", the selection must be validated against `household_memberships` inside the tenant session, and the "identity comes only from the port" rule becomes "the *set* of permitted households comes only from the port".
2. **Role semantics.** `owner` and `member` exist in the schema and the port returns whichever the membership row holds, but nothing yet distinguishes what an owner may do that a member may not. That is Q3, still open, so the inventory read permits both roles explicitly rather than by omission. The machinery to narrow a route to owners exists and is tested.
3. **A documentation nit, not fixed (outside file scope).** The docstring on `microsToDecimalText` in `apps/api/src/db/inventory/repository.ts` says `1250000n -> "1.25"`. The function actually returns `"1.250000"`; a fraction is always written to six places. The code is right and the comment is wrong. One-line comment fix for a maintenance bundle.

## 8. Proposed documentation changes (for the architect to apply at acceptance)

Workers do not edit `docs/**` (rule 30), so these are proposals.

### 8.1 ARCHITECTURE.md §7.2 (Authorization)

Current:

> **Authorization:** every request resolved to (user, household, role); default-deny; the authz matrix is a permanent test suite (INV-TENANT-1).

Proposed (M2-T1, IMPLEMENTED):

> **Authorization:** every request is resolved to (user, household, role) by the identity port and by nothing else. No header, query parameter or body field may name a user or a household; a request carrying `x-household-id` is answered for the household its *token* resolves to. Default-deny is enforced twice: a registration-time guard refuses to register a route without an explicit `config.authorization` declaration (so the app cannot boot with an unguarded route), and the request-time hook denies a matched route that carries none. 401 and 403 answer identically shaped bodies carrying no reason, because the difference between "unknown token" and "not your household" is itself information; the reason is recorded in the audit log instead. A denied request opens no database session. The authz matrix is a permanent test suite (INV-TENANT-1), now at both the database boundary (`db/inventory/tenancy.test.ts`) and the HTTP boundary (`http/tenancy.db.test.ts`).

### 8.2 ARCHITECTURE.md §7.15 (Logging redaction)

Current:

> **Logging redaction:** structured logger with denylist (names, emails, tokens, profile fields, allergy details); log payload review is part of code review.

Proposed (M2-T1, IMPLEMENTED):

> **Logging redaction:** structured JSON logging with a correlation id on every line (UUIDv7, `genReqId`, echoed as `x-correlation-id`). Framework request logging is off: the framework serialises whole requests including headers, and the bearer token is a header, so the API emits its own request line from an explicit allowlist (correlation id, method, matched route pattern, status, duration, and the opaque session identifiers). The raw URL, and therefore the query string, is never logged. A denylist (`apps/api/src/http/redaction.ts`) runs over every log record as a second layer, matching keys on a normalised form and additionally scrubbing email addresses and `Bearer …` credentials out of string *values*, which is what catches a message assembled elsewhere such as a driver error quoting a row. Opaque identifiers (user id, household id, correlation id) are deliberately not redacted: they carry no personal data alone and they are what makes an authorization denial auditable (§7.10). Log payload review is part of code review.

### 8.4 data-model.md §5 (Tenancy isolation)

The section still describes the DB layer as `PROPOSED (evaluate in M1-T2)`, which M1-T2 settled. Proposed replacement for the first two bullets:

> - **App-layer:** every repository and read function takes a mandatory household context, and that context comes from the identity port alone (M2-T1). Over HTTP it is structural rather than conventional: handlers are handed a tenant-session runner instead of the connection pool, so the only SQL a route can issue is SQL already inside a transaction scoped to the caller's household. No query path exists without a household context.
> - **DB-layer (DECIDED, M1-T2):** Postgres row-level security keyed on the transaction-local `app.household_id` setting (migration 0006), as defence in depth. `withHouseholdTransaction` sets it and pins `SET LOCAL ROLE sk_app` on every request transaction, whatever role the pool connects as, so the policies bind identically in test and production. Unset context means `app_current_household()` is NULL and every policy denies: isolation fails closed. The two layers are tested independently, each with the other disabled (`apps/api/src/http/tenancy.db.test.ts`).

### 8.5 data-model.md §3 or §5: the provenance gap

Worth recording as an **OPEN QUESTION**, since a screen will hit it:

> `inventory_transactions` carries a full provenance block (tier, source, confidence, model ref, observed at, confirmed by). `inventory_lots.expiry_tier` carries a tier and nothing else, so an expiry date has a confidence tier but no recorded source or timestamp. `GET /v1/inventory/items` therefore returns `{ tier, source: null, confidence: null, recordedAt: null }` for a lot's expiry. Whether lots should gain a provenance block (a scanned best-by date is a different kind of fact from a shelf-life estimate, and the copy deck distinguishes them) is an open schema question, related to OQ-D7.

## 9. What the reviewer should attack first

In the order I would attack it:

1. **Try to reach the Okafor household from a Chen session, through every layer.** The obvious ones are covered (header, query, body). Look for the ones I did not think of: a route parameter, a `content-type` that makes Fastify parse the body differently, a second `Authorization` header, header case, an `x-forwarded-*` header, HTTP method override, HEAD on the same route (Fastify mirrors GET into HEAD, and I claim the config is inherited: verify it, do not take the comment's word).
2. **The bearer parser.** `/^Bearer[ ]([^\s]+)$/` is deliberately strict. Confirm there is no input that reaches `resolveSession` with a token the fixture map does not contain verbatim, and no input that produces a token with surprising content. ### 11.4a F8 (blocker): F1 broke `pnpm lint` on any clean checkout

**The finding, and why neither I nor the reviewer saw it.** Pointing the three packages' `exports` at `dist/` (F1) also moved where `eslint-import-resolver-typescript` looks. `dist/` is a build artefact: on a fresh checkout it does not exist, and **CI runs `pnpm lint` before `pnpm typecheck`**, which is the step that builds it. So every cross-package import fails to resolve, and `pnpm lint` exits 1 with ten `import-x/no-unresolved` errors across `apps/api`, `apps/mobile` and `packages/adapters`.

Every green `pnpm lint` any of us ran, mine included, ran on a working tree that already had a `dist/` from an earlier build. That is the whole lesson of this finding and of F1 before it: a check that silently depends on a build artefact reports the state of the machine, not the state of the branch. Reproduced exactly as described:

```
rm -rf packages/*/dist apps/api/dist packages/*/*.tsbuildinfo apps/api/*.tsbuildinfo apps/mobile/*.tsbuildinfo
pnpm lint    # 10 problems (10 errors, 0 warnings)
```

**The fix**, the one the review recommended, using two of its three levers:

1. Each of the three packages gains a **`"source"` export condition** ahead of the others:
   `"exports": { ".": { "source": "./src/index.ts", "types": "./dist/index.d.ts", "default": "./dist/index.js" } }`.
   `source` is a widely used community condition, not a standard one, which is exactly what makes it safe here: a consumer that does not ask for it never sees it. Node ignores it and takes `default`, so `node apps/api/dist/server.js` is unaffected. Metro's condition set is `require`/`import`/`react-native`, so the mobile bundle is unaffected.
2. **eslint** asks for it: `import-x/resolver.typescript.conditionNames` now lists `source` first. The rest of the array restates the resolver's default set, because supplying `conditionNames` replaces the defaults rather than extending them. Lint now resolves to `src/index.ts`, which always exists, so it no longer depends on a build having happened.

**What I deliberately did not do, and why.**

- **No `customConditions` in TypeScript.** The review said to add it only if it does not break `tsc -b`, and it is not needed at all: TypeScript does not recognise `source` unless told to, so it falls through to `types`, and `tsc -b` builds referenced projects before the ones that depend on them. I verified `pnpm typecheck` from a state with no `dist/` and no `*.tsbuildinfo` anywhere: exit 0. Adding `customConditions` would have pointed the API's program at another project's `src/`, which is the `rootDir` violation that project references exist to avoid. Left alone.
- **No `resolve.conditions` in vitest.** The alias map added in F1 already pins the three package names to `src/index.ts`, it is unambiguous, and it is exercised by every run. Vite splits resolution conditions between client and SSR, so `resolve.conditions` would have been the less certain of the two mechanisms for the same outcome. One mechanism, not two.

**Proof it is not a build-dependent pass this time.** With `apps/api/dist`, all three `packages/*/dist` and every `*.tsbuildinfo` deleted, `pnpm test` is still green (956 passed, 171 skipped) and the compiled-entry-point suite skips loudly by name rather than failing. Lint, typecheck and test now each stand on their own from an empty build state.

### 11.6 The other findings

**F2 (major): the error path logged `[object Object]`.** Confirmed and fixed, and there was a second half the finding did not mention.

pino applies `formatters.log` **before** its serializers. The `err` serializer therefore never saw the thrown value, only the object the formatter had already produced, and reported every 500 as `{"type":"NonError","message":"[object Object]","stack":""}`. Errors are now reduced inside the formatter, by `redactError`, which is the only place in the pipeline that still holds the real `Error`.

Dropping the `err` serializer outright, as the finding suggested, is not sufficient: **Fastify installs its own default one**, which then re-serializes the already-reduced object and reports its `type` as `"Object"`. I found this because the new test asserted `err.type === "Error"` and got `"Object"`. So `redactError` is now idempotent (`isSerializedError` recognises its own output and returns it untouched) and is kept as the serializer as well, which makes the result correct whichever order the two run in.

A third thing fell out of the same test. ### 11.7 The reviewer's point about D-022's wording

Recording it as asked, without resolving it (rule 3; this is the architect's call).

D-022 says "the fixture identity is compiled out of production builds." That is not literally what happens and never was. `apps/api/src/identity/fixture-identity-port.ts` is an ordinary module in the build: `tsc` emits it to `dist/`, and a production artefact contains it. What is guarded is **selection**, in one function (`chooseIdentityAdapter`), which refuses the combination and stops the process. Two ways to close it, for the architect: reword D-022 to say "cannot be selected outside development, enforced at startup", which is what the code does and what the tests prove; or keep the wording and add a build-time exclusion when a real adapter lands and there is something to exclude it in favour of.
