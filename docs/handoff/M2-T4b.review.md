Reviewer: Opus (independent session, read-only). Base: origin/main 6754b92. Branch: m2-t4b-lookup-hardening @ bf3e8a4.

## Round 1 verdict: FAIL

The code does what the ticket says, and it is careful. The UPC-E expansion was checked exhaustively against an independent GS1 reference: all 20,000,000 number-system-0/1 inputs, zero mismatches, no wrong check digit accepted, no valid EAN-8 misread. All the compiled-API acceptance curls pass, and both suites are green and network-free from an empty build state. It fails on one allergen-safety point: D-026 as written narrows screening. On the real Honey Maid recording, a member with a user-defined "gluten" restriction gets BLOCKED on main and ALLOWED_WITH_UNKNOWNS on this branch, because the engine matches user-defined terms against raw tags and a celiac member can only say "gluten" as a user-defined term under D-017. That breaks the ticket invariant "the tag map never narrows" and the D-017 rule that the worst outcome wins. The worker built D-026 exactly as proposed, so the conflict is in the decision, not the workmanship (rule 25). The second issue is major: the EAN-8 versus UPC-E collision is 58% of the UPC-E code space, not "about 1 in 10", and the precedence decision and the proposed ADR wording rest on the wrong number.

## Judgment calls
- EAN-8 precedence: no worse than main (main already read every check-valid 8-digit code as EAN-8; the new path resolves only codes that cannot be EAN-8; exhaustive: 0 EAN-8s misread), but the cost is far larger than reported (F2). GS1-8 prefixes 000 to 099 are Restricted Circulation Numbers (store-internal), never global GTIN-8s, so a leading-0 8-digit code read as EAN-8 against OFF is a miss or a wrong store-internal item. Recommendation: for a leading `0`, try UPC-E first when its expansion's check digit holds, then EAN-8; keep EAN-8 precedence for a leading `1`. Sending the symbology from the phone stays the real fix; raise its priority.
