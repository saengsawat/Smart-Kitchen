# M2-T7 worker report: lot label and quantity origin on item create

Branch `ticket/M2-T7` (from 40ff295). No migration, no ADR or invariant conflict.

## What changed

- `packages/contracts/src/inventory.ts` (+ index export, + test): `CreateItemRequestDto` gains optional `lotLabel` and `quantityOrigin`; new `CreateItemQuantityOriginDto` and `MAX_LOT_LABEL_LENGTH_DTO` (64).
- `apps/api/src/db/inventory/create-service.ts`: `planCreation` validates the label (trim, 1 to 64 characters counted by code point, no control characters, else `INVALID_FIELD` on `lotLabel`) and the origin (`BARCODE` only; `USER_TYPED` gives the new constant `BARCODE_SCAN_TYPED_SIZE_SOURCE = "barcode-scan-typed-size"`, `PRODUCT_DATA` or absent keeps `barcode-scan`; unknown value or any value on `MANUAL` is `INVALID_FIELD` on `quantityOrigin`). The label goes into the lot insert inside the existing create transaction. Replay now also compares the stored lot label (selected as `l.label` in `findByKey`) and the stored source, so a changed label or origin under the same key is `IDEMPOTENCY_KEY_CONFLICT`. The server never stores a client source string.
- `apps/api/src/http/routes.ts`: body schema accepts `lotLabel` and `quantityOrigin` (loose caps only; the rules live in `planCreation` so the refusal is a ledger `INVALID_FIELD`, not a generic 400) and passes them through. This was needed because the schema has `additionalProperties: false`.
- (d) Item detail: the lot DTO already read `inventory_lots.label`; the DB test confirms the stored label comes back on create and on GET detail. No code change needed.
- Mobile: `quantity.ts` (`ScanPackageSizeInput.userTyped`, `ScanQuantityPlan.origin` with `quantityOrigin` and `lotLabel` "{qty} {unit}", only set when the typed size was actually used, so a typed size in an unsupported unit that falls to the count-only branch sends neither); `scan.tsx` passes `userTyped` and spreads the two fields only when present; fixture `client.ts` mirrors the validation (`LedgerRefusedError("INVALID_FIELD")`) and stores the label on the fixture lot. `HttpApiClient.createItem` already sends the body verbatim.

## Notes and deviations

- The HTTP error body carries `ledgerCode` but not the field name, so DB tests assert `INVALID_FIELD`; the field names (`lotLabel`, `quantityOrigin`) are asserted in the `planCreation` unit tests.
- Label shows the typed package size (e.g. "248 g"), not the total (count x size), matching "{qty} {unit}" in the ticket.
- Out of scope items untouched (locale decimal separator, S5 header, range check, showing label on S5).
