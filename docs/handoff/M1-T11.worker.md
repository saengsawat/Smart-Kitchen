## 2. The two mechanisms

### 2.1 `repository.ts` — savepoint around the insert block

```
await client.query(`SAVEPOINT ${LEDGER_APPEND_SAVEPOINT}`);      // "ledger_append", a module constant
try {
  insert the recorded transaction (+ the clamp ADJUSTMENT if the domain produced one)
} catch (error) {
  if (23505 && constraint === "inventory_transactions_idempotency_key") {
    ROLLBACK TO SAVEPOINT ledger_append; RELEASE SAVEPOINT ledger_append;
    return ok({ status: "rejected", … IDEMPOTENCY_KEY_CONFLICT })      // unchanged payload
  }
  throw error;                                                          // transaction left aborted, deliberately
}
RELEASE SAVEPOINT ledger_append;
```

Three decisions worth the reviewer's attention:

- **The name is a compile-time constant**, never interpolated from caller data. Savepoint names are identifiers and cannot be parameterised, so the only safe name is one no request can influence.
- **The savepoint is released on both the success and the rejection path**, so an append never leaves a savepoint behind for a later append in the same transaction to trip over. Postgres keeps a savepoint alive after `ROLLBACK TO`, so the rejection path needs its own `RELEASE`.
- **Every other error still propagates untouched, with the transaction left aborted.** The sequence-key `23505` the M1-T9 retry helper looks for, a trigger's `40001`, a policy's `42501`: this module is not entitled to decide that the caller's other work should survive an error it does not understand. `withHouseholdTransaction` rolls the transaction back; `withRetriedHouseholdTransaction` re-runs it. Rolling back to the savepoint for an unrecognised error would have been the more "helpful" choice and the wrong one.

**Nesting:** Postgres savepoints nest, so a caller that already holds its own savepoint needs no special handling. A caller holding a savepoint *of the same name* also works: `SAVEPOINT ledger_append` creates a new one that shadows the outer one until this code releases it, which restores the outer. (Documented in the code comment; not tested, since no caller nests today.)

**New precondition made loud:** `SAVEPOINT` outside a transaction block is `25P01`. `appendTransactionToDb`'s header already required a transaction (the `FOR UPDATE` lock and the inserts are only atomic together); calling it on an autocommit connection now fails immediately instead of silently appending without a lock. The doc comment says so.

### 2.2 `session.ts` — what the driver actually returns on COMMIT-of-aborted

Observed directly against the throwaway cluster (Postgres **17.10**, node-postgres **8.23.0**), scratch probe, not inferred:

| Situation | `QueryResult.command` | `rowCount` | error / notice |
|---|---|---|---|
| `COMMIT` on a healthy transaction | `"COMMIT"` | `null` | none |
| `COMMIT` on an **aborted** transaction | **`"ROLLBACK"`** | `null` | **none** — no exception, no notice, `fields: []` |
| `SELECT 1` immediately after that `COMMIT` | `"SELECT"` | `1` | none — **the connection is clean and reusable** |
| `ROLLBACK` immediately after that `COMMIT` | `"ROLLBACK"` | `null` | Postgres emits the **warning notice `there is no transaction in progress`** |

So the fix reads the tag, not the absence of a throw:

```
const commit = await client.query("COMMIT");
if (commit.command === "ROLLBACK") { abortedAtCommit = true; throw new TransactionAbortedAtCommitError(); }
return result;
```

`TransactionAbortedAtCommitError extends Error` (exported, `name` set), message: *"the transaction was in an aborted state at COMMIT, so Postgres rolled it back (COMMIT answered with the ROLLBACK command tag): nothing was committed. Some earlier statement failed and its error was swallowed instead of propagating."*

**Release logic on this path.** The `catch` short-circuits before the rollback attempt and leaves `poisoned === false`, so the client is returned to the pool rather than destroyed. That is correct by the third and fourth rows of the table above: Postgres has already ended the transaction, the connection is usable, and issuing a `ROLLBACK` would only draw a spurious warning. Verified: the pool-reuse test asserts a following transaction commits normally and `pool.waitingCount === 0`, `idleCount > 0`.

**The short-circuit is keyed on a local flag, not `instanceof`.** If `fn` itself were to throw a `TransactionAbortedAtCommitError` (nothing does today, but it is exported), an `instanceof` check would skip the `ROLLBACK` and hand a still-open transaction back to the pool. The `abortedAtCommit` flag is set only where the tag was actually read, so every other error, including that one, takes the normal rollback path.

**What did not change:** `assumeRole` validation and `SET LOCAL ROLE`, the `app.household_id` set_config, the rollback-and-poison logic for ordinary errors, and error identity (an error `fn` throws still comes out by identity). Pinned by two regression tests in `session.test.ts` and by the untouched tenancy/retry suites.

## 5. Proposed `data-model.md` §6 note (for the architect to apply — rule 30)

> **Idempotency rejections are savepoint-scoped.** The database's idempotency index is household-scoped, so a key already used elsewhere in the household is refused by the index rather than by the domain. `appendTransactionToDb` wraps its insert block in `SAVEPOINT ledger_append` and, on `23505` / `inventory_transactions_idempotency_key`, issues `ROLLBACK TO SAVEPOINT` before returning the typed `IDEMPOTENCY_KEY_CONFLICT` rejection. A rejected append therefore costs the caller exactly its own two candidate rows and nothing else: sibling writes earlier in the same transaction stay valid, and the transaction remains usable (a batch writer may keep going, or commit what already succeeded). Every other database error propagates with the transaction left aborted, for the session wrapper to roll back or the retry helper to re-run.
>
> **`COMMIT` is not proof of commit.** Postgres answers `COMMIT` on an aborted transaction with the `ROLLBACK` command tag and no error. `withHouseholdTransaction` inspects `QueryResult.command` and throws `TransactionAbortedAtCommitError` when it is `ROLLBACK`, so "returned normally" means "committed" for every household-scoped write path. Any code that catches a database error and then returns must therefore either use a savepoint (as the repository does) or let the error propagate.

Cost/benefit is real but low priority while every caller goes through `withHouseholdTransaction`. Suggest folding into M2's first HTTP write handler ticket.

Worth a lint rule or a review checklist item before M2 adds handlers, since the failure mode is invisible without the `COMMIT`-tag check.

Options: a longer `afterAll` timeout in the harness, a shared template database migrated once, or `poolOptions` capping file concurrency. Out of this ticket's file scope (`vitest.config.ts` / `harness.ts`).

## 7. Honest gaps and judgement calls

- **The clamp-collision case (a3) injects its error.** A pre-existing row holding `<key>::over-consumption-clamp` is *unreachable* through the schema unless the CONSUME's own key is already burnt: the `inventory_transactions_reserved_marker` check only accepts that suffix on a correctly shaped clamp row, and `inventory_transactions_clamp_cause_fkey` then requires the causing transaction — carrying that very key — to exist on the same item. In that case the **first** insert fails, which is case a1. So a3 injects a driver-shaped idempotency `23505` at the second insert while every other statement (lock, load, first insert, savepoint statements) runs for real against the cluster. The rewind it asserts is genuine SQL. I decided this was worth testing with an injected error rather than not testing at all; the reviewer may disagree. Conversely, this also means **the two-row rewind cannot occur in production today** — worth knowing when judging risk.
- **d2–d4 inject their errors too**, for the reason stated in the file: through the repository, a real sequence-key `23505` or trigger `40001` needs genuine concurrency (the `FOR UPDATE` lock serialises writers), which cannot be scheduled deterministically. Real-error coverage of those codes lives in `retry.test.ts` (8-way contention) and `constraints.test.ts`, both untouched and green. d1 and e are the two cases here that use **real** database errors, at statement time and at COMMIT time respectively.
- **Savepoint nesting is documented, not tested.** No caller nests today; a test would be constructing a situation the codebase does not contain. Flagged rather than invented.
- **`rowCount`/`fields` on the aborted `COMMIT`** were observed once, on one cluster and one driver version, and are recorded in §2.2 for the reviewer to re-check. The code depends only on `command`.
- **No production caller exists yet**, so this fixes a latent defect. The behavioural claim I am making is exactly what the tests assert and no more: after this change, within the repository write path, a return from `withHouseholdTransaction` means committed, and a typed idempotency rejection leaves siblings intact.
- **Throwaway cluster** (`initdb` on a scratch path, port 55442) stopped and deleted at the end of the session; the installed Windows PostgreSQL service was never touched.

## 8. Fixes applied (post-review)

Independent Opus review of `a3a8eec` returned **PASS WITH FIXES**: code correct, one required test, no source change.

**F1 (MEDIUM, required) — the `abortedAtCommit` flag decision had no coverage.** The short-circuit in `session.ts` is keyed on a local flag precisely so that a `TransactionAbortedAtCommitError` thrown *by `fn`* still takes the real `ROLLBACK` path (§2.2). Nothing tested that: the reviewer's mutation **M8** (`if (error instanceof TransactionAbortedAtCommitError)`) survived all 785 tests, and the hazard is real — on a `max: 1` pool the next borrower of the same physical connection saw an open transaction with `SET LOCAL ROLE sk_app` and the previous request's `app.household_id` still in force, which is a tenancy boundary (data-model.md §5) broken by a connection that was never cleaned up.

**Fix:** one new DB-gated test in `apps/api/src/db/session.test.ts` — *"rolls back normally when fn itself throws TransactionAbortedAtCommitError"*. It runs against a second pool built with `max: 1` (so "the next borrower" is literally the same connection), has `fn` insert a row as `sk_app` under a household context and then throw a `TransactionAbortedAtCommitError`, and asserts: the error propagates **by identity**, the insert is **not durable**, and the next borrower observes `pg_current_xact_id_if_assigned() IS NULL` (no open transaction), `current_user` back off `sk_app`, and `current_setting('app.household_id', true)` empty. The single-connection pool is closed in `afterAll` before the database is dropped. No source file changed for F1.
