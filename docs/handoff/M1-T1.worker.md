## 1. What was built

All code is in `packages/domain/src/inventory/**` plus the package entry point. Zero runtime dependencies,
zero I/O, no clock, no randomness: the module is a pure function of its inputs, so the same call sequence
always produces the same ledger.

### Design decisions worth the reviewer's attention

1. **Exact arithmetic, not floats.** Every delta is stored twice: `qtyDelta: number` (the boundary/display
   form the caller supplied) and `qtyDeltaMicros: bigint` — the authoritative value, in micro-units
   (scale 1e-6). All ledger addition is `bigint`. This is what makes INV-LEDGER-1 *exactly* true: with
   `number` addition, `currentQty == Σ deltas` is order-dependent and false for ordinary grocery decimals
   (`0.1 + 0.2 !== 0.3`), so a maintained snapshot would provably drift from a recomputed sum. Inputs that
   cannot be represented exactly are **rejected, never rounded** (`PRECISION_EXCEEDED`, `NOT_FINITE`,
   `QUANTITY_OUT_OF_RANGE`). `MAX_QUANTITY_MICROS` is 1e14 (1e8 units) so every representable quantity has
   ≤15 significant digits and round-trips exactly through its `number` view.
2. **Total functions.** No domain-rule violation throws. `appendTransaction` returns
   `appended | duplicate | rejected`, and on the two non-appended paths returns the *same aggregate
   instance* — callers can assert "nothing was written" by reference.
3. **Runtime immutability.** Every returned aggregate is deep-frozen. Because the package is ESM (strict
   mode), writing to a recorded row throws `TypeError` instead of silently corrupting the ledger.
4. **Ordering.** `sequence` (1-based, per item, assigned at append) is the ledger's authoritative order, not
   `occurredAt` — backdated entries are recorded where they were appended, so history never rewrites itself.
5. **Units are pass-through and strict.** An item declares one unit; a transaction or lot in any other unit
   is rejected `MIXED_UNITS`. No conversion, no case-folding, no guessing — that is M1-T3's job.
6. **No clock.** `recordedAt` is supplied by the caller; the domain only validates that it is a well-formed
   instant and not earlier than `occurredAt`.

## 2. Exact negative-quantity semantics (the policy this ticket had to settle)

The ticket directed the PROPOSED "clamp + flagged adjustment" approach (domain-model.md §4.2, ADR-008 open
question) and left the details to implementation. What is implemented:

**Rule.** No committed state of a lot or an item is ever negative. When a decrease would take a lot below
zero, the ledger appends **two rows in one atomic operation**:

1. the caller's transaction, **recorded at its full stated magnitude** (it is *not* trimmed), and
2. a compensating `ADJUSTMENT` for the exact residual, authored by the system.

**Worked example.** Lot holds 1.00 lb; the user logs `USE_IN_MEAL −1.25 lb`.

| seq | type | qtyDelta | actor | flag | balance |
|---|---|---|---|---|---|
| n | `USE_IN_MEAL` | −1.25 | user | — | (−0.25, uncommitted intermediate) |
| n+1 | `ADJUSTMENT` | +0.25 | system `inventory-ledger` | `OVER_CONSUMPTION`, residual 0.25 | **0.00** |

**Specifics:**

- **The user's statement is preserved.** Trimming the consumption to −1.00 would silently rewrite what the
  user told us. Recording −1.25 plus a flagged +0.25 says the true thing: *"you used 1.25; our record was
  0.25 short."* The residual is inventory-accuracy data — the correction-rate KPI (brief §18C) reads it
  directly.
- **Clamping is per lot.** One lot's surplus never covers another lot's overdraw; a decrease on lot A is
  clamped against lot A's balance only. Because every lot is ≥ 0, the item total is ≥ 0 by construction.
- **All decreasing instruments clamp, including `ADJUSTMENT`.** A negative `ADJUSTMENT` larger than the
  balance is clamped and flagged the same way. Negative physical stock is meaningless, so no instrument can
  produce it. (Note for the architect: INV-LEDGER-4's wording — *"negative quantity is impossible without an
  explicit flagged adjustment"* — can be read as permitting a deliberately flagged negative balance. The
  implementation takes the stronger reading: never negative, and the flagged adjustment is the mechanism
  that guarantees it. Proposed doc wording in §6.)
- **The clamp row is unmistakably system-authored:** `type: "ADJUSTMENT"`, `actor: {kind:"system",
  component:"inventory-ledger"}`, `reason: "over-consumption-clamp"`, `provenance: {tier:"ESTIMATED",
  source:"inventory-ledger:over-consumption-clamp"}`, and `systemFlag: {kind:"OVER_CONSUMPTION",
  residualMicros, residual, causedBySequence, causedByIdempotencyKey}`. It inherits the causing row's
  `correlationRef`, so a clamp caused by a meal log stays traceable to that meal.
- **Deterministic, replay-safe key.** The clamp's idempotency key is `<causing key>::over-consumption-clamp`.
  Caller keys may not contain the reserved separator `::` (`INVALID_IDEMPOTENCY_KEY`), so system rows can
  never collide with user rows, and replaying the causing key is a no-op that does **not** produce a second
  clamp.
- **Zero-delta transactions are rejected** (`ZERO_DELTA`) and **sign must match the type**
  (`WRONG_SIGN`): `PURCHASE`/`INITIAL_STOCK` are positive, `CONSUME`/`USE_IN_MEAL`/`DISCARD`/`EXPIRE`/
  `DONATE` are negative, `ADJUSTMENT` is the only signed instrument.

**Idempotency detail worth ratifying.** A key reused with a *materially different* payload is
**rejected** (`IDEMPOTENCY_KEY_CONFLICT`) rather than swallowed as a duplicate — silently discarding a
different write would be exactly the "inventory disappears" failure INV-LEDGER-1 exists to prevent.
Comparison covers every field except `recordedAt` (a genuine retry legitimately arrives later).

## 3. Tests

`packages/domain/src/inventory/*.test.ts` + `packages/domain/src/index.test.ts` — **63 tests, all passing**.

- **`invariants.property.test.ts`** — fast-check property tests, each `describe` named for its invariant:
  - **INV-LEDGER-1** — over any generated sequence (mixed types, two lots, pooled keys so
    duplicate/conflict paths are exercised): snapshot == Σ deltas at item *and* lot level; every accepted
    append moves the balance by exactly the rows it wrote; rejections/replays write nothing; every row is
    attributable (contiguous sequence, item id, unit, actor, provenance source, unique key, non-zero delta);
    `reconcile().ok`. Plus: derivation is order-independent (shuffled sums identical).
  - **INV-LEDGER-2** — earlier rows are byte-identical after later appends and are the *same frozen object
    references*; mutation of a row or of the transactions array throws `TypeError`; a correction appends an
    `ADJUSTMENT` and leaves the original row untouched.
  - **INV-LEDGER-3** — replaying every input of any generated sequence, in a shuffled order and with a later
    `recordedAt`, returns `duplicate` for each and leaves the aggregate identical by reference and by
    serialization; a clamped write replays without generating a second clamp.
  - **INV-LEDGER-4** — no committed state is ever negative; whenever a decrease overshoots, a flagged
    system `ADJUSTMENT` with the exact residual is present and the lot lands on 0; the un-clamped case emits
    no adjustment; only the ledger authors flagged rows; walking the stored rows, the balance dips below
    zero only inside a clamped pair, whose next row is that clamp. A non-vacuity counter asserts the
    generated space actually reaches the clamp branch.
- **`transaction-types.test.ts`** — an example per transaction type (with a test asserting the case list
  covers `TRANSACTION_TYPES` exactly), the negative-`ADJUSTMENT` correction case, a waste-analytics query
  over reasons, and **the brief §7 worked example verbatim**: chicken breast 2.0 lb, `USE_IN_MEAL` −0.75 lb
  ⇒ **1.25 lb** (asserted as `amount === 1.25`, `micros === 1_250_000n`, and `"1.25 lb"`), plus its retry
  case (logging the same meal twice still leaves 1.25 lb).
- **`ledger.test.ts`** — creation/lot opening; every rejection path (mixed units, unknown lot, zero delta,
  wrong sign, unrepresentable quantity, malformed/out-of-order timestamps, incomplete attribution, reserved
  key); idempotent replay and key conflict; the clamp cases incl. per-lot isolation and correlation
  inheritance; immutability; derivation/reconciliation incl. tampered-snapshot and multi-problem detection;
  rehydration incl. corrupt-history refusal.
- **`quantity.test.ts`** — exact conversion, explicit float-drift contrast, rejection of unrepresentable
  values, round-trip properties, formatting, frozen quantities.
- **`index.test.ts`** — the placeholder test was replaced with a real public-API surface test (package name,

## 8. Open questions for the architect

1. **Idempotency key scope in the database (M1-T2).** The domain enforces uniqueness *within one item's
   ledger*. The same key on two different items is currently possible. M1-T2 must decide the unique index:
   `(item_id, idempotency_key)` (matches the domain) vs `(household_id, idempotency_key)` (stronger; safer
   for receipt/meal batches that fan out across items). Recommendation: household-scoped, with per-line key
   suffixes.
2. **AI-tier rows.** A transaction may currently carry `provenance.tier: AI_INTERPRETATION` without
   `confirmedBy`. I did **not** add a gate, on the reading that confirmation is enforced upstream at the
   `AIObservation` boundary (INV-CONF-1, ai-architecture.md §2) and that a ledger-level rule here could
   conflict with that ticket. Confirm — if the ledger should also refuse unconfirmed AI-tier rows, that is a
   small, testable addition.
3. **Clock skew vs `recordedAt >= occurredAt`.** The ledger rejects `TIMESTAMP_ORDER`. Offline clients
   (ADR-010) with skewed clocks could legitimately trip this. Should there be a tolerance window, or should
   the sync layer normalise timestamps before append?
4. **Snapshot maintenance (ADR-008 open question, M1-T2).** The domain maintains item and lot snapshots with
   each append; the DB must do the same *in the same transaction* (app-tx) or via trigger. The domain's
   `reconcile()` is the reference implementation for the reconciliation query.
5. **Extreme totals.** Per-*delta* magnitude is capped at 1e8 units so any single delta's decimal view is
   exact. **Correction (review F5/R1):** my original "~1e6 appends" figure was wrong — the guarantee is
   per delta, not per balance, and a balance can pass the exact-view threshold after as few as ~100 appends
   at the per-delta maximum (1e14 × 100 = 1e16 micro-units). Past that, `micros` stays exact and
   authoritative while the `amount` view may round in its last digits. **Architect decision recorded: no
   balance cap; the comment in `quantity.ts` now states this honestly** rather than overclaiming.
6. **Merge strategy for this branch (needs an architect decision).** Commit `b917222` still contains the
   gitleaks false positive described in §4. Options, in my order of preference:
   1. **Squash-merge** the branch — the merge produces one commit whose content is the fixed version, so the
      push scan on `main` is clean and no history is rewritten. Recommended, and it fits "short-lived
      branches" in CONTRIBUTING.
   2. **Architect authorises a rebase/force-push** on this feature branch to fold `2eb4fe4` into `b917222`.
      I did not do this unprompted: the dispatch instruction was explicit that the worker never force-pushes.
   3. Merge normally and accept that a `pull_request`-triggered run (or any future full-history scan) will
      flag `b917222`; a `.gitleaksignore` fingerprint entry would then be needed — a root-level file outside
      this ticket's scope, and a worse outcome than 1 or 2 because it permanently weakens the gate.

## 9. Proposed backlog items

1. **Lot-selection policy for consumption (FEFO/FIFO).** `appendTransaction` requires a `lotId`; nothing yet

2. **M1-T2 acceptance additions** derived from this module: ledger tables reject UPDATE/DELETE; unique index
   on the idempotency key (scope per item 8.1); snapshot updated in the same DB transaction as the append;
   a reconciliation query whose results match `reconcile()` on generated data.
3. **Correction-rate telemetry query.** The KPI is now directly derivable: count/sum of `OVER_CONSUMPTION`
   clamps and user `ADJUSTMENT` rows over total transactions. Small analytics ticket once M1-T2 lands.
4. **`Unit` type replacement when M1-T3 lands.** `Unit` is `string` here; M1-T3 should replace it and add
   conversion at the *service* boundary, keeping the ledger's "one unit per item, no silent conversion" rule.
5. **Boundary schema validation.** The domain re-validates untrusted-shaped input defensively; when
   `packages/contracts` gains request schemas, decide whether the API layer validates first and the domain
   keeps its checks as a belt-and-braces layer (recommended) or defers.
