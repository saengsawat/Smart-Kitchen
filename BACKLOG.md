# BACKLOG.md — Implementation Backlog

Authoritative work plan. Structure: **Milestone → Epic → Ticket**. M0 and M1 are fully ticketed and complete; M2 (API) and M3 (client) are ticketed one step ahead of the work as each predecessor is accepted (M2-T1, M2-T2, M3-T1 to M3-T4b done; M2-T3 and M3-T5 done 2026-09-29; M2-T3, M2-T4a, M3-T4d, M3-T4e and M3-T5 done 2026-09-29; batch A: M7-T1, M3-T6 and M9-D1 done 2026-09-30, M9-T0 and M2-T4b done 2026-10-01, R-6 open on the FoodKeeper download; M2-T4 outlined); M4 to M9 stay at epic level until reached. No speculative ticket dumps. Sequencing is dependency-driven, not demo-driven.

> **Tracking view:** a spreadsheet mirror of this backlog (tickets, model recommendations, status column) lives in `BACKLOG_TRACKER.xlsx` / `BACKLOG_TRACKER.csv` for status tracking. **This file remains authoritative** for ticket content; when tickets change here, regenerate/update the tracker (status values live in the tracker only).

> **Finished tickets live in [BACKLOG_ARCHIVE.md](BACKLOG_ARCHIVE.md)** (moved 2026-10-03, PO request, to cut what every agent has to read). This file keeps open tickets, epics, follow-ups and the template. When a ticket is accepted as DONE, the architect moves its section to the archive in the same docs commit.

**Gate:** No implementation starts until the product owner approves D-002 (MVP scope) and D-003 (ledger) in [DECISIONS.md](DECISIONS.md). Ticket 1 additionally requires explicit go-ahead from the product owner (per founding task).

**Ticket template** — every ticket includes, in order:

1. **Implementation model:** Sonnet | Opus — reason
2. **Review model:** Sonnet | Opus — reason
3. **Objective**
4. **Context**
5. **Dependencies**
6. **Invariants**
7. **Acceptance criteria**
8. **Tests required**
9. **File scope**
10. **Out of scope**
11. **Definition of done (DoD)**

Model routing rules (default Sonnet; Opus for the high-risk domain list; separate reviewer always required before done) are defined in [CLAUDE.md rules 20–27](CLAUDE.md). The architect sets the model lines; deviating requires architect sign-off recorded on the ticket. Work outside a ticket's file scope requires escalation, not improvisation.

#### R-6 — Shelf-life data research: USDA FoodKeeper coverage, licence and the estimation rule (docs only)
- **Implementation model:** Sonnet. A research spike in the R-1 pattern: a script, a raw capture, a findings document; no app code.
- **Review model:** Sonnet. The reviewer checks the licence statement against the source, re-runs the coverage numbers, and that nothing in the findings is asserted without evidence.
- **Decision basis:** the brief's expiry tracking; ADR-006 (data sources); rule 17 (no signup, no spend, no new external service beyond a public-domain download; if the source requires an account, terms beyond public domain, or an API key, stop and report instead of proceeding); rule 18 (fixtures).
- **Objective:** (a) locate the USDA FoodKeeper dataset (FSIS; published on data.gov and as the FoodKeeper app's data), record the exact URL, retrieval date, format and the licence or public-domain statement verbatim; download it once into `tests/fixtures/shelf-life/raw/` with a README (source, date, checksum, licence). (b) Measure coverage: for each of the 101 fixture products (`tests/fixtures/products`) and the nine seeded Chen items, can a FoodKeeper row be matched by category (pantry, fridge, freezer ranges; opened versus unopened) using a simple, documented mapping from the product's `category` and name; report hit, ambiguous and miss counts with examples, the same way R-1 reported OFF. (c) Describe the data shape: per-category ranges (min, max, metric), storage types, opened/unopened, and where ranges are missing or contradictory. (d) Propose, marked PROPOSED and with evidence: a `shelf_life_rules` table or a static JSON in `packages/adapters` (compare both), the estimation rule (best-by = the anchoring date plus the range minimum for the item's storage location; anchoring date = purchase or open date, never invented; tier ESTIMATED with source `usda-foodkeeper` and the rule id; a printed label date always wins and is never overwritten; the estimate is confirmable and correctable through the existing S5 flow), the mapping approach from OFF `categories_tags` and our fixture categories to FoodKeeper categories, and the open questions for the PO (opened-date capture on S5, freezer moves, what the freshness ring shows when only an estimate exists). (e) Deliver `docs/research/shelf-life.md` with a coverage table, `docs/research/shelf-life.raw.json` (the measured matches), and `scripts/shelf-life-coverage-research.mjs` (offline against the downloaded file; never in `pnpm test`).
